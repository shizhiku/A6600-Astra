# 129 · 第十六轮：阻塞点精确锁定（重大进展）

> 时间：2026-11-22。纯离线 QEMU + 静态分析。

## 一、方法学突破：探针必须落在指令边界

之前多轮"定位失败/崩溃"的**根本原因**是：探针地址没有落在 32-bit Thumb 指令边界上。例如我用了 `0x54F690`，而真实指令边界是 `0x54F68E`。打在指令中间会破坏指令流 → `sig=11`。

**修正后**，用 capstone 逐条列出 `0x54F664` 的指令边界与长度，只在"调用指令 + 其长度"的位置布点，全部稳定命中、零崩溃。

## 二、前几轮的错误结论（已推翻）

| 之前的判断 | 实际情况 |
|---|---|
| `0x54EF74` 里的 `blx r3` 是阻塞点 | **错**。vtable[0] = `0x54D05C`，是 `push/add/pop` 三指令 no-op，立即返回 |
| `0x54EF74` 不返回 | **错**。`S_54F678`（`bl 0x54EF74` 的返回点）实测命中 |
| 台阶探针"不命中"意味着阻塞 | **错**。台阶探针每次命中后重新 `dladdr` 太慢，错过后续点 |

## 四、阻塞点精确锁定

**`0x54F71A` 的 `bl 0x60E2F4` 不返回。**

### 4.1 `0x60E2F4` 结构

```asm
0060e2f4  push {r7, lr}
0060e2f6  add  r7, sp, #0
0060e2f8  bl   0x54E140        ; 只读 getter，立即返回
0060e2fc  cmp  r0, #1
0060e2fe  bne  0x60E308        ; != 1 则返回
0060e300  pop.w {r7, lr}
0060e304  b.w  0x60E274        ; == 1 则【尾调用】，不压返回地址
0060e308  pop  {r7, pc}
```

关键：`b.w` 是尾调用，**不压入返回地址**，所以 `0x54F722` 永远不执行。

### 4.2 `0x54E140` 是纯 getter（排除）

```asm
0054e140  ldr r3, [pc, #0x10]
0054e148  ldr r2, [r2]              ; 取全局索引
0054e14e  ldr.w r0, [r3, r2, lsl #2]  ; 返回 table[index]
0054e152  pop {r7, pc}                ; 立即返回
```

### 4.3 `0x60E274` 是真正的阻塞函数

```asm
0060e274  push {r4,r5,r6,r7,lr}
0060e278  sub  sp, #0x1c
0060e280  ldr  r5, [全局对象]
0060e282  add.w r4, r5, #8         ; 起点
0060e286  adds  r5, #0x68          ; 终点 → 2 次迭代，步长 0x30
0060e288: 循环体
0060e290  blx  0x52A60C            ; memset
0060e2aa  blx  0x9257D8            ; ← 关键
0060e2be  blx  0x924500            ; ← 关键
0060e2dc  adds r4, #0x30
0060e2de  cmp  r4, r5
0060e2e0  bne  0x60E288
0060e2e8  pop  {r4,r5,r6,r7,pc}
```

### 4.4 `0x9257D8` 解析为 OSAL 调度锁封装

veneer `0x9257D8` → `0x2B1B524`：

```asm
02b1b524  push {r4,r5,r7,lr}
02b1b528  movs r0, #0xf
02b1b52c  mov  r1, r0
02b1b530  bl   0x2C2E46C        ; sched_lock(0xf, 0xf)
02b1b534  mov  r0, r5
02b1b538  bl   0x2B749CC        ; 业务函数
02b1b540  pop.w {r4,r5,r7,lr}
02b1b544  b.w  0x2C2E3C0        ; sched_unlock(0xf, 0xf)
```

### 4.5 `0x2B749CC` 是 infra_wrapper 的内存映射释放函数

通过 pc-relative 字面量解出的日志字符串（决定性证据）：

```
'[INFRA_WRAPPER]'
'%s%s(%d) munmap ERROR! errno = %d\n'
'munmap'
```

函数结构：

```asm
02b749d6  ldr r3, [r0, #8]      ; 句柄
02b749dc  cmp r3, #0
02b749de  blt 0x2b74a34         ; <0 → 状态 3
02b749e0  ldm r0, {r0, r1}
02b749e2  blx 0x2BA0FAC        ; ← 第一个外部调用
02b749e6  cmp r0, #0
02b749e8  bge 0x2b74a0a
02b749ea  blx 0x2BA1818        ; 错误处理
02b74a02  bl  0x2C2B288        ; 日志，行号 0x273
...
02b74a80: 循环
02b74a96  blx 0x2BA0E94        ; 读取/recv 类
02b74aa2  blx 0x2BA074C        ; 关闭/close 类
```

### 4.6 `0x2BA0FAC` 一类是 ARM 长跳 veneer 表

```asm
02ba0fac  ldr  ip, [pc]
02ba0fb0  add  pc, pc, ip      ; 直接跳转（尾跳）
```
以及 `0xE28FC632` = `add ip, pc, #0x632` 形态，属于 **GOT 间接跳转桩**，用于调用外部共享库函数（libObj 等）。

## 五、结论与含义

**阻塞机制**：五代 `Application_Start` → `0x54F664` → `0x60E2F4` → 尾调用 `0x60E274` → 在 `sched_lock(0xf,0xf)` 保护下，循环调用 **infra_wrapper 的 munmap 封装** 释放 2 个对象的内存映射。该调用**未返回**。

**最可能的原因**：
1. **`sched_lock(0xf, 0xf)` 本身在等锁** —— 若另一个线程已持同一把锁且永不释放（例如我们缺失的初始化任务本应释放），就会永久阻塞；
2. **`munmap` 对应的内存映射在内核侧状态不一致** —— 我们 QEMU 环境下 `/dev/mem`、`dmpgles2` 等映射由模拟器处理，可能未正确响应 unmap；
3. `0x2BA0FAC` 等 GOT 桩指向的 libObj 函数在我们环境里解析到了错误实现。

## 六、下一轮（已明确）

1. 解析 `0x2BA0FAC`、`0x2BA0E94`、`0x2BA074C` 等 GOT 间接桩，得到**真实导入符号名**（如 `munmap`、`close`、`ioctl`）——需要正确处理 `add ip,pc,#imm` + `ldr pc,[ip]` 形态；
2. 若确认是 `sched_lock` 等锁，用 4 点探针在 `0x2C2E46C`（sched_lock）与 `0x2C2E3C0`（unlock）布点，判断是加锁前阻塞还是加锁后；
3. 若确认是 `munmap`，检查 QEMU 侧 `/dev/mem` 映射实现是否支持 unmap 并返回值。
