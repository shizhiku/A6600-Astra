# 80 · 字体注册链路完整分析（libObj.so 纯静态）

> 目标：搞清 Sony AppFramework 里「字体注册」的完整链路，并给出**不依赖副控制器**把中文字体注册进内存注册表的方法。
> 本轮为**纯静态分析**（不运行 QEMU、不改镜像）。分析对象：`03-证据/静态分析/libObj.so`
> （20,889,004 B，ELF32 ARM E_INVALID/ET_DYN，`.text` 0x104A30–0xE3F120，`.rodata` 0xE3F128 起，`.bss` 0x13F3820–0x1431FE8）。
> 文中地址一律为 **libObj 内偏移（= 文件偏移，代码段恒等映射）**；运行期基址按项目既有 0x057E3000 叠加。

---

## 〇、结论摘要（先看这里）

1. **`0x63E2DC`（`ux::core::TextLayout::registerFontFaceFile`）根本不碰字体链表** `0x13F64FC`。
   它只是一个 3 行转发器：取单例 → 取 `*(inst+0x30)` 子对象 → 调该子对象虚表第 0 项 `fn(u8, char*, u8)`。
   真正写链表的结构在另一个子系统（TextRM C API，0x54Exxx），而两条路径**没有任何静态连接**。
   全库对 `0x13F64FC` 的写入点只有 2 处（初始化清零 + 建节点前插），两者都不在 `0x63E2DC` 的可达链上 → **方案 (a) 方向错误**。

2. **注册的真实入口是「字体列表文件解析器」`0x54E94C`**，它由一次性初始化 `0x54F3A0` 调用（唯一调用点 `0x54F42C`）。
   它的**文件路径不是硬编码**：先 `Backup_get_datasize(0x810000)` / `Backup_read(0x810000, buf)` 从 **Backup 数据区（ID 0x810000）** 取出一段**路径字符串**，再 `fopen(那块内存, "r")`；
   只有在 Backup 取不到数据时才回退到 `fopen("TEXTRM_FONT_LIST", "r")`（一个 16 字节的"假路径"，实际不存在）。
   这解释了"全固件里没有 fontlist 字符串"——**路径是数据驱动的**。

3. **`fontlist.dat` 的格式与该解析器完全吻合**（TAB 分隔 4 字段：`名字 \t 路径 \t id \t flag`，多次 TAB 被跳过=允许对齐填充）。
   解析每行 → `createNode` 建节点 → 写 name/path/id/flags。注册**不要求字体文件存在**（文件是 `TextRM_loadFont` 时才 fopen 的）。
   因此**不需要副控制器**：只要让这次 `fopen` 成功且内容含 `FONT_S_CHINESE` 一行，注册即完成；之后 `/tmp/images/*.ltt` 存在即可正常加载。

**推荐落地（最省事 → 最稳妥）**：① 在 UI 进程 CWD 放一个名为 `TEXTRM_FONT_LIST` 的文件；或 ② 把 `.rodata` 里 `"TEXTRM_FONT_LIST"` 这 16 字节原地改成 `"/fontlist.dat"`（长度够，纯字符串补丁、零代码改动），再把 `fontlist.dat` 放到 `/`；或 ③ 改 Backup 数据区 ID `0x810000` 的值为真实路径。

## 一、方法与可复核性（本轮同时修正了一个寻址错误）

| 项目 | 做法 | 规模 |
|---|---|---|
| 反汇编 | capstone 5.0.7，Thumb，`skipdata`，按 1 MB 分段（整段 13.8 MB 单次调用会崩） | 全 `.text` |
| 导入符号还原 | 解析 `.rel.plt`（2547 条）→ 手工解码 ARM PLT stub（`add ip,pc,#imm` + 旋转）→ GOT 槽号 → `.dynsym` 名 | **2546/2547 成功** |
| 直接调用图 | 不依赖反汇编器，**按位解码全部 Thumb-2 `BL`/`BLX`/`B.W` 编码**，逐 2 字节扫 `.text` | **698,835 个调用点 / 74,220 个不同目标** |
| PC 相对数据引用 | `ldr rX,[pc,#imm]` 与随后的 `add rX,pc` 配对求目标 | 140,214 条 xref |
| 函数指针/虚表 | 全文件按 4 字节搜目标地址；`.data.rel.ro` 逐字扫描 | 见 §六 |

> **重要修正（影响之前若干文档的字面量推导）**：
> Thumb 的 `add rX, pc`（高寄存器 T2 编码 0x44xx）其 PC 值 = **指令地址 + 4，不做 4 字节对齐**；
> 而 `ldr rX,[pc,#imm]`（字面量加载）用的是 **Align(insn+4, 4)**。本轮用两个独立锚点验证了这一点：
> `0x54E81A` 的 `add r3,pc`（insn+4=0x54E81E）恰好复现链表头 `0x13F64FC`；
> `0x54E59E` 的 `add r3,pc`（insn+4=0x54E5A2）恰好复现 flag 映射表 `0xF85CA0 = {0,1}`。
> 若按"对齐"规则算，会得到 0x13F64FA / 0xF85C9E 这种差 2 字节的错值——文档 68 的链表头结论是对的（那一处恰好在 4 字节边界上），但同法用于别处会错。

## 三、字体节点结构体（0x314 B，`malloc` 于 `0x54E804`）

`create_node(char** out)` @ `0x54E7D4` 反汇编要点：

```
54e7d4 push {r4,r5,r6,r7,lr}; sub sp,#0xc
54e7d8 ldr r4,[pc,#0x80] ; 字面量 0x00EA7D14
54e7da movw r3,#0x3e6                     ; 上限 998
54e7e0 add r4,pc                          ; r4 = 0x13F64F8 = &count
54e7e4 ldr r5,[r4]                        ; r5 = count
54e7e6 cmp r5,r3
54e7e8 ble 0x54e804                       ; 超过 → 记 "The maximum index of the fontID has been exceeded" → 返回 -0x14
54e804 mov.w r0,#0x314; blx malloc
54e80e str r0,[r6]                        ; *out = 新节点
54e812 ldr r3,[pc,#0x54]                  ; 字面量 0x00EA7CDE
54e814 adds r5,#1                         ; index = count+1
54e816 str r5,[r0,#4]                     ; node->index
54e81a add r3,pc                          ; r3 = 0x13F64FC = &head
54e81c strb r0,[r1,#8]                    ; node->name[0]=0
54e81e strb.w r0,[r1,#0x208]              ; node->path[0]=0
54e822 strb.w r0,[r1,#0x108]              ; node->desc[0]=0
54e826 ldr r2,[r3]                        ; old head
54e828 str r5,[r4]                        ; count = index
54e82a str.w r0,[r1,#0x310]               ; refcount=0
54e82e strh.w r0,[r1,#0x308]              ; id=0
54e832 str.w r0,[r1,#0x30c]               ; flags=0
54e836 str r2,[r1]                        ; node->next = old head
54e838 str r1,[r3]                        ; head = node   ← 前插
```

| 偏移 | 类型 | 含义 |
|---|---|---|
| `+0x000` | ptr | `next`（链表，前插，故遍历顺序与文件相反） |
| `+0x004` | u32 | `index`（1 起递增序号，= 建立时的 count+1） |
| `+0x008` | char[0x100] | **name**（`FONT_xxx`，`find_by_name` 的唯一键） |
| `+0x108` | char[0x100] | **desc**（加载成功后由 `0x5662C2` 生成的引擎侧描述名） |
| `+0x208` | char[0x100] | **path**（字体文件路径，`loadFont` 用它 fopen） |
| `+0x308` | u16 | **id**（字体 ID，传给 `0x54E5B0`） |
| `+0x30C` | u32 | **flags**（flag 字段） |
| `+0x310` | u32 | 引用计数 |

> 注意：`+0x208` 是路径、`+0x108` 是"描述名"，两者容易混。`fontlist.dat` 的解析器写的是 name(+8) 与 path(+0x208)；`0x54EE50` 写的是 desc(+0x108) 与 path(+0x208)，**name 保持空串**。

## 四、注册链路 A：一次性初始化 → 字体列表文件解析器

### 4.1 解析器 `0x54E94C`（完整伪代码，含被调用的导入函数名）

导入函数是通过 PLT 解析出来的真实符号（见 §一的方法），因此这段语义是确定的：

```c
long load_font_list(void)          // 0x54E94C, 栈帧 0x124, 忽略全部入参 r0-r3
{
    char  line[0x100];             // r7+4
    char* buf = NULL;              // r5
    FILE* fp  = NULL;              // r4
    long  err = -9999;             // fp 寄存器终值字面量 0xFFFFD8F1
    int   bad = 0;                 // r5 复用：出错/格式标志

    memset(line, 0, 0x100);                                     // 0x54E95E PLT memset
    if (Backup_get_datasize(0x810000) > 0) {                     // 0x54E966 PLT Backup_get_datasize
        buf = malloc(0x810000);                                  // 0x54E96E PLT malloc（固定 8 MB 缓冲）
        if (buf != NULL && Backup_read(0x810000, buf) > 0) {      // 0x54E97A PLT Backup_read
            fp = fopen(buf, "r");                                // 0x54E99A  ← 路径来自 Backup 数据
            free(buf);
        }
    }
    if (fp == NULL)                                              // 0x54E984 回退分支
        fp = fopen("TEXTRM_FONT_LIST", "r");                     // 0x54E98C  ← 字符串在 .rodata 0xF85C34
    if (fp == NULL) {
        log(0x81, 0, file, "The font list file was absent or corrupted ...", 0xF85C45);
        return -9999;                                            // 0x54E9C4 直接返回，不 fclose
    }
    while (fgets(line, 0x100, fp)) {                              // 0x54EA92 PLT fgets
        n = strlen(line);                                        // 0x54E9C8 PLT strlen
        if (line[n-1]=='\n') line[n-1]=0;                        // 去 \n
        if (line[n-2]=='\r') line[n-2]=0;                        // 去 \r
        t1 = line;                                               // 0x54E9E6
        t2 = next_token(t1);                                     // 0x54E534：TAB→NUL，跳过连续 TAB
        t3 = next_token(t2);
        t4 = next_token(t3);
        id    = parse_int_or_default(t3, 0);                     // 0x54E560 PLT strtol
        flags = flag_table[parse_int_or_default(t4, 0)];         // 0x54E594 + 表 0xF85CA0={0,1}
        if (!t1 || !t2 || !t1[0] || !t2[0]) { bad = t1 ? t2 : t1; continue; }
        node = NULL;
        if (create_node(&node) != 0) break;                       // 0x54EA46（唯一建节点处之一）
        set_name (node, t1);                                      // 0x54E8EE
        set_path (node, t2);                                      // 0x54E908
        set_id   (node, (u16)id);                                 // 0x54E938
        set_flags(node, flags);                                   // 0x54E924
    }
    if (bad) { /* fp = 0 */ }
    else log(0x81, 0, file, "The font list file format is invalid ...", 0xF85C74);
    fclose(fp);
    return fp_last;                                              // 0 / 最后节点 / -9999
}
```

要点：
* 路径 → **Backup 数据区 ID `0x810000`**（8 字节对齐的"数据项"概念，与文档 31–40 里已改过的 Backup 区同一子系统）；回退串 `"TEXTRM_FONT_LIST"` 是**占位假名**（16 字节，`0xF85C34`）。
* 字段分隔是 **TAB(0x09)**，不是空格；连续 TAB 会被跳过（所以 `fontlist.dat` 里 `FONT_KOREAN\t\t/usr/...` 也正确）。
* 缺字段不致命：`t3/t4` 为 NULL 时 id=0、flags=table[0]=0。
* **文件不存在 → 返回 -9999 → 上层初始化判定失败**（见 4.4），所以"文件打不开"不是静默，而是直接导致 TextRM 初始化失败。

### 4.2 `fontlist.dat` 实测内容（与解析器逐字段对得上）

```

FONT_JAPANESE\t/usr/share/app/HeiseiKakuGothW5-SJ_wIcon.ltt\t0\t0\n
FONT_KOREAN\t\t/usr/share/app/MYingHeiC-KSX1001-SJ_wIcon.ltt\t0\t0\n
FONT_S_CHINESE\t/tmp/images/MYingHeiC-GB18030-SJ_wIcon.ltt\t\t0\t0\n
FONT_T_CHINESE\t/tmp/images/MYingHeiC-Big5-SJ_wIcon.ltt\t\t\t0\t0\n
FONT_ICONS\t\t/usr/share/app/Sony_DI_Icons.ttf\t\t\t\t0\t0\n
```
文件真实位置：`/share/app/fontlist.dat`（360 B，`nflasha15` 镜像内存在；全镜像中除该目录项外**没有任何代码字符串含 `fontlist`**——再次印证路径来自 Backup）。

### 4.3 注册时不校验文件是否存在

`create_node` 只写 name/path/id/flags，**不 stat 文件**。字体文件是 `TextRM_loadFont` 阶段由 `0x54E5B0` 才 `fopen` 的。
→ **这是"不需要副控制器"的根本原因**：注册只需要那张表；`.ltt` 只要在真正绘制前放进 `/tmp/images/` 即可。

### 4.4 一次性初始化 `0x54F3A0`

```
54f3a0 push {r4,r5,r6,r7,lr}
54f3a4 ldr r4,[..] ; add r4,pc        ; r4 = 0x13F6534（TextRM 互斥锁）
54f3ae blx pthread_mutex_init
54f3b4 blx pthread_mutex_lock
54f3b8 ldr r3,[..] ; add r3,pc        ; r3 = 0x13F6530（一次性标志）
54f3bc ldrb r5,[r3] ; cbz r5, first   ; 已初始化 → 直接返回 0
54f3cc strb #1,[r3]                   ; 置位
54f3ce bl 0x54E518                    ; head=0, count=0
54f3d2 bl 0x54D08C / 0x54E1FC / 0x54E434 / 0x54DF24 / 0x54D408 / 0x54D1AE   ; 6 个模块初始化
54f404 bl 0x54F1FC                    ; 建引擎：out 0x13F6524 / 0x13F652C / 0x13F6528，尺寸 0x100000
54f412 bl 0x5757E0 ; str r0,[0x13F6520]
54f42c bl 0x54E94C                    ; ★ 字体列表解析（本文件唯一调用点）
54f430 cmp r0,#0 ; movne r6,#-1       ; 解析失败 → 整体返回 -1
54f438 bl 0x54F368                    ; 读 Backup 0x810001（OSD 区域，u32，>2 归 0）
54f442 return r6
```
唯一调用者：`0x647AAC`（C++ 外壳的懒初始化函数）。该外壳 `0x647AB2` 处 `cbz r0` 判失败 →
写日志 `"TextRM_ErrNone == err <(0x40000000)>"`（`0xFB1CE2`）→ `0x641910` → 产品侧 abort 处理器。
**即：解析器返回非 0 会让 TextRM 初始化就 abort，而不是等到 loadFont。**

> 由此可反推运行时事实：既然实测崩溃点在 `TextRM_loadFont`（`0x647945`），说明 **初始化成功了 → 那次 `fopen` 是成功的 → 运行环境里 Backup `0x810000` 确实给出了一个能打开的路径**（或回退名恰好存在）。
> 这与"只注册成功 FONT_ICONS"的记录吻合：打开的那个文件只有一行/只有 ICONS。**这是本轮最值得马上验证的一条。**

### 4.5 另一条注册函数 `0x54EE50`（按路径注册，名字留空）

```c
long TextRM_registerFontByPath(const char* path,   // r0，必须非 NULL
                               u16         fontId, // r1
                               u32         flags,  // r2
                               u32*        outIdx) // r3
{
    lock(0x13F6534);
    *outIdx = 0;
    err = font_face_load(*0x13F6528 /*引擎*/, path, fontId, &descPtr);   // 0x54E5B0
    if (err) goto out;
    if (create_node(&node)) { err = -9999; goto out; }                   // 0x54EEA8
    *outIdx = node->index;
    desc = malloc(0x100); sprintf(desc, descPtr);                         // 0x5662C2
    set_desc (node, desc);                                                // +0x108
    set_path (node, path);                                                // +0x208
    set_id   (node, fontId);                                              // +0x308
    set_flags(node, flags);                                               // +0x30C
    refcount_inc(node);                                                   // 0x54EB2C
out:
    unlock(); return err;
}
```
**它不给 `node+8` 写名字** → 用 `find_by_name("FONT_S_CHINESE")` 永远找不到它。
→ 想让 `TextRM_loadFont` 命中，**必须**走"带名字"的那条：`set_name` 只有解析器（`0x54EA56`）会调用。这是决定性的结构事实。

### 6.1 `0x63E2DC` / `0x54E94C` / `0x54E7D4` 的直接调用点

## 七、`registerFontFaceFile`（0x63E2DC）实现全解

```asm
63e2dc push.w {r4,r5,r6,r7,r8,lr} / sub sp,#8 / add r7,sp,#8
63e2e4 mov  r8, r0            ; arg1: unsigned char
63e2e6 mov  r6, r1            ; arg2: char const*
63e2e8 mov  r5, r2            ; arg3: unsigned char
63e2ea bl   0x79EF88          ; r0 = getInstance()  ← 经 .bss 0x13FDFD8 的函数指针间接调用
63e2ee mov  r4, r0
63e2f0 cbnz r0, 0x63e30a
      ; 单例为空：log(level=0x10, fmt=?, file=?, line=0x13)（PLT 0x1047D8）→ return 0
63e30a bl   0x79F00C          ; r0 = *(instance + 0x30)      （0x79F00C = ldr r0,[r0,#0x30]; bx lr）
63e30e mov  r1, r8            ;   → 第 1 实参原样传
63e310 mov  r2, r6            ;   → 第 2 实参原样传
63e312 ldr  r3, [r0]          ; r3 = 子对象虚表
63e314 ldr  r4, [r3, #8]      ; r4 = vtable[0]（偏移 8 = 第一个虚函数）
63e316 mov  r3, r5            ;   → 第 3 实参原样传
63e318 blx  r4                ; 子对象->vtable`arg1, arg2, arg3`
63e31a..  epilogue
```

* **参数含义（按签名 `registerFontFaceFile(unsigned char, char const*, unsigned char)`）**：
  `(u8 id_or_lang, char const* path, u8 flag)` —— 三个参数**语义完全由虚函数实现决定**，本函数既不解释也不校验，只做透传。第三个参数只有 1 字节，与 `0x54EE50` 的 `flags`（整字）不同，故更可能是"语言/编码选择子"或布尔标志。
* **不写 `0x13F64FC`**（§6.3）。它触及的结构是「`getInstance()` 单例 + 偏移 0x30 的子对象 + 该子对象自己的虚表」——属于 `ux::core` 图形/文本引擎层，与 TextRM 的 C 链表是两套注册表。
* `getInstance()`（`0x79EF88`）读 `.bss 0x13FDFD8` 的函数指针后 `blx`，且 `0x79EF68` 有一个 setter（`str r0,[0x13FDFD8]`）。
  → 该单例是**运行期注入**的（注册/绑定模式）。**推测**：注入方是某个"引擎装配"初始化代码，静态解析不到；在同一库里另有 74 处调用 `0x79EF88`，说明它是引擎层的通用单例取用器。

## 八、谁在"按语言加载字体"（问题 3 的回答）

1. 字体**名字**不在代码里：`FONT_*` 只出现在两处数据——`/share/app/fontlist.dat`（注册表）与 `/share/app/lang_cmn.uxc`（语言资源）。
   `lang_cmn.uxc`（1048 B）的字符串池恰好只有 5 个名字，顺序固定：
   `FONT_UNIVERS, FONT_JAPANESE, FONT_KOREAN, FONT_S_CHINESE, FONT_T_CHINESE`
   → **语言 → 字体名的映射在 uxc 资源里**，由上层（`viewUnified2.so`/`libmpr.so` 里的 UI 框架）按当前语言取出名字再调用 TextRM 接口。
2. libObj 自身的两处 `TextRM_loadFont` 调用点：
   * `0x1EF77C`：`if (!*(0x13F3928)) { TextRM_loadFont("FONT_UNIVERS", &h); ... }` —— **硬编码的"默认字体懒加载一次"**（`0x13F3928` 是"已加载"标志）。这是全库里唯一硬编码的字体名，只有 UNIVERS。
   * `0x647940`：通用 `loadFontSlot(slot, name)`，名字由参数传入（即 §五 的 abort 点）。
3. `ux::core::TextLayout`（`registerFontFaceFile` 所在类）与 `ux::resmgr::ResourceManager::sys_setFontNameWithNamespace`（`0x5EA68D`）、`ux::core::TextRMLayoutEngine` 等同属 ux 引擎层；RTTI 名可在 `.rodata` 0xFB0BFC–0xFB1D12 看到（`TextRMSingleTextHandler` / `TextRMMultiTextHandler` / `TextRMLayoutEngine` 等）。
   **推测**：ux 层的"按语言选字体"最终会 `TextLayout::registerFontFaceFile(id, path, flag)` 注册到引擎侧表，而**绘制时用 `setFont(name)`/`setFont(id)`** 走 TextRM。也就是说：**引擎侧注册表与 TextRM 名字链表是并联的两套**，我们在 QEMU 里撞的是后者。

## 九、三种方案评估（按可行性排序）

### 方案 B′（**推荐**）：让一次性初始化的那次 `fopen` 成功并读到完整 `fontlist.dat`

依据：§4.1/4.4 —— 这是唯一会调用 `set_name` 的路径，也是唯一能让 `find_by_name("FONT_S_CHINESE")` 命中的路径。
三种等价实现，按"改动量"排序：

* **B1（零补丁，先试）**：UI 进程的 CWD 里放一个文件，**文件名就叫 `TEXTRM_FONT_LIST`**，内容 = `fontlist.dat` 原文。
  依据：`0x54E98C` 的回退 `fopen("TEXTRM_FONT_LIST","r")` 是**相对路径**，没有目录前缀。
  风险：CWD 不确定；且**只有走回退分支时才生效**（若 Backup `0x810000` 有数据且能打开，就不会走回退）。
  → 建议在 `/`、`/usr/share/app`、`/tmp`、`/share/app` 各放一份同名文件（成本极低）。
* **B2（最稳、改动最小、推荐落地）**：把 `.rodata 0xF85C34` 的 16 字节 `"TEXTRM_FONT_LIST"` **原地改字符串**（不动任何代码）：
  `"TEXTRM_FONT_LIST\0"` → `"/fontlist.dat\0\0\0"`（13 字节，剩余补 0；仍是 NUL 结尾、长度更短，安全）。
  然后 `fontlist.dat` 放到根文件系统 `/fontlist.dat`（initrd 或 usr 镜像，两种现有打包流程都支持）。
  优点：**只需 1 处 16 字节的字符串替换**，不涉及代码/栈/ABI；对 Backup 分支无影响（两个分支都会被走到 `0x54E98C` 之外——注意：Backup 分支若成功则 fopen 的是 Backup 里的路径，所以 B2 只在回退时生效，见下方 B3）。
* **B3（治本）**：直接改 Backup 数据区里 ID `0x810000` 的内容为 `"/usr/share/app/fontlist.dat"`（字符串，NUL 结尾）。
  依据：`0x54E966/0x54E97A/0x54E99A` 的 Backup 读取 + `fopen(buf,"r")`。
  优点：与真机行为完全一致，不用改 libObj；缺点：需要摸清 Backup 项格式（项目里已有 `Backup-state1.bin` 的修改经验和 `backup-property.json` 证据）。
  **建议先做一次诊断而不改**：在 `0x54E99A` 下断，读 `r5` 指向的字符串 → 立刻知道当前 emulator 实际打开的是哪个路径；若不等于 `/usr/share/app/fontlist.dat`，就说明该改 B3。

**共同前置**：`/tmp/images/MYingHeiC-GB18030-SJ_wIcon.ltt`（已从真机采集）必须在**绘制前**就位——因为 `TextRM_loadFont` 会 `fopen` 它。注册阶段不需要它。

### 方案 A（不推荐）：直接调 `registerFontFaceFile(id, path, flag)`

* **方向错误**：它不写 `0x13F64FC`（§6.3、§七），即使成功也不会让 `TextRM_loadFont` 命中 → 崩溃照旧。
* **也不可行**：`getInstance()` 经 `.bss` 函数指针（`0x13FDFD8`）间接跳转，静态拿不到实例；`0x63E2DC` 在全固件里**没有任何导入方**（§6.2），说明这条 API 在本代产品里就是"备用/未启用"。
* 唯一可能的用途：将来做 UI 移植（ASTRA/五代）时，若引擎侧渲染路径启用，才需要考虑它。

### 方案 C（不推荐作为第一步）：伪造副控制器"字体就绪"消息

* 事实：`libsencore.so` 里确实有 6 条 `/tmp/images/...` 路径（`Big5HKSCS`、`Big5`、`GB18030`、`GB2312`、`UniversOTS`、`Sony_DI_Icons.ttf`），但它**只依赖 libosal_uipc/libpro00/libInfraUsbCmn 等通信库，不 import `TextRM_*`，也不 import `ux::core::TextLayout`**（其 `.dynsym` 791 项中无相关符号）。
  → libsencore 的职责是"把文件落到 /tmp/images"，**它自己不触发注册**。
* 而且按 §4.3，注册根本不需要文件先到位 → **这条路线对"注册"是多余的**，只对"提供 .ltt 文件内容"有用，而文件我们已经有了。
* 结论：C 不能解决注册问题；若将来要复现完整链路才需要逆向它的分片报文（`resCode/Adrs/DataSize`，0x300 分片）。

### 10.2 用 5 个内部函数"手工注册"一个中文字体（无需任何文件）

若不想依赖文件系统/Backup，可用最小 shim（在 libObj 内就地调用，全部 Thumb 地址 +1 调用）：

```c
void register_chinese_font_inline(void)
{
    void* node = 0;
    pthread_mutex_lock(&g_textRmMutex);            // 0x13F6534
    if (create_node(&node) == 0) {                  // 0x54E7D5 → r0=&node
        set_name (node, "FONT_S_CHINESE");          // 0x54E8EF

```

* 5 个 setter 都返回 `0` 成功 / `-6` 参数空。
* **必须持锁**：`TextRM_loadFont`/`0x54EE50`/解析器都在 `0x13F6534` 锁内操作链表；不持锁有竞态（绘制线程正在遍历）。
* **必须早于第一次绘制**：`loadFont` 会缓存/引用计数，晚注册只会让已失败的 `loadFont` 已 abort。

## 十一、明确标注为推测 / 未确定的部分

1. **【推测】** `registerFontFaceFile` 三个参数的确切语义 `(u8, char*, u8)`：本函数只透传，实现在虚表里；按同类 API（`0x54EE50` 的 `path/id/flags`）推断第 2 个参数是路径、第 1 个很可能是 id 或语言选择子、第 3 个是 flag。**未证实**。
2. **【未确定】** `getInstance()`（`0x79EF88`）实际指向哪个函数：`0x13FDFD8` 是运行期写入的函数指针，静态无写入者常量（setter `0x79EF68` 的调用者也没找到）。因此 `*(inst+0x30)` 的类型/虚表内容**无法静态确定**。
3. **【未确定】** `0x54E5B0` 的 4 个扩展名候选在 `.rodata` 里是 `.a3a/.a3b/.a3c/.a3d`（0xF85B3E/43/48/4D，逐字节确认），**与 `fontlist.dat` 的 `.ltt`/`.ttf` 不符** → `.ltt` 会走 `0x571D0C` 的另一条装载路径（推测是交给 `ux::resrc`/MappedFile 抽象，字符串里有 `MappedFile: Cannot open file: %s`）。这条分支本轮未展开。
4. **【待运行时验证】** 当前 emulator 里 Backup ID `0x810000` 是否真有数据、那条路径是什么。建议的诊断断点：`0x54E99A`（Backup 路径分支，`r5` = 路径串）、`0x54E98C`（回退分支）、`0x54EA46`（建节点，每行一次）。这三点能一次性判定"走哪条路 / 注册了几个"。
5. **【与既有记录的差异】** 文档 68 记录运行期 `[0x13F64FC] = 0x000557B0`（非 NULL）。若按 §4.1，`fopen` 失败会返回 -9999 → 初始化失败 → 在 `0x647AB2` 就 abort，与"崩在 loadFont"矛盾。
   因此**更可能**：该次 `fopen` 成功、确实建了若干节点（0x557B0 很像低地址堆指针），只是列表里没有 `FONT_S_CHINESE` 那一行。**建议以 11.4 的断点复核，而不是沿用"链表非空"的旧结论。**

## 十三、给下一步的三条最省事动作

1. **一次断点定性**：在 `0x54E99A` 读 `r5` 的字符串、在 `0x54EA46` 数命中次数 —— 立即知道"当前打开的是哪个文件、注册了几条"，不用猜。
