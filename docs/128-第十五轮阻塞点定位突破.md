# 128 · 第十五轮：阻塞点静态定位取得实质突破

> 时间：2026-11-22。本轮为纯离线 QEMU 分析（未碰相机）。

## 一、重大修正：之前对 `0x54EF74` 的判断是错的

用 4 点并行探针（`MULTI`）实测，**全部命中**：

```
[MULTI] P_54EF90 #1   ← blx r3（vtable[0]）之后
[MULTI] Q_54EF96 #1   ← blx 0x925FB0 之后
[MULTI] R_54EFA6 #1   ← blx 0x9246B8 之后
[MULTI] S_54F678 #1   ← bl 0x54EF74 整个返回之后
```

**结论：`0x54EF74` 从头到尾正常返回**，之前的"台阶探针不命中"是探针自身缺陷（每次命中都重新 `dladdr` 太慢，错过后续点）。

## 二、静态分析的重要成果：vtable 与类名

### 2.1 对象的 vtable 已完整解出

`0x54D154` 构造对象并写入 vtable：

```
r4_base = 0x54D164 + 0x0322DA62 = 0x0377ABC8  （正好是 .got 起点）
slot    = r4_base + 0x5E9F0 = 0x037D95B8
slot 值 = 0x0353C510
vtable  = 0x0353C510 + 8 = 0x0353C518      （位于 .data.rel.ro）
```

### 2.2 vtable[0] 是空函数（关键）

```
vtable[0] = 0x0054D05D  →  实际入口 0x54D05C
0x54D05C:  push {r7, lr}
0x54D05E:  add  r7, sp, #0
0x54D060:  pop  {r7, pc}      ← 立即返回，no-op
```

**这解释了为什么 `P_54EF90` 能命中**：那个虚调用根本不会阻塞。

### 2.3 RTTI 揭示对象身份

vtable 附近的 `.data.rel.ro` 结构含标准 C++ RTTI：

| 位置 | 内容 |
|---|---|
| vt[6] | reloc → `_ZTVN10__cxxabiv120__si_class_type_infoE`（单继承） |
| vt[7] | `0x02CEB040` = `"N8debug_if8debug_ifE"` |
| vt[9] | reloc → `_ZTVN10__cxxabiv117__class_type_infoE`（基类信息） |
| vt[10] | `0x02CEB055` = `"10i_debug_if"` |

同区域还有两个接口名：

- `"21i_touch_event_handler"`（`0x02CEB062`）
- `"30i_display_update_event_handler"`（`0x02CEB07A`）

**含义**：这个对象是 `debug_if` 的实现，而 `0x54F664` 这个函数在涉及 **触摸事件处理器** 和 **显示更新事件处理器** 的初始化。这正好解释了为什么 UI 卡在这里会导致 `ch53` 不编程、`draw=0`。

## 三、ARM veneer 解析规则（已修正并验证）

gen5 appFw 里的 `0x92xxxx` 是 **ARM 状态 veneer**：

```asm
V+0:  e59fc004   ldr ip, [pc, #4]     ; ip = *(u32*)(V+12)
V+4:  e08fc00c   add ip, pc, ip       ; ip = (V+4+8) + ip
V+8:  e12fff1c   bx  ip
V+12: <word>
```

**正确公式：`target = V + 12 + word`**（之前误用 `V+8+word`，导致目标偏 4 字节、反汇编全乱）。

用正确公式重算后，`0x54EF74` 的所有调用都落到 `.text` 内合法函数（以 `push {r7,lr}` 开头）。

## 四、当前阻塞定位状态

已验证的调用顺序（`0x54F664` 内，前段）：

```
0x54F664
 ├ 0x54F674  bl 0x54EF74        ← 完整返回（S 点命中）
 ├ 0x54F68A  bl 0x54833C        ← 已知很短、正常返回
 ├ 0x54F694  blx 0x925FB0  → 0x1C7E69D
 ├ 0x54F6A6  blx 0x9256A8  → 0x1C7EB79
 ├ 0x54F6B0  blx 0x9246B8  → 0x1C7E6AD
 ├ 0x54F6BE  bl 0x52A60C
 ├ 0x54F6CE  blx 0x9240F8  → 0x1C1B797
 ├ 0x54F6E2  bl 0x54E8F0
 ├ 0x54F70A  bl 0x52A60C
 ├ 0x54F712  bl 0x54F004
 ├ 0x54F716  bl 0x712100
 ├ 0x54F71A  bl 0x60E2F4
 └ ...（后续还有约 30 个调用）
```

**新问题**：在 `0x54F690` 之后布设探针会导致 `sig=11` 崩溃。两种可能：
1. 我选的探针地址落在 32-bit Thumb 指令中间（破坏了指令流）；
2. 该区域确实敏感。

需要先用 capstone 确认 `0x54F690`、`0x54F6A0`、`0x54F6B4`、`0x54F716` 是否是**合法指令边界**。
