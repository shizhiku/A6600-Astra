## 二、未达成项的唯一缺口

**`Application_Start` → `0x54F664` 阻塞**，这是通往 M-E 的最后一道门。

本轮已把阻塞范围收窄到确定的调用序列：

```
Application_Start (0x54D580)
  └→ 0x54D2B0                       [命中]
       └→ 0x54F664                  [进入后不返回]
            ├→ 0x54EF74              [命中]
            │    └→ blx r3           ← 对象 vtable[0] 虚调用（首要嫌疑）
            ├→ 0x54833C              [命中，且函数很短、正常返回]
            └→ 0x925FB0 …            [未命中]
```

### 本轮新增的静态结论（可直接用于下一轮）

1. **`0x92xxxx` 不是 PLT 桩，而是 appFw 内部 thunk**。原始字节 `04 c0 9f e5 / 0c c0 8f e0 / 1c ff 2f e1 / <word>` 解析后，`0x925FB0` 等 12 个调用点全部跳转到 `.text` 内部（如 `0x1C7E699`、`0x1D5A3D5`），**不是导入符号**。这意味着阻塞发生在 appFw 自己的逻辑里，而不是某个缺失的外部库调用。
2. `0x54833C` 只有 12 条指令（调 `0x5482E4`、`0x9245CC` 后返回），**排除**。
3. `0x54EF74` 的第一条动作是**间接虚调用** `ldr r0,[r0,#0x10]; ldr r3,[r0]; ldr r3,[r3]; blx r3` —— 取对象 `+0x10` 处的管理器，调其 vtable[0]。这是最可能的阻塞点（虚函数可能内部等锁/等消息）。
