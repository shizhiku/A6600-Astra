# 32 · noinit 路径的非法指令排查（未完成）

本轮为离线分析。无设备写入。

## 一、故障位置确认

noinit 路径下的 `Illeagle Instruction`（trap 6）地址在两次运行中不同：

| 运行 | 故障地址 |
|---|---|
| `cmdline-20261120T192924Z-42273` | `0x04253796` |
| `observe-20261120T193306Z-42511` | `0x0427C796` |

两者 **低 12 位相同**（均为 `0x796`），差值 `0x29000` 恰为库基址随机化偏移 → **ASLR 生效，故障恒在 libc 的 VA `0x15796`**。

这解释了对固定地址下断点抓不到现场（第一次尝试超时）。

## 二、静态解码结果

按程序头把 VA `0x15796` 换算为文件偏移 `0x15796`（该库首个 LOAD 段 `vaddr=0`）：

```
015790  80b5      push {r7, lr}
015792  6746      mov  r7, ip
015794  00df      svc  #0
015796  80bd      pop  {r7, pc}   ← 故障点
```

即这是 **glibc 的 Thumb 系统调用桩**：把 syscall 号从 `ip`(r12) 载入 r7，执行 `svc`，随后返回。

`: 0x15796` 处的 `pop {r7,pc}` 在 **Thumb 状态下完全合法**，因此报“未定义指令”只有一种解释：**执行时 CPU 处于 ARM 状态**，把 `80 bd af f3` 当作 ARM 指令解码而失败。

## 三、异常向量抓取（未得出结论）

在未定义指令向量 `0xFFFF0004` 设断并读取 LR：

```
ENTRY routine_entry_observed LR=0x4104048
```

- 若当时为 ARM 状态，故障指令地址 = LR − 4 = `0x04104044`；
- 若为 Thumb，则为 LR − 2 = `0x04104046`。

该值与前两次的 `0x04253796` 不在同一位置，说明这条异常并非那次 SIGILL（可能是启动早期另一次未定义指令），本次抓取**没有定位到目标事件**。

## 四、目前的判断

故障形态是“**进入 Thumb 例程时状态位丢失**”，属于典型的函数指针/调用状态错误。它只在跳过 av-cam 初始化的诊断镜像下出现，因此**高度可能是跳过初始化造成的次生问题**，而不是独立的模拟器缺陷。

## 五、结论

- noinit 证明了 UI 栈可运行（上一轮的重要结论不变）；
- 但 noinit 不是可用方案，它引入状态不匹配；
- 真正的解法仍是让 av-cam 初始化正常完成。

## 六、下一步（择一）

1. **更小侵入**：不跳过整个初始化，只让 liro 的那次判据满足一次，观察 av-cam 其余初始化能否继续并让 UI 起来；
2. **补 ch0 对端**：继续逆向 SIO ch0 协议（需要对其帧语义有更多证据）；
3. **ASLR 关闭**：给客户机 cmdline 加 `norandmaps` 或早期写 `randomize_va_space=0`，以便对 libc 故障点稳定下断、拿到完整寄存器与调用栈。

第 3 条是纯观测手段，成本最低，建议先做。
