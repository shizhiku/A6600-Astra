## 重试判据（静态解析）

例程 `0x638529d8` 的逻辑为：

```
r0 = [obj+3]                 ; 某个对象的状态字节
r5 = [global_byte]           ; 全局字节
r5 = (r0 ^ (r5 << 4)) & 0x7f
if ([state+0x3b] & 2) -> 调用 0x63d2ab3e
if (r5 == 0) -> 清零计数并走 0x638524d4
if ([state+1] == 1) -> 清零计数并走 0x638524d4
否则 -> 计数加一；超过 0x1d 时写入状态 7 并发布消息 0x3a
```

## 已验证的观测

1. **`[state+1]` 在运行期从未被写入。** 对该字节设硬件写监视，全程只捕获到一次写入：来自设置备份的批量拷贝（源 `0x62ee7f54`，即 Backup.bin 偏移 `0x67f54`，属性 `0x00170000`）。之后到致命断点前没有任何写入。
2. 该结构当时内容为 `00 00 03 02 01 …`：`[state+1]=0`、`[state+2]=3`。因此“`[state+1]==1` 则为就绪”这一条在模拟中始终不成立。
3. 连续 40 次命中计数点，`r2` 每次都是 `0x1`，说明清零路径确实在反复执行，计数不会一路累加到 30。此前“连续重试 30 次”的表述已撤回。

## 未解决的不一致（已解决）

此前静态解析出的计数器地址 `0x6385e3a8` 与运行时 `0x644ae3aa` 相差 `0xC90002`。现已定位为**两个方法错误**，并已修正：

1. **寄存器宽度错误。** 本机 QEMU 的 GDB `g` 包对 32 位 ARM 使用 **每寄存器 4 字节**，此前按 8 字节解析，导致寄存器整体错位、数值不可用。修正后 `r3=0x644ae3aa`、`r4=0x6431f3c0`、`r6=0x64437e98` 自洽。
2. **PC 相对寻址的取值错误。** Thumb 16 位编码 `ADD Rd, PC`（如 `0x63852a2a` 的 `7b44`）使用的 PC 为「指令地址 + 4」，**不做 4 字节对齐**。此前按对齐计算，结果差 2 字节。同时字面量必须按 **4 字节** 读取（`ldr`），此前只读了 2 字节。

修正后的验算：`0x63852a2a + 4 = 0x63852a2e`，其 4 字节字面量为 `0x00C5B97C`，相加得 **`0x644AE3AA`**，与运行时实测一致。

## 运行代码身份校验

在模拟器中断点处直接读取运行内存，与本地文件同址字节比对：

```
运行: 1a70 fff757fd 11e0 134b 7b44 1a78 0132 d2b2 1a70 1d2a 05d9
文件: 1a70 fff757fd 11e0 134b 7b44 1a78 0132 d2b2 1a70 1d2a 05d9
```

完全一致，说明模拟执行的确是我们分析的这份原厂 av-cam，不存在镜像替换。
