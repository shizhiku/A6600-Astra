> 本轮两条线（运行时对照 + 静态逆向）都拿到决定性结果，修正了此前多个判断。

## 一、黑屏真因：不是预加载，是**缺少副控制器帧回放**

### 对照实验（同一时段、同一抓帧点 vsync 1200/1800/2400/3000）

| 组 | 配置 | 预加载 | 副控制器帧 | 四帧结果 |
|---|---|---|---|---|
| C0 | `boot_with_real_tmp.sh` | 无 | **无** | **全黑**（nonzero=0） |
| C1 | `boot_inject.sh` + `libempty.so`（完全空 DSO） | 有（空） | **无** | **全黑** |
| C2 | `boot_keypress.sh`（BTN=0, ADC_SEQ=） | 无 | **有** | **四帧全亮**（76800/76800/76800/76800） |

截图：`fbc2_3.png` = 「运行于NTSC。」完整界面。

### 结论

- **黑屏与 `ld.so.preload` 无关**（空 DSO 也黑，无预加载也黑）
- **真正的门控是 `-M sony-a6400,rear-controls=on,submicro-frames=<384B 文件>`** —— 没有副控制器帧回放，UI 不绘制
- 这同时解释了此前的"画面状态不一致"：**带 submicro 参数的运行会画，不带的会黑**，而不是随机

### 更正

| 原说法 | 更正 |
|---|---|
| 预加载破坏渲染 | ❌ 错误；黑屏由缺少 submicro 帧导致 |
| 空 DSO 对照必要 | ✅ 仍必要，且正是它证明了这一点 |

> 附带经验：以后所有 UI 相关实验**必须**带 `rear-controls=on,submicro-frames=...`，否则基线就是黑屏。

## 二、按键派发链路：静态逆向的确定性结论

来源：`92-InfraInput键映射静态分析.md`（协作者完成，已复核关键地址）

### 2.1 `key_code` 和 `event_code` 是同一个值（0x1AC）

- `_InfraInputEvent`（24 B）字段：`+0x00 event_code`、`+0x04/+0x06 tp_x/tp_y`、`+0x08 status`、`+0x0c prev_status`、`+0x10 ex_info`、`+0x14 repeat`
- **该结构里没有 key_code 字段**；所谓"物理键码"是上一级 `InputPhyKeyInternal+0x00`
- `InfraInput::MainThread`（`0x862430`）在 `0x862668/0x862674` 执行 `event.event_code = phy.key_code`
- `InputService` 直接用它作 UI 事件 ID：`0x3D2D84 ldr r1,[ev]` → `0x3D2D8E blx` → `createEvent(unsigned long, unsigned char)`
- `.data@0x13F0928` 有 37 项按键名表，`0x1AC = "KEY_TACT_MENU"`（串在 `0x1014593`）
- 全文件穷举 `ac 01 00 00`（42 处）按 8/12/16 步长扫描，**不存在** `{key_code,event_code}` 静态映射表

**→ 所以：如果 MENU 真的派发了，`createEvent` 一定会收到 `0x1AC`。实测没收到，说明它在中途被丢弃。**

### 2.2 三条派发条件（丢弃点）

`MainThread` 要求：

1. **`config_pos(msg+0x10) >= 0`** —— 该键必须存在于运行时 key config 表，否则打印 `unknown key`(`0x100DB7C`) 丢弃
2. **`this[+0x9c]` 链表中必须已有 `entry[+0x00]==0x1AC` 的 key_list 项**，否则整条键**静默丢弃** ← **最可能的原因**
3. 去重：`(cbflags&2)==0 && (internal_flag&5)==0` 时按 `(sub_key_code,status)` 比较，相同则打印 `same event`(`0x1013021`) 丢弃

另有 `internal_flag&1` 的 16 字节比对（`do not`）、`event inh`、`no group` 等分支。

### 2.3 键表由 UIPC 运行时下发，没有内置默认表

- `SendEventInitData`(`0x8610FC`) 只打印 `send ini_eve` 并回灌内部缓存，**不读文件/Flash**
- `key_conf` 系列（`0x8637C0/0x86384C/0x8638AC/0x863960`）也是运行时建链
- 真正的 `key_code→event_code` 载体是 12 字节/项的 `InfraInputKeyList`
- 唯一"外部"入口：`RecvThread`(`0x862D60`) 的 **`INFRA_INPUT_UIPC_SETEVENTKEYLIST`**
  - 处理器 `0x85E5C4` 在 `0x85E840 add.w r2,r4,#0x10` 把**报文缓冲 +0x10** 当表传给 `SetEventKeyList`(`0x861AA8`，落成 0x44B/项内部表)

**→ 结论：我们的模拟器没有下发这份 key list，`this[+0x9c]` 链表为空 → 所有物理按键被静默丢弃。这就是"ADC 有值、UI 无反应"的根因。**

## 四、下一步（有明确目标）

### 优先级 1：确认 key list 是否为空

- 断点 `0x862668`（`event.event_code = phy.key_code` 之后），看是否被执行到 → 若从未执行，说明在更早的分支就被丢弃
- 或断点 `0x85E846` 读 `r2`，看 `SetEventKeyList` 是否被调用、表内容是什么

### 优先级 2：补上 key list 下发

两条路：

| 方案 | 做法 |
|---|---|
| A · 让 submicro 帧携带该消息 | 修改回放帧，加入 `INFRA_INPUT_UIPC_SETEVENTKEYLIST` 报文（需要报文格式） |
| B · 用户态注入 | 写一个小工具，用 `osal_snd_msg` 直接向 InfraInput 的 RecvThread 队列投递该报文 |

### 优先级 3：2×2 重复验证

MENU 按住 / 不按 × 2 次，固定抓帧点，确认"NTSC 提示页 → 拍摄 OSD"的转变是否由 MENU 引起。

## 五、运行时段验证（本轮新增，基址已用 createEvent 交叉验证）

| 钩子 | 运行时地址 | 结果 | 含义 |
|---|---|---:|---|
| `InputService::createEvent`（基址校验） | `0x05BB2AEA` | **命中 6+** | 基址 `0x057E3000` 正确，零命中结论可信 |
| `InfraInput::MainThread` 派发点（`event.event_code = phy.key_code`） | `0x06045668` | **0 命中** | 物理键根本没走到派发层 |
| `INFRA_INPUT_UIPC_SETEVENTKEYLIST` 处理器 | `0x060435C4` | **0 命中** | **运行时键表从未下发** |
| `input.ko` 的 `osal_snd_msg` 调用点 | `0x5f07cae0` | **仅 1 次**（初始化） | 驱动没有按键消息发送行为 |

### 结论：链路两端都是"暗"的

```
副控制器 UIPC  →  input.ko  →  InfraInput.RecvThread  →  MainThread  →  InputService
     ?              仅初始化发过 1 条        ?                0 命中         活跃（但无 0x1AC）
```

- **上游**：`input.ko` 在整个运行中只调用过一次 `osal_snd_msg`（初始化时），没有按键事件发送
- **下游**：`InfraInput` 从未收到 `SETEVENTKEYLIST`，key list 为空；`MainThread` 派发点从未执行
- 因此，"ADC 注入有值、UI 无反应"的完整解释是：**两端都缺数据通路，不是单点故障**

2. 钩驱动接收侧（UIPC 帧处理），确认驱动是否收到 ADC/按键数据
3. 取得 `INFRA_INPUT_UIPC_SETEVENTKEYLIST` 的**报文格式**后自行投递（用户态 `osal_snd_msg` 或改 submicro 帧）
