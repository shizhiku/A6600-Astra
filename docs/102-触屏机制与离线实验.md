# 102 · 触屏机制与离线实验（a6600 / 四代 UI）

日期：2026-11-22。本轮只做离线镜像与 QEMU，无设备写入。

## 一、结论：a6600 支持全域触屏，缺的是“能力开关 + 事件投递”

参考项目 [nolan2628/ZVE10-Astra-Public](https://github.com/nolan2628/ZVE10-Astra-Public) 实现了全域触屏（拍摄界面和设置菜单都能点）。它的做法不是模拟触摸控制器，而是两层：

1. **改 UI 能力判定**（`viewUnified2.so`）：`isTouchToggleSupported` 返回 1、`isTouchPanelPadSupported` 返回 4、`PAS_MenuSelectMode::setTouchable` / `PAS_BarCtrlDial::setTouchable` 的参数从 2 改成 0；
2. **在客户机内投递鼠标事件**：`ux::wgtsys::WidgetSystem::postMouseMove / postMousePress / postMouseRelease`，再驱动 `processEvent / updateFrame / notifyDraw`。项目里由定制 `appFwBoot_g4host.c` 的 UART 线程读 `TOUCH DOWN/MOVE/UP/TAP x y` 后投递。

## 二、a6600 四代库里的同一套符号（本轮实测）

`/lib/viewUnified2.so`（11,553,828 B）：

| 符号 | VA | 原始行为 |
|---|---:|---|
| `CmnViewFeatureManager::isTouchToggleSupported()` | 0x2FBF90 | 仅当内部 getter 返回 1 时为真 |
| `CmnViewFeatureManager::isTouchPanelPadSupported()` | 0x2FBFA6 | 仅当内部 getter 返回 4 时为真 |
| `PAS_MenuSelectMode::setTouchable(bool)` | 0x56F660 | false 时向 UI 传 2 |
| `PAS_BarCtrlDial::setTouchable(bool)` | 0x5BA00C | false 时向 UI 传 2 |

`/lib/libObj.so`（20,889,004 B）：

| 符号 | VA |
|---|---:|
| `ux::wgtsys::WidgetSystem::sys_getInstance()` | 0x5F1299 |
| `postMouseMove(u8,s16,s16,MsecTime const&)` | 0x5F2641 |
| `postMousePress(u8,u8,MsecTime const&)` | 0x5F26D1 |
| `postMouseRelease(u8,u8,MsecTime const&)` | 0x5F2739 |

这与参考项目使用的符号完全一致，说明 a6600 的四代 UI 本身具备全域触屏能力，只是能力判定被关掉了。

## 三、离线实验（第一版）

产物：

- `03-证据/静态分析/touch/viewUnified2_touch.so`：四处能力开关补丁（0x2FBF90→`movs r0,#1; bx lr`，0x2FBFA6→`movs r0,#4; bx lr`，两处 `movs r1,#2`→`#0`）；
- `04-产物/98_touch_preload.c` → `libtouchinject.so`：在客户机内 `dlopen("libObj.so")`，解析上面四个 WidgetSystem 符号，等 `sys_getInstance()` 非空后依次点击 (320,240)、(40,40) 等；
- 镜像副本：`/root/astra/97/touchtest/usr-touchui.img`（仅替换 viewUnified2）。

运行结果（`touch-ui-20261121T185737Z-2387-1`）：

- `[TOUCHINJ] WidgetSystem symbols found, waiting for instance` → `instance ready, tapping`；
- 第一次点击 `(320,240)` 被接受并返回；
- 第二次点击前线程停住（4 秒后没有出现 tap 1 日志），没有异常、没有崩溃；
- 画面仍停在“运行于NTSC。”提示（这次 ENTER 注入没有走到确认路径，属于时序问题）。

这说明“能力开关 + WidgetSystem 投递”方向可行，但直接从任意线程调用 `postMouse*` 会卡住。参考项目是在自己的渲染线程里调用，并每帧驱动 `processEvent/updateFrame/notifyDraw`；下一步应把投递放到 UI 事件线程，或像项目那样接管一帧循环。

## 四、下一步

1. **把投递移到 UI 线程**：用 `WidgetSystem` 的帧回调或事件线程执行 `postMouse*`，避免跨线程锁死；
2. **驱动帧管线**：必要时每帧调用 `updateCurTime/processEvent/updateFrame/notifyDraw`，与参考项目一致；
3. **先过 NTSC 提示**：触摸测试前先用 ENTER 注入确认，再把点击坐标映射到菜单；
4. **接入网页**：网页点击 → 客户机内投递（参考项目用 UART `TOUCH ...` 命令，我们的方案可以用串口命令或共享文件）；
5. **五代 UI**：参考项目对五代 `libOb5` 用的是同一套 `ux::wgtsys::WidgetSystem` 符号，所以五代 UI 一旦能正常启动，触屏投递可以复用同一套接口。

## 五、第二轮：不提前 dlopen 的文件通道注入

第一版的问题是 preload 在 UI 尚未加载 libObj 时就 `dlopen("libObj.so")`，可能侧载了第二份 libObj，导致 UI 启动异常、第二次点击卡住。

第二版改为：

- **不 dlopen**，用 `dlsym(RTLD_DEFAULT, …)` 等 UI 自己把 libObj 载入全局作用域后再解析符号；
- 新增 `/tmp/touchcmd` 文件通道：宿主通过客户机 shell 原子写入 `x y kind`（kind 0=tap、1=down、2=move、3=up），preload 轮询、消费后删除文件；
- 去掉 `sscanf`/`fstat`（会引入 GLIBC_2.38/2.34 版本依赖），改手写整数解析，保证 GLIBC_2.4-only。

结果：`[TOUCHINJ] WidgetSystem ready; watching /tmp/touchcmd`，随后 **3 次点击都成功投递**（`apply x=40 y=40 kind=0`），无异常、无崩溃。说明“客户机内投递 + 宿主任意时刻下发点击”的通道已经打通。

## 六、仍未解决：打开触摸后 UI 停在 NTSC 提示

同一镜像（仅打能力开关补丁）在这轮运行中画面一直停在“运行于NTSC。”，ENTER 注入没有把它推过去；点击被投递但画面无变化。可能原因：

1. 能力开关打开后，UI 期望存在对应的触摸面板/事件源（参考项目还有 TP raw 回调钩子），而我们只投递了 WidgetSystem 鼠标事件；
2. `isTouchPanelPadSupported` 返回 4 在我们这版 UI 里可能代表“触摸板类型 4”，进入等待面板初始化的状态；
3. 该轮镜像里还带着早期的 `infra_tp_key_emulation.txt`，可能与 ENTER 处理冲突。

已另建干净镜像 `usr-touchui-clean.img`（只替换 viewUnified2，不含额外文件），下一步先在干净镜像上验证 ENTER 能否正常通过 NTSC，再做单点 tap。

## 七、边界

- 能力补丁与 preload 都只用于诊断镜像，不是最终方案；真机刷写仍需单独授权。
- 本轮没有产生“触摸可操作”的最终演示，只验证了符号、补丁位置和第一次事件被接受。
