### 3.2 97 报告与任务书表述核对

- 97 报告建议替换的“153 行”表述，其核心已被 **96 v3（CTX-11）第 14 行**采纳：“`part_image.sum` 不匹配可能在分区写入后才被读回校验发现；不得视为安全的‘写前拒绝’。” 因此本报告不再要求改任务书。
- 96 v3 第 163 行“已知障碍”仍写“updater 会拒绝”；按 F1-8/9，应读作“**预计不能成功完成更新，且拒绝可能发生在写入之后**”，不能读作“安全拒绝”。
- 96 v3 第 165 行“在 F1/F2/F4 有结论前不做真机刷写”仍有效；F2/F4 至今未按“可接受+可恢复”闭合。

### 3.3 F1 结论

**F1 的 CRC 部分闭合**：算法、覆盖范围、原值/修改值、可重算性均可复现。**但 F1 原问题中“该文件是否被签名”未闭合**，归入 F2；且“CRC 能重算”绝不等于“updater 接受”。

### 4.2 关键未决问题

1. **256 B trailer 的身份**：是否签名？签名覆盖 FDAT 明文、加密块流还是仅头部？验证发生在 updater 模式（uPD/引导链）还是运行中的 `im.elf→libIMDB→libupdaterufp→crypter` 链？现有材料无法回答。
2. **updater 的接受判定点**：`CheckGuardResult`/`ModelFile`/`VersionFile`/`RegionFile` 类存在，但没有任何真机响应、串口日志或 instrumented 运行；无法判断拒绝发生在传输前、写入前还是写入后。
3. **重封装脚本的认证保真度**：`02-脚本/build_full_image.py` 只替换 `/usr` 成员、复制旧 IV+256 B、重算 fdat 头 CRC 与 DEND CRC（97 报告已核）；**不产生任何新认证材料**；“打包成功”不能推导“认证成功”（CTX-06 已明确“DAT 解密回读成功只证明容器层能够解析”）。

### 4.3 两个外部结论的冲突（必须显式登记）

| 来源 | 陈述 | 等级 | 对 F2 的影响 |
|---|---|---|---|
| PMCA README（`_public_research/pmca-src/Sony-PMCA-RE-master/README.md`，CTX-07，5,548 B，SHA256 `779f36d8…`）第 49 行 | “Devices based on the CXD90045 and CXD90057 architectures are not compatible, since their firmware is cryptographically signed.”（指其自定义 updater 固件模式） | E3 | 暗示 updater 模式对**自定义固件**存在签名级拒绝；若成立，改包即使 CRC 全对也可能被拒 |
| 本工作区 `01-文档/01-方案总览.md`（CTX-04）§2.2 与 `01-文档/02-已验证事实.md`（CTX-02）§9 | 相机端更新链“只验 CRC32，无 RSA”（转述 anlock6600 全链路反汇编 + CST 研究） | E3（二手转述，未在工作区复现） | 若成立，F2 风险可缩到 guard/型号/版本与 256 B trailer；但**与上条冲突未解释** |

**处理原则**：在两条外部结论被独立证据协调之前，**任何一个都不能作为 F2 闭合依据**。可能的调和方向（均未证）：PMCA 的“签名”约束的是**自定义 updater body/固件**，而 anlock6600 的“只验 CRC32”描述的是**运行中系统的 `/usr` 内容更新链**；两者作用对象不同。该假设需要在 §10 的证据中验证。

### 4.4 F2 结论

**F2 未闭合。** 已证实的是“容器可读、可重封装、内部 CRC 可复算”；未证实的是“相机/updater 是否接受、依据什么接受、拒绝发生在何处”。因此：
- 不能回答 96 任务书 F 的验收问题“改的镜像 updater 收不收”；
- 不能把 `129576f8` 的 CRC 不匹配简单表述为“会被安全拒绝”；
- 在 F2 闭合前，**不得**以“最多就是被拒”为前提做任何真机写入。

### 5.4 新发现的接口缺口：M1 的 300 MiB 与 sum size 字段

- `part_image.sum` 对 `dev/nflasha15` 的记录为 `0,520fff36,0cd88800,...`：CRC=`520fff36`，**size=`0x0CD88800`=215,517,184**（FL-08）。
- M1 候选镜像是 **314,572,800**（300 MiB，见 F3-14/F3-15 的 manifest）。
- 因此 M1 若走官方 updater：
  1. CRC 要改成 300 MiB 镜像的 CRC；
  2. **size 字段也要改**；
  3. 但 `uc_crc32sum.elf -s -c` 的 `size` 语义、是否核对设备/分区容量、是否只读、超界如何报错，**没有机器码级证据**（`97_flash_updaterimg_bin_uc_crc32sum.elf.disasm.txt` 仅 1 B 空文件，FL-24 只有字节与字符串；32 个 native 自动反汇编文件中有 26 个为 1 B 空文件）。
- 这是 F1（重算）与 F3（几何）/F2（接受性）之间的**新增未闭合点**：即使 CRC 全对，size 字段变化本身也可能触发拒绝或未定义行为。

### 5.5 F3 结论

- **几何与“USER 模式不重分区”已闭合**；这否定了 97 之前的“扩 ext2 必须扩 SDM”的担心。
- **M1 的 300 MiB 镜像与清单 size 字段不一致**，是新的、真机前必须解掉的接口问题。
- **M2 的 SDM 迁移仅 QEMU**；真机不可行（通道未取得），且属于看门狗恢复通道覆盖范围之外（§6.4）。
- 因此 F3 只能支持“**M1 是不改分区表的正确方向**”，不能支持“M1 真机可写”。

**对既有结论的修正**：`01-文档/04-风险与安全边界.md`（CTX-03）§1 曾判断“改坏 `/usr` 后 USB 服务通道可能一起消失，a6600 没有验证过的救砖路径”。按所有者一手经验，该判断对“**仅 `/usr`-only 失败**”应修正为“存在看门狗→USB 兜底通道，但细节未固化”；对启动链/SDM/bootloader 仍成立。“绝对无恢复手段”的表述应撤回（97 报告已开始撤回）。同时要注意：看门狗强制进入的 USB 模式**不一定**是原 `im.elf` 建立的 service 模式，二者是不同通道，其切换机制尚未离线证实。

**必须补齐的细节（否则 O-1 只能作为“存在性”证据，不能作为可执行恢复预案）**：

1. 触发场景：固件挂起的具体类型（`/usr` 挂载失败？`im.elf` 卡死？启动早/晚期？），与“只改 `/usr`”的因果是否来自多次事件统计。
2. 恢复现象：复位后主机看到的是哪种 USB 模式/设备（VID:PID、是否官方 updater 模式、是否海量存储），屏幕是否有提示。
3. 恢复工具：主机侧具体工具（官方 `Update_ILCE6600V110.exe`？PMCA？其它），版本，操作步骤。
4. 恢复结果：是否成功回到可开机状态、恢复的是哪一版固件、失败/重试次数、是否丢设置/备份。
5. 卡与供电：SD 卡容量/格式、日志文件名、断电/拔卡是否影响恢复。

## 7. 风险分级

> 分级只针对“若将来在用户授权下操作”的风险；当前阶段**一律不执行**。

| 等级 | 操作 | 恢复覆盖 | 主要风险 | 当前结论 |
|---|---|---|---|---|
| **R0** | 纯离线分析/模拟器 | 不涉及相机 | 无 | 允许（本报告即 R0） |
| **R1** | 真机只读（服务模式读文件/枚举） | 拔线/断电即恢复 | 低；但需授权且不得在 `/usr` 异常时误判 | 本阶段不做 |
| **R2** | 真机写非启动数据（`/setting`、`/tmp`） | 常规启动可恢复 | 中低（历史已有写入并复位记录） | 本阶段不做 |
| **R3** | 真机写 `/usr`（`nflasha15`，几何不变，≤300 MiB） | **有**：所有者验证的看门狗→USB 通道（O） | 中高：F2 未闭合；size 语义未解；写入中断/挂起时序；恢复工具细节未固化 | **禁止**（须先过 §8 全部 gate） |
| **R4** | 真机写 `/usr` + SDM/分区表（M2） | **无**（超出看门狗通道） | 高/不可逆：分区表错误即启动链损坏；官方 USER 通道也不改表 | **禁止** |
| **R5** | 真机写 kernel/initrd/WBI/rootfs/loader | **无** | 极高/不可逆：直接破坏启动链 | **禁止** |
| **R6** | bootloader/SPI/拆焊 | **无已验证通路** | 可能永久变砖 | **禁止** |

关键判断：**R3 是唯一有恢复通道的操作等级，但恢复通道只覆盖“失败”，不覆盖“F2 拒绝/写入中断/错误镜像导致更广损坏”**；且恢复细节仍是 O 级、未固化。因此 R3 也不能现在做。

> 以下 gate 缺一不可；当前状态全部为“未满足”。任何一条未满足时，**不得**进行真机写入，包括“byte-identical”接受性试验。

| **G5** | **第二台相机，或已定位的 UART/JTAG 救砖点** | a6600 UART 测试点未定位 | ❌ 不满足 |
| **G6** | 电源与操作条件：满电 NP-FZ100（≥3 格，建议满电）、原装 USB 线、升级中不断电、按官方说明操作 | 官方警告：中断可永久损坏 | ⬜ 待执行 |
| **G7** | 候选镜像洁净：M1（300 MiB ext2，e2fsck 干净，逐文件语义回读通过），不含 QEMU-only 补丁（`emmc.ko` 调优、`Backup.bin` fixture 等），不含未验证 UI | 避免把模拟器补丁带入真机 | 🟡 M1 构建干净但**阶段一 UI 未达成** |
| **G8** | 校验合同闭合：`part_image.sum` 的 CRC **与 size 字段**更新语义已解、`uc_crc32sum -s -c` 行为已证；FDAT 头 CRC、DEND CRC、trailer 处理均已复核 | 否则 CRC 全对也可能被拒或越界读 | ❌ size 语义未解 |

## 9. “当前不支持真机刷写”的边界声明

1. **本报告不是刷写许可。** 它只整理离线证据和风险边界，不构成任何“可以写”的结论。
2. **阶段二未完成，阶段一也未完成。** 按 96 v3：阶段二完成条件是 M-F（能明确回答“改的镜像 updater 收不收”“刷坏能不能救”），当前 F2 未闭合；阶段一 M-E（可辨识 ASTRA 界面）未达成，候选 M1 镜像本身尚未证明目标功能可用。
3. **任何真机写入必须由用户明确授权。** 授权必须针对具体镜像 SHA256、具体分区/范围、具体操作步骤和失败预案；口头“可以试试”不构成授权。未授权时，本项目不得连接相机进行任何写入（含“只读”之外的 `/setting` 写入、`touch` 测试、byte-identical 试验、刷机）。
