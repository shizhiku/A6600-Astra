# 84 · 首帧门控只读分析：先查 View/dirty，不把第 20 条命令当按键回执

本轮只读分析了 31–45、76–77、最新 81（字体版与四问版）、82、83，及当前 QEMU `dmp_smaph.c`、本地 `libObj.so` 和同架构公开研究。未启动 QEMU，未修改已有文件。

## 结论

1. 当前最早、最直接的软件绘制门控不是 YUV，而是：
   - `View::drawDirect` 只在 `ScalarAppfwIF::IsViewModeDiadem()!=0` 时继续；
   - widget 的 dirty 队列必须非空；
   - dirty widget 的虚函数状态必须允许 dispatch；
   - `GraphicsEngine::updateResource` 中资源虚函数必须返回 0，才执行更新。
2. 现有证据不能证明 YUV off、服务、setting、自检或显示时序直接禁止 OSD 绘制。ch53、PSC、PPF、双缓冲已工作，YUV ch51 是另一层。
3. 上游候选中，**av-cam / submicro 的 boot state / power state 最强**：31–45 已证明 av-cam 状态可直接阻断早期启动；同架构的已验证研究进一步显示 root view 可创建并提交 OSD，但 `CheckerBootState/CheckerBootType` 等待 av-cam/ObjPower 生产者时画面全透明。该跨代结果是强线索，不是 a6600 本轮运行时接收证明。
4. 83 的“第 20 条小命令”不是按键接收证据：它在日志顺序上发生于首个 `KEYINJ` 之前，而且日志只有 24 条全类型共享额度。
5. `reg 0x010=0x12345678` 不应再称为“周期自检写回”。原始 `grm_gles.ko` 的 `sugilite_register_init` 明确写 `BAR+0x1080=0x12345678`；公开命令流研究只把它定为重复 terminator candidate。GPU 完成通过 `BAR+0x34` 状态位和 IRQ 76，不通过 GPU 写回内存 fence。

## 第 20 条小命令复核

`dmp_job_log()` 使用单个 `static int left=24`，`p3d-list`、`ppf-transfer`、`psc-fill`、`p3d-draw` 共用额度。额度耗尽后所有类型均静默。

`frontbtn-20261121T110710Z-113958/stderr.log` 的顺序是：

- 19 个连续的 `p3d-list n=4`；
- 2 PPF + 2 PSC；
- 第 20 个 `p3d-list addr=0x205493c0 n=4`（恰为第 24 条总日志）；
- 之后才出现首个 `[KEYINJ] press ... at 20042 ms`。

所以它既不在按键之后，也不是新增总提交数。基线运行同样固定输出 24 条，只是第 24 条被 PPF 占用。最合理解释是初始化列表与 PPF/PSC 的调度先后改变了日志窗口。

## `0x12345678` 与 GPU 完成

同架构 CXD90045 驱动的直接反汇编合同：

- P3D kick：写 `BAR+0x1804/0x1800`，完成置 `BAR+0x34 bit31`；
- PPF：完成置 bit30；PSC0：完成置 bit26；
- IRQ 76 handler 累积状态并唤醒 `ioctl` waiter；
- EGL sync 是请求执行线程在 ioctl 完成后设置 `0x30F2` 并广播条件变量；没有 GPU 写回 fence/timestamp。

因此 `THREAD_INFRA0` 在 `sugilite_ioctl` 只说明它在驱动等待路径中，可能是等待当前完成，也可能是空闲 kick worker 等下一任务。必须同时看 `BAR+0x34`、IRQ 76、驱动累计状态/等待 mask 才能判死锁。

## 最小运行时探针（当前 libObj load bias `0x055db000`）

### P0：View 模式门控

- `0x05E20AB0`（`ViewManager::drawDirect` 调用 `IsViewModeDiadem` 返回后）
  - `r0==1`：允许继续 draw；
  - `r0==0`：本次 draw 立即返回。
- `0x06A070A0`（`libObj+0x142C0A0`，Diadem mode 全局）
  - 必须为 `0`，`IsViewModeDiadem @ 0x05E224DC` 才返回 1。
- 若 `0x05E20AB0` 从未命中，则门控更早：尚无 View 调用 `drawDirect`。

### P0.5：ViewManager / draw backend 只读字段

- `0x06A06E7C`：导出全局 `pViewManager`；先读 `vm=*(u32*)0x06A06E7C`。
- `backend=*(u32*)(vm+0x14)`：`ViewManager::drawDirect` 实际传给 draw backend 的对象。
- backend 可只读采样：`+0x29`（一次性 dirty/rebuild 标志，函数内部会清）、`+0x08`、`+0x10`（后续 draw/update 对象指针）、`+0x2C`（同步/状态字段）。
- `0x05E22960`：draw backend 入口，`r0=backend`。
- 若需获得 View 包装对象，钩 `View::C2 @0x05E1C308`：入口 `r0=View`、`r1=ViewManager`。View 内 `+0x18` 是底层 view，`+0x24` 是 manager。未找到可可靠命名为 current/root View 的单一导出全局，不应猜结构偏移。

### P1：widget dirty 门控

- `0x059EE284`：`LayoutableWidgetBase::checkAndHandleDirtyEvent` 入口，`r0=this`。
- `0x059EE2A2`：dirty queue empty 检查返回后；此时 `r4=this`。
  - `r0==1` / `[r4+0x19C]==0`：队列为空，直接退出；
  - `r0==0` / `[r4+0x19C]!=0`：存在 dirty，继续。
- `0x059EE2AE`：第二个 widget 虚函数（vtable `+0x104`）返回后。
  - `r0!=0`：进入 dirty dispatch `libObj+0x4131A8`；
  - `r0==0`：dirty 已存在但 widget 状态禁止处理。
- `0x059EE0D2`：`handleDirtyEvent`；若命中，`[this+0x174]` 会暂存当前 dirty event。

### P2：GraphicsEngine resource update

- `0x05BC803E`：`GraphicsEngine::updateResource` 入口。
- `0x05BC8072`：每个 resource 的 vtable `+0x10` 返回后；`r6=resource`。
  - `r0==0`：执行实际更新 helper（`libObj+0x790974`）；
  - `r0!=0`：跳过该 resource。

### P3：事件链（用于区分“按键进入 UI”）

- `0x059AAAEA`：`InputService::createEvent`（偏移 `0x3CFAEA`，Thumb）。
- `0x05E1DA88`：`EventManager::push`。
- `0x05E1C2D8`：`View::requestApplicationExecute`。

只有这些命中并出现正确 event ID，才能证明按键进入 UI；宿主 `[KEYINJ]` 日志和 DMP 列表相关性都不够。

## 候选门控证据排序

| 候选 | 当前直接证据 | 判断 |
|---|---|---|
| View/dirty/资源 update | a6600 `libObj` 直接反汇编 | **首查，直接门控** |
| av-cam / submicro boot/power state | 31–45 的 a6600 早期阻塞 + 同架构透明 root view 的 Checker 证据 | **最强上游候选，待 a6600 运行时确认** |
| GPU completion | 模型已实现 status/IRQ；PSC/PPF 已完成；线程 wchan 单独不判死锁 | 次查状态位与 waiter mask |
| YUV | 与 OSD 分层，无 OSD 门控调用证据 | 不支持直接归因 |
| display timing | ch53 双缓冲、vsync、PPF 已工作 | 不支持直接归因 |
| setting | 字体路径与字体文件已修复；未见 draw gate | 无直接证据 |
| service/self-test | `0x12345678` 是初始化/终止候选，不是接收或绘制证明 | 原结论应撤弱 |

## 额外证据边界

82 号仅凭 preload constructor 早期 `/proc/self/maps` 未见 `libObj`，不足以证明后续不会 `dlopen`。新运行已实证 PID 144 `im.elf` 在用户态映射 `libObj`；因此“UI 位于 LIRO 内核态、用户态探针结构性不可行”的结论应撤回。后续以晚期 maps、线程和实际 PC 为准。
