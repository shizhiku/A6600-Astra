# 119 · A6400 root 通道（PCIEARIA/A6400-Extra-Menu）评估与授权边界

> 撰写时间：2026-11-22。本文件只做**离线技术评估**，不代表已执行任何真机操作。
> 来源：`https://github.com/PCIEARIA/A6400-Extra-Menu`（已 `git clone` 至 WSL `/root/astra/aria`，仅本地阅读）。

## 一、这个项目证明了什么

它是 A6400（FW 2.00，同架构 A6100 亦验证）上的**自制触控浮层菜单**，但对我们真正有价值的是它的**部署通道**：

1. 通过 **Sony-PMCA-RE**（`ma1co/Sony-PMCA-RE`）把相机从「大容量储存」(`054C:0CA8`) 切到 **PMCA service mode** (`054C:0336`)，进入 `serviceshell`；
2. `serviceshell` 内可直接以**高权限**读写机身文件系统（文档中它直接 `cat` 机身 `/usr/lib/libAK8975.so`、写 `/etc/ld.so.preload`、写 `/etc/a6400-autoexec.so`）；
3. 部署脚本 `tools/pmca_deploy_v3_clite.py` 只用**纯数据写入**（`data-only`），并在文档里立了安全铁律：*禁止在 PMCA shell 内热执行守护进程或挂载 SD 卡，一律拔线冷启动*；
4. 开机挂勾 `/etc/a6400-autoexec.so`（配合 `/etc/ld.so.preload`）让任意 ARM 代码在每次冷启动时自动运行 → 即**持久化的开机代码执行**；
5. 提供 `--rollback`（还原 `.pre-v3c-backup` 或干净移除挂勾并 `sync`）、`--diag`（抓日志）、以及 SD 卡 `/disable_hook` + `/A6400/DISABLE` 两个**离线急停旗标**。

所以「可以提取 root」的准确含义是：

- **PMCA `serviceshell` 本身就是一个高权限 shell**，不需要额外漏洞即可读机身任意文件、任意分区设备节点；
- 进一步，用 `/etc/a6400-autoexec.so` 可以做到**开机自动以高权限执行任意 ARM 程序**（这是持久化，风险也最高）。

## 一·补 · root 权限已由源码证据确认（两条独立路径）

**结论：能，而且是确定性的，不是推测。**

### 路径 1：PMCA serviceshell 本身是 root

`tools/pmca_deploy_v3_clite.py` 的实际写入步骤（第 100–154 行）直接执行：

```sh
/bin/busybox cp ... /etc/a6400-autoexec.so.new      # 写 /etc
/bin/busybox mount -t tmpfs -o size=4096k tmpfs /tmp_bt   # mount（需 CAP_SYS_ADMIN）
/bin/busybox mount -t tmpfs -o size=2048k tmpfs /tmp_bt/v3c_up
echo /etc/a6400-autoexec.so > /etc/ld.so.preload.new
```

**能 `mount`、能写 `/etc` 就说明这个 shell 是 root**。这不是提权漏洞，而是 PMCA service mode 本身就是高权限维护 shell。

### 路径 2：开机钩子是持久化 root 代码执行（源码可证）

`tools/build_autoexec_hook.py` 把一段**裸 ARM 汇编**打进 `libAK8975.so` 偏移 `0x988`，装成 `/etc/a6400-autoexec.so`，并写 `/etc/ld.so.preload`。这段汇编做的事：

| 步骤 | 汇编证据 |
|---|---|
| 三处急停检查 | `sys_access`(33) 查 `/mnt/disable_hook`、`/mnt/disable.txt`、`/tmp/disable_hook` |
| 建锁 | `sys_open`(5) `O_EXCL` 建 `/tmp_bt/ae.lock`，防重复执行 |
| **挂 tmpfs** | `sys_mount`(21) `-t tmpfs size=2048k /tmp_bt` → **需 root 权限，证明钩子以 root 运行** |
| **脱离会话** | `sys_fork`(2) 两次 + `sys_setsid`(66) → 完全脱离的守护进程 |
| **执行任意脚本** | `sys_execve`(11) `/bin/sh /tmp/autoexec.sh`，env `PATH=/usr/bin:/bin:/sbin:/usr/sbin:/tmp` |

**含义**：每次冷启动，`ld.so.preload` 会在最早加载它的 root 进程里运行这段代码，进而以 **root 身份执行 `/tmp/autoexec.sh`**。而 `autoexec.sh` 的内容正是我们通过 PMCA 写进去的任意脚本 → **开机自动 root 执行任意命令**。

### 这条 root 能力对「修改固件」意味着什么

Sony 的签名校验（F2）是在**升级程序（updater）里**做的，不是在 flash 控制器里。**拿到 root 后可以直接 `dd` 写 `/dev/nflashaXX` 分区，完全绕过 updater 的签名检查。**

也就是说：

- **F2（签名/接受性）不再是刷入的硬门槛** —— 有了 root 可以绕过；
- 但这同时意味着**安全网也没了**：绕过了官方校验，写错就是写错。

## 二、对 96 号任务书的价值（这是重点）

我们阶段一目前最大的外部依赖是：**ZV-1M2 五代固件里 `/system`（nflasha16 等）、部分 `/rootfs` 分区不在我们手上的 `firmware.tar` 里**。`109` 号报告的结论是「本机确实没有 libgpe/libCoreSync 等实现，但原厂 ZV-E10 也只是引用不实现，倾向可跳过」。如果这个结论错了，我们需要真机数据才能证伪。

用 PMCA 通道可以（在**只读**前提下）：

| 目标 | 用途 | 是否写机身 |
|---|---|---|
| `cat /proc/mounts`、`mount`、`df` | 确认 a6600/ZV 实际挂载布局与分区表 | 否 |
| `cat /proc/partitions`、`/proc/cmdline`、`/proc/modules` | 确认 SDM 分区名/大小、内核模块清单 | 否 |
| `dd if=/dev/nflashaXX of=...`（**输出到 SD 卡或经 shell 回传**） | dump 我们缺的分区（`/system` 等） | 否（只读源分区） |
| `ls -l /usr/lib/`、`sha256sum` 等 | 核对真机库清单与我们镜像的差异 | 否 |
| 确认看门狗/恢复通道（F4/F5） | 读 `dmesg`、`/proc/cmdline` 里的 `wdt.*`、日志路径 | 否 |

也就是说：**仅用 PMCA 的只读能力，就能大幅补强 F1–F5 证据、并验证「缺失库」结论**，而不需要写任何东西进机身。

## 三、风险分级

| 操作 | 风险 | 说明 |
|---|---|---|
| **A. 只读 serviceshell**（`cat`/`ls`/`dd` 读分区到 SD） | **低** | 不写机身；PMCA 会切 service mode，但正常断电即可恢复。仍需注意：`/etc` 与 `/tmp` 共用 `/dev/nflasha10` 同一 inode，**任何误删/误写都会同时影响两者**。 |
| **B. 写 `/etc/a6400-autoexec.so` + `/etc/ld.so.preload`**（持久化开机执行） | **中高** | 修改了 `/etc`（= `/dev/nflasha10`），属于「非 `/usr` 分区」改动。按 `110` 号报告，**看门狗→USB 恢复通道只对 `/usr`-only 改动有效**，改 `/etc` 不在已验证的救砖范围内；虽然有 `--rollback`，但依赖机器还能进 PMCA。 |
| **C. 用该通道刷入我们自己的 ASTRA 改造镜像** | **高** | 等价于改 `/usr`（甚至 SDM），当前 F2 未闭合，且 M-E 未达成，**没有任何理由现在做**。 |

## 四·补 · 拿到 root 后「修改固件」的三条现实路线

有了 root，改固件不再受 updater 签名约束，但**风险等级完全不同**，必须分开对待：

| 路线 | 做法 | 风险 | 是否推荐 |
|---|---|---|---|
| **R1 只读 dump** | `cat`/`ls`/`dd` 读 `/dev/nflashaXX` 到 SD 或回传，**不写机身** | 低 | ✅ 现在最有价值 |
| **R2 原位改 `/usr`** | `dd` 写 `nflasha15`（/usr） | 中：仅 `/usr` 改动在已验证的「看门狗→USB 恢复」范围内 | ⚠️ 需 M-E 先成功 |
| **R3 改启动链** | 写 `/etc`(nflasha10)、kernel(nflasha3)、SDM、bootloader | **高：无已验证恢复通道**，砖机风险 | ❌ 不建议 |

**关键判断**：现在最该用 root 做的是 **R1**，因为它能直接回答我们最大的未知——「五代缺失库到底在不在 `/system`」。而 R2/R3 现在没有意义：**我们还没有一个能出画面的 ASTRA 镜像可刷**（M-E 未达成）。

## 五、结论与建议（需要你决定）

**技术结论**：这个项目确实提供了一条可行的 root/高权限通道，且它对我们最有价值的用法是**只读 dump 缺失分区**，而不是刷我们的实验镜像。

**我的建议**：

1. **现在不要做任何真机操作**。理由：阶段一卡点是五代 UI 初始化/绘制逻辑（离线可继续推进），不是「缺库」——`109` 报告已证明原厂 ZV-E10 同样「只引用不实现」也能开机。
2. 如果后续离线确实推进不下去、且怀疑是缺 `/system` 库导致，**再考虑 A 类只读 dump**，并把范围严格限定为：只读 `cat`/`ls`/`dd` 到 SD 卡，**不写机身任何文件**。
3. **B/C 类（写 `/etc` 挂勾、刷改造镜像）在你没有逐次明确授权前一律不做**；即使授权，也需要先给出镜像 SHA256、目标分区、步骤、失败预案与恢复路径。
