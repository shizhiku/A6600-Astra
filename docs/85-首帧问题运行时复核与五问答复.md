# 85 · 首帧问题：两轮运行时复核与五问答复

日期：2026-11-21。全部实验在 QEMU 的新 qcow2 子覆盖层中完成，未连接或修改相机。eMMC 与字体沿用当前基线，不重新讨论其根因。

## 先纠正两个会改变调查方向的前提

### UI 实际在用户态，82 号结论应撤回

第一轮 `probe84-20261121T115805Z-118001` 在启动后晚期扫描所有 `/proc/*/maps`，明确发现：

```text
OWNER=/proc/144
im.elf
055db000-068d8000 r-xp ... /usr/lib/libObj.so
068df000-069cf000 rw-p ... /usr/lib/libObj.so
Threads: 172
```

证据：该运行 `serial.log` 2129–2133、2221–2223；线程采样3174–9882。

因此，“没有用户进程映射 libObj”只是先前 preload 构造阶段过早采样的结果，不能推广到应用完成 dlopen 以后。LIRO 负责 av-cam/RTOS 任务，并不意味着 Appframework 也在内核态。

第二轮 `probe84-20261121T122259Z-127568` 用显式 GLIBC_2.4 符号版本的 preload 线程，成功在 PID144 读取 libObj 的运行时全局。这是用户态探针可行的直接验证。该轮因 preload 改变映射，libObj 基址变为 `0x05A04000`，不能沿用第一轮绝对地址。

### “19 条变 20 条”不能证明按键进入 UI

QEMU `hw/display/dmp_smaph.c` 的 `dmp_job_log` 使用 `static int left=24`，P3D、PPF、PSC、draw 共用同一额度。第24个任务以后日志全部静默。

`frontbtn-20261121T110710Z-113958/stderr.log` 中第20个 P3D 小表 `0x205493c0` 实际出现在首个 `KEYINJ` 之前。第一轮新实验再次出现同一小表，位置仍在注入前的初始化阶段。

此外，`REA_DMP_DUMP` 的列表内容输出本身也只保留前40个列表。因此，仅据现有这两种限额日志，不能证明整个运行期间从未写过 draw kick。

这不否定已实测的 PSC/PPF 像素通路；它纠正的是提交次数、按键因果关系与“永远无 draw”证据覆盖范围。

## Q1 · 第一帧还需要什么？

**目前不能给出一条已证实的 a6600 READY opcode，也没有证据支持“先有传感器图像，OSD 才能画”这个必要条件。**

本机静态代码中可直接看见的软件门控是：

1. `View::drawDirect` 的路径要求 `IsViewModeDiadem()!=0`。
2. widget dirty 队列非空，且 widget 的状态检查允许处理 dirty。
3. GraphicsEngine 的资源更新检查允许执行实际 update。
4. 上层必须已经创建/激活要显示的业务 View，产生有内容的资源/dirty；仅建立显示后端和交换黑色缓冲不能证明这一步完成。

### 本轮已实测排除哪个门控

第二轮每秒只读采样40次，结果稳定：

```text
[UI84] pid=144 base=05a04000 mode=0 inputsvc=00141df0 fonthead=00054938
[UI84] vm=00120a30 backend=00114bb0 dirty=0 obj8=0007d9a8 obj10=0007d160 sync=00000000
```

- mode 全局是 `libObj+0x142C0A0`；0使 `IsViewModeDiadem` 返回1。**模式门控通过。**
- InputService、ViewManager、backend 对象非空。**对象已建立。**
- backend+0x29 是一次性重建标志，本轮采样为0。它不是 widget dirty 队列计数，也不证明根 View 完全透明或没有业务 View。
- 尚未运行命中式探针统计 widget dirty 检查、业务 View 激活、GraphicsEngine update 的次数，所以最终卡在哪个业务状态仍未定。

### 调查顺序

先修观测，再找状态生产者：

1. 给 `p3d_write` 的 `reg==0x202` 增加**独立、无共享额度的总计数**；同时分别统计 P3D list、PSC、PPF。不要用前24条任务日志当总数。
2. 在 `InputService::createEvent` 记录真实 eventId，确认 MENU 是否到达 UI；宿主 KEYINJ 只证明模型写入，不能证明驱动/框架已经接收。
3. 若确实 draw_count=0，钩 View/dirty/update 链，定位第一个从未执行或条件不满足的分支。
4. 只有业务 View 的 checker 明确在等 boot/power/camera state 时，才回追 av-cam/ObjPower/submicro 的生产者。不要先伪造一个未知结构的“系统就绪”消息。

静态探针地址均写成 libObj 偏移，运行时必须加**当轮真实 load bias**：

| 位置 | 偏移 | 记录内容 |
|---|---:|---|
| InputService::createEvent | 0x3CFAEA | r1=eventId；确认是否0x1AC |
| EventManager::push | 0x842A88 | 事件是否入总线 |
| drawDirect 模式检查返回 | 0x845AB0 | r0=1允许继续 |
| widget dirty 检查返回 | 0x4132A2 | r0=1空/0非空；r4=this，this+0x19C为队列成员 |
| widget 状态检查返回 | 0x4132AE | r0非0才处理dirty |
| resource 更新检查返回 | 0x5ED072 | r0=0才做实际update；r6=resource |

另见 `84_first_frame-首帧门控只读分析.md`。目前最强上游候选是 av-cam/ObjPower 的 boot/power state；这是候选，不是已定位的 a6600 首帧判据。

## Q2 · input 调试接口真名

**`/proc/udm/input`。不需要 Input_debug 才创建。**

模块通过 UDIF 注册驱动，`kbd_probe(.text+0x40C0)` 无条件调用 `udif_create_proc`，名字为 `input`，父目录由 UDIF 提供为 `/proc/udm`。`Input_debug` 只控制错误日志；`key_tbl` 参与键表选择，不控制 proc 创建。

客户机可执行：

```sh
echo table > /proc/udm/input
cat /proc/udm/input

echo adc > /proc/udm/input
cat /proc/udm/input

echo front > /proc/udm/input
cat /proc/udm/input

echo get > /proc/udm/input
cat /proc/udm/input
```

本轮 `get` 和 `table` 已实测读取成功。`get` 可附数值选择查询键，例如先核对驱动解析行为后以 `get 0x1ac` 定向读MENU；单纯 `get` 默认查询0，不能把其零事件当作所有键均未采到。

真实键表摘录：

```text
*** ADC KeyConfig ***
port:f-0  0/5b ... H2 key:1ac-1
```

这对应 MENU 码 `0x1AC`，ADC全局端口0x0F，电平0..91。全局0x0F实际是第二ADC单元/local ch3，**并不是向单个 ADC 对象传15**。现有 `REA_ADC_SEQ="3:45"` 的通道选择有依据；下一步应在按住期间读 `adc` 和 `get`，闭环确认，而不是继续扫未知位。

完整静态注册与参数说明见 `84-proc节点与LIRO状态诊断.md`。

## Q3 · 哪个节点能看阻塞？

- `/proc/liro` 是目录；本机只有 `susres`。
- **不要把 `/proc/liro/susres` 当状态页读取。** 读回调是 `proc_suspend`，会执行 suspend/resume 动作。第一轮探索读取返回EIO；之后不应再把它列入常规采样。
- `/proc/osal/minfo` 仅是内存池。
- `/proc/osal/uipc` 是 OSAL 队列/信号量/代理进程诊断。普通cat本轮读取到版本4.2、proxy线程数、msgq/sem计数与内存池；代码有 msgq_dump、bsem_dump 内部分页，具体用户态切页方法尚未实测，不能把 `dd skip=1` 当作可靠分页选择。
- `/proc/osal/ulogio` 是日志方向，本轮未完整还原，不作为任务等待原因来源。

真正先看标准Linux线程节点：

```sh
# 启动完成后找真正映射libObj的PID
for p in /proc/[0-9]*; do
  grep -q libObj.so "$p/maps" 2>/dev/null && echo "$p"
done

# PID以本次结果为准
P=144
for t in /proc/$P/task/*; do
  echo "$t"
  cat "$t/comm"
  cat "$t/wchan"
  echo
 done
```

可再尝试 `status`、`stack`、`syscall`，但是否可读取决于本内核配置；本轮**可靠取得的是status/wchan**，没有取得完整用户态调用栈。

实测重要线程：

| 名称 | TID（第一轮） | wchan |
|---|---:|---|
| Appframework | 365 | osal_wai_sem_tmo |
| ObjRenderer | 428 | futex_wait_queue_me |
| ObjRendererInfr | 427 | osal_rcv_msg_tmo |
| I-InputRecv | 356 | osal_rcv_msg_tmo |
| I-InputRepeat | 355 | utimer_res_sleep |
| THREAD_INFRA0 | 318 | sugilite_ioctl |

这些都是某个采样时刻的等待点，不等于故障结论。尤其GPU worker在ioctl中可以是正常空闲等待，不能据此直接补中断或强制唤醒。

## Q4 · 能否绕过liveview进菜单？

a6600尚未实证“无需任何相机状态即可直接进菜单”；也没有查到一条可确认的 factory/service 参数让机身无条件显示菜单。

但本次已经证明用户态可达，**LD_PRELOAD/ptrace不再是结构性不可行**。后续可在 Appframework 初始化后，沿真实InputService路径注入MENU，或追菜单View激活条件。仍需确认event结构与消费时机，不能把旧的未验证injector称为已成功方案。

USB senser/service shell与机身菜单是不同层次。PMCA service mode资料证明的是USB维护/校准与运行中代码执行，不证明菜单跳过liveview依赖。

## Q5 · 同类项目是否已有画面？

以下是项目方公开运行声明及证据记录，不是本工作区已复现；公开文档记录了截图路径/哈希，但未找到对应公开artifact图片，不能冒称已经亲眼核验stock截图。

### a5000

Oein/a5000-cfw 的 emulator README明确声明原厂UI能在QEMU窗口渲染、MENU高亮能按方向移动，并能经过首次设置到拍摄OSD。其真实sensor/ISP仍缺失，liveview黑底与OSD菜单能够并存。实现覆盖VPH、SIO/GPIO/ADC、submicro回放和P3D解码/光栅化。

- https://github.com/Oein/a5000-cfw/blob/main/packages/emulator/README.md
- https://github.com/Oein/a5000-cfw/blob/main/packages/emulator/docs/RE_UI_BRINGUP.md

### a6400

bionz-x-research记录了原厂菜单和后屏拍摄OSD。关键演进是：早期用诊断overlay强制选择后屏；后续补齐**active-low眼感GPIO P0.2复位高电平**后，原厂FINDER/MONITOR状态机可选择并渲染后屏。合成亮度liveview是单独的opt-in路径，不是真实sensor/RAW/color ISP。

- E0573：原厂菜单/后屏按键：https://github.com/ivica00/bionz-x-research/blob/main/docs/evidence/0573-qemu-a6400-rear-panel-controls.md
- E0651：眼感与原厂后屏选择：https://github.com/ivica00/bionz-x-research/blob/main/docs/evidence/0651-qemu-a6400-stock-finder-monitor-rear-lcd.md
- E0591：合成亮度liveview：https://github.com/ivica00/bionz-x-research/blob/main/docs/evidence/0591-qemu-a6400-first-live-view-frame.md
- E0665：公开updater输入可到OSD、仍有输入与step限制：https://github.com/ivica00/bionz-x-research/blob/main/docs/evidence/0665-qemu-boots-from-the-public-updater.md

因此眼感、FINDER/MONITOR和实际输出head值得对齐；但不能把a6400 P0.2直接照搬为a6600引脚合同，更不能仅凭它解释本机所有黑屏。
