# 42 · 问题 B 收窄：疑似 Thumb 位丢失导致的 ARM 态执行

本轮为离线分析。无设备写入。

## 一、修正上一轮的错误结论

上一轮我看到日志里的

```
WARNING: file not found: im.elf
```

就判断“im.elf 缺失”。**这是错的**。

`im.elf` 确实存在：`/bin/im.elf`，21,820 字节，位于 `/usr` 分区（`nflasha15`）。那条警告是加载器**先按相对路径查找失败**的记录，随后仍从 `/bin` 正常加载了。

同时确认：

- `/lib/libc-2.11.2.so`（`nflasha7`，984,276 B）是唯一的 libc；
- `/usr` 分区没有第二份 libc；
- `nflasha5`（34 MB）不是文件系统，是原始数据。

## 二、故障地址的内存内容与文件一致

在固定基址下断并读取该地址内存：

```
0x041CC796: 80 bd af f3
```

与文件中 libc 偏移 `0x15796` 完全一致。Thumb 解码为 `pop {r7,pc}`（合法指令），前面是 `push {r7,lr}; mov r7,ip; svc #0` 的系统调用桩。

## 三、异常现场的寄存器（关键）

日志给出完整 dump：

```
pc: 0x04253796   lr: 0x04262d8f   sp: 0x129d5014
r0: 0x00000000   r1: 0x00000170   r2: 0x00000006  r3: 0x170
r4: 0x00000006   r5: 0x129d7920   r6: 0x129d7460  r7: 0x0000010c
r9: 0x00000003   ipsr: User(SVC)  cpsr: 0x20000030 (Thumb: on)
```

- `r7 = 0x10C`（268）—— ARM 系统调用号就放在 r7，符合 syscall 桩的形态；
- `lr = 0x04262D8F`，**奇数**，说明调用方处于 Thumb 状态，调用点在 im.elf 内 `0x04262D8E` 附近；
- 但被调用的目标 `0x04253796` 是**偶数**。

## 四、最可能的解释：Thumb 位丢失

若调用方用 `blx` 跳到一个**低位被清零**的地址（`...796` 而非 `...797`），CPU 会切到 **ARM 状态**执行该地址。

在 ARM 状态下，该地址的机器码为 `0xF3AFBD80`——属于 ARM 的 SIMD/无条件指令空间。QEMU 的 `cortex-a5` 模型若不解码这一具体编码，就会抛出**未定义指令**，内核随即向进程投递 SIGILL。

这可以解释全部现象：

1. 内存字节正确、Thumb 解码正确，却报未定义；
2. CPSR 显示 Thumb=on 是**异常处理后的保存值**，不能反推异常瞬间的状态；
3. 崩溃点正好是函数中段（`pop`），不可能是正常调用目标。

## 五、QEMU 异常日志的旁证

用 `-d int` 记录整轮异常：

| 异常类型 | 次数 |
|---|---|
| 1 未定义指令 | 1,272 |
| 2 SVC | 34,384 |
| 3 预取中止 | 1,909 |
| 4 数据中止 | 13,530 |
| 5 IRQ | 153,044 |

其中**用户态（from EL0）的未定义指令有 305 次**，全部返回到内核向量 `0x6010DD20`——说明内核会例行处理未定义指令（其中大部分应是被内核识别的特殊编码）。我们这一次落在“内核不认识”的那一类，于是投递 SIGILL。

## 六、下一步

1. 在 `0x041CC796` 下断时**读取 CPSR 的 T 位**（当前观察器只解析 r0–r15，需要扩展），直接判定异常瞬间是 ARM 还是 Thumb；
2. 反汇编 im.elf 中调用点 `0x04262D8E` 附近（需先确定 im.elf 的加载基址），确认调用用的是 `bl` 还是 `blx`、目标地址从哪来；
3. 若确认是 Thumb 位丢失，则要查该函数指针的来源（重定位、函数表、还是 `dlsym`）。
