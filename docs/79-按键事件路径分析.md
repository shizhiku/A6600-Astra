# 79 · 用户按键事件路径分析（MENU 注入可行性）

本轮为纯静态分析：只读 ext2 镜像、只反汇编固件内的 ELF，不运行 QEMU、不修改任何镜像。
所有地址均为**文件内虚拟地址（VA）**。libObj.so 的 `.text`/`.rodata` 满足 `sh_addr == sh_offset`，
故对 libObj 而言 VA 与文件偏移相等；其他库未逐段核对偏移，只给 VA。

---

## 一、结论（TL;DR）

1. **按键不走 `/dev/input`，走 uipc 消息 + 共享内存**，与之前的排除结论一致。真正的输入枢纽是
   libObj.so 里的 **`InfraInput`**（单例，对象 0x224 = 548 字节），它通过 `libosal_uipc` 的
   消息队列收发 `_InfraInputEvent`（24 字节：key_code / sub_key_code / status / ex_info / …）。
   `InfraTp`（触摸屏）、`InfraDial`（转盘）、`InfraLanc`、`InfraSircs`（遥控）是并列的同类
   "Infra*" 端点，全部同一套 uipc 命令语义。
2. **UI 侧存在一个明确的、可进程内调用的注入入口**，而且链条极短：

   ```
   InputService::callback_direct(ev)            ← 物理键回调（InfraInput 注册）
     └→ 内部转换器 0x3D2D1C(cb, ev, 0)
          ├→ snd_InfraInputEvent_to_InputServant(ev)      // 同步转发给"输入仆人"
          ├→ InputService::createEvent(ev->key_code, 4)   // ★ Event 的 ID 直接用 key_code
          ├→ Event::addParameter(27/28/32, ParamBase*)    // status / ex_info / sub_id
          └→ InputService::pushFilterEvent(Event*)        // ★ 进 UI 事件总线
                └→ UtilityBase::pushEvent → AbstractUtilityManager::pushEvent
                     └→ EventManager::push(Event*, bool)  // vtable 分发到 View/Widget
   ```

   `createEvent` / `pushFilterEvent` / `Event::Event` / `EventManager::push` **全部是 libObj 的
   导出符号**，且 `InputService` 有全局单例指针 `InputService::m_pMyInstance`(0x13F5E6C)。
   因此"在客户机里投递一个按键/事件"在 ABI 层面是**完全可行**的（方案 A）。
3. **还发现两条更"原厂"的注入面**（都在 libObj 里，且都靠字符串/结构自证）：
   - `/usr/share/appfw_infra/infra_tp_key_emulation.txt`：`InfraTp` 构造时用 `fgets`+`strtol`
     读入**最多 9 个整数**到 `.bss` 里的 `int key_emulation[9]`，把"模拟按键"换算成触摸坐标
     （日志 `[INFRATP]%s, key_emulation[%3d] (x, y) = (%3d, %3d)`）。该目录在固件里**不存在**，
     目前是死代码——但只要我们造出这个文件，就得到一个"不改代码"的按键注入通道（方案 B3）。
   - `INFRA_INPUT_TEST_CMD_CB_SEND_EVENT`：InfraInput 自带一个测试命令回调，参数就是
     `key_code / sub_key_code / status / ex_info` —— 即**官方留的"造一个按键事件"接口**；
     另有 `ILOG_*` 录制/回放（`/tmp/appfw_infra/ilog_data_%010d.bin`），可回放伪造按键序列（方案 B2/B4）。
4. **缺口只有一个：MENU 键的数值。** 物理键码由副控制器/配置表下发（`key_code → local_code`
   的 `config_table` 通过 uipc 命令 `INFRA_INPUT_UIPC_GETKEYCONFIG` 在运行时取得），**固件里没有
   静态按键枚举**。但注入并不一定需要它：可直接用"UI 层事件 ID"或触摸坐标绕过（见第七节）。

## 二、分析对象与方法

| 对象 | 路径（镜像内） | 大小 | 说明 |
|---|---|---|---|
| UI 主进程 | `/bin/im.elf` | 21,820 | 引导器：NEEDED `libosal_uipc/libosal_utm/libIMDB/libbackup/libjemalloc`，自身仅 2 个导出函数、62 个导入 |
| 输入枢纽+UI 框架 | `/lib/libObj.so` | 20,889,004 | 1,853 个导出函数；`.ARM.exidx` 恢复出 **61,481 个函数入口**（含 static） |
| 视图/布局插件 | `/lib/viewUnified2.so` | 11,553,828 | `LG_view*` 家族；NEEDED 只有 libc/libgcc/`CautionConfig.so` → 由 libObj `dlopen` 载入，反向引用 libObj 的 162 个类符号 |
| 副控制器传输 | `/lib/libsencore.so` | 349,760 | `SenserThread`/`NinThread`/`Usb`/`SenserPacket`/`HandlerSlot{u16 cmd}`；导入 `osal_snd_msg/osal_rcv_msg_tmo`、`testcmd_init` |
| uipc 用户态 | `/lib/libosal_uipc.so` | 26,644 | `u_osal_*` 封装 + `osal_*` 实现：msgq / sem / vpool / fblock |
| uipc 内核态 | `/kmod/osal_uipc.ko` | 38,872 | `/dev/uipc` |
| 触摸/按键端点 | `/lib/libObj.so` 内 `InfraTp`/`InfraInput`/`InfraDial`/`InfraLanc` | — | 同一套 uipc 命令语义 |

方法（全部离线）：

1. 用项目 `02-脚本/a6600_usr.py` 的 `Ext2` 类把 `/lib`、`/bin` 下的 162 个 ELF 全量导出；
2. `readelf -sW` 取 `.dynsym`（这些库已 strip，只有动态符号表）；`c++filt` 反修饰；
3. 用 `.ARM.exidx`（PREL31）恢复**全部函数入口**，解决"本地 static 函数无符号导致调用点归因失败"；
4. 自写 Thumb-2 `BL/BLX` 解码器扫 `.text`：libObj 解析出 **253,635** 条直接调用边；
5. 自写 PC 相对字面量解析（`ldr rX,[pc,#n]` + `add rX,pc`，含 `LDR.W/ADD.W`），得到
   **128,406** 条字符串/数据引用，用于"某函数引用了哪些日志字符串"的归因；
6. `arm-linux-gnueabi-objdump` 定点反汇编关键函数（宿主 x86 binutils 无 ARM 目标，故装了
   `binutils-arm-linux-gnueabi`）。
7. **重要技巧**：libObj 里**每个函数开头都会打印自己的反修饰签名**（如
   `static void InfraInput::EventThread(void*)` 存在 `.rodata` 0x10135c3），可用来给 static 函数命名。

### 4.2 关键函数的反汇编摘录（objdump，Thumb-2）

**(1) `snd_InfraInputEvent_to_InputServant` @0x3CF87C** —— 拿到 msg_id 与事件长度：

```
3cf884  blx ScalarAppfwIF::IsViewModeDiadem()      ; 某模式下不转发
3cf896  ldr r0,[pc] → msg_id = 0x014A0429           ; ★ "InputServant" 的 osal 消息号
3cf898  blx osal_valloc_msg_wait(msg_id,&msg,24,1)  ; ★ size = 24 = sizeof(_InfraInputEvent)
3cf89e  ldmia r4!,{r0..r3} ; stmia r6!,{r0..r3}     ; 拷 4 个字
3cf8a6  ldmia.w r4,{r0,r1} ; stmia.w r6,{r0,r1}     ; 再拷 2 个字 → 共 24 字节
3cf8b2  blx osal_snd_sync_msg(msg_id, msg)          ; 同步发送（会等对端）
3cf8ba  blx osal_free_msg(msg_id, msg)
```

**(2) 共享转换器 0x3D2D1C（无符号，static；被 callback_direct / callback_panel / callback_tp 共用）**

```
3d2d2e  blx snd_InfraInputEvent_to_InputServant(ev)  ; 无条件先转发
3d2d32  cbnz r6, 3d2d80                              ; r6 = 第3参数 isDest；非0 跳过"键重复"分支
   ; --- isDest==0（物理按键路径）的重复/抑制判定 ---
3d2d46  ldr r3,[r5,#0]                               ; ev->key_code
3d2d58  bl 0x3D14F8(this,&keyCode)                   ; 取"上次键模式"
3d2d60  bl 0x3D0A26(this)
3d2d6c  bl 0x3D0666(&a,&b)                           ; 判定是否需抑制/合并
3d2d7a  cmp r9,#0 ; bne 3d2e38                       ; 抑制 → 直接返回（不产生事件）
3d2d80:
3d2d84  ldr r1,[r5,#0]                               ; ★ r1 = ev->key_code = Event ID
3d2d82  movs r2,#4                                   ; ★ dest = 4
3d2d8e  blx InputService::createEvent(id, 4)         ; → new(16) + Event::Event(id,4,1)
3d2d96  bl  0x3CF120                                 ; isDest!=0 时 setDest(0)（TP 路径）
3d2da0  movs r0,#20 ; blx operator new(20)           ; ParamBase = 20 字节
3d2da6  ldr r1,[r5,#8]  ; bl ParamBase::ctor(...)     ; ★ 参数1 = ev[8]
3d2db4  ldr r1,[r5,#12] ; bl ParamBase::ctor(...)     ; ★ 参数2 = ev[12]

3d2dfc  blx InputService::pushFilterEvent(event)      ; ★ 进入 UI 事件总线
```

**(3) `InputService::pushFilterEvent` @0x3D1818**

```
3d182e  blx osal_wai_sem_tmo(lock, -1)               ; 加锁
3d1838  ldr r3,[GOT] → [r3] ; cbz ; blx r3           ; ★ 可插的"过滤器回调"（空则走 3D1702）
3d1876  bl UtilityBase::pushEvent(event)             ; ★ 真正入队
3d187c  blx osal_sig_sem(lock)
```

**(4) `EventManager::push(Event*, bool)` @0x842A88**

```
842a98  bl Event::getDest()  → dest
842a9c  cmp #1 / cmp #3                              ; dest∈{1,3} 走"直接分发"
842ab2  ldr.w r0,[vtable + dest*4]                   ; ★ 按 dest 选目标对象
842ab6  blx [this+8]                                 ; ★ 调成员函数指针（分发）
842ac0  blx [this+12]                                ; dest==1 时追加一次
```

```
860e1c  bl 0x860C64                                  ; 找一个空槽 → r0
```

## 五、uipc 报文与命令字（从 `.rodata` 日志字符串反推）

### 5.1 记录结构

```
struct _InfraInputUIPCDataRecord {
  struct Header {            // 日志: "command = 0x%08X = %d" / "size = 0x%08X = %d"
      uint32 command;        // ★ 命令字，实际按 0x%04X 打印/比较
      uint32 size;           // payload 字节数
  } header;
  struct Payload {           // 日志: "payload.params[%3d] = 0x%08X = %12d"
      int32  params[N];      // ★ 定长参数数组（不是变长 blob）
  } payload;
};
```

对应日志（libObj `.rodata`，VA）：
`[INFRAINPUT]%s, command = 0x%04X, size = %d` @0x1011243；`payload.params[%3d]` @0x1011201。

### 5.2 命令字

调度处 `0x85E614: cmp r3,#9` → **请求命令 = 0x0000..0x0009（10 条）**；
每个分支末尾把 `movw r3,#0x800N` 写进应答 → 应答值为 `0x8001..0x8008`（**推测规则为 `0x8000|cmd`**，
观测到的是这 8 个具体常量）。

| 请求 cmd | 应答 | 名称（字符串自证） | 参数 |
|---|---|---|---|
| 0 | 0x8000 | （未单独出现日志） | — |
| 1 | 0x8001 | `INFRA_INPUT_UIPC_GETKEYCONFIG` | `subsystem`；返回 `config_table/config_table_no/config_size` |
| 2 | 0x8002 | `INFRA_INPUT_UIPC_SETOSALID` | `osal_id`（src osal_id） |
| 3 | 0x8003 | `INFRA_INPUT_UIPC_RMCALLBACK` | `callback_id` |
| 4 | 0x8004 | `INFRA_INPUT_UIPC_SETEVENTKEYLIST` | `callback_id, list_no` |
| 5 | 0x8005 | `INFRA_INPUT_UIPC_RMEVENTKEYLIST` | `callback_id, list_no` |
| 6 | 0x8006 | `INFRA_INPUT_UIPC_SENDEVENTINITDATA` | `callback_id` |
| 7 | 0x8007 | `INFRA_INPUT_UIPC_SETKEYINH` | `key_code, inh` |
| 8 | 0x8008 | `INFRA_INPUT_UIPC_GETKEYINH` | `key_code` |
| 9 | (0x8009) | `INFRA_INPUT_API_SETKEYREPEAT` / `…SETKEYREPEATRESET` | `key_code, stop, repeat0, repeat` |

其他日志：`[INFRAINPUT] Unknown error, command = 0x%04X, size = %d`；`exec command`；
`[INFRAINPUT] ret = %d, callback_id = %d`。

**注意**：这 10 条都是**控制类**（注册/查询/抑制/重复率），**没有"投递一个按键事件"的命令字**。
事件的实际投递是"枢纽 → 回调/osal 直发"，因此见 5.3 与第七节。

### 5.3 `_InfraInputEvent`（24 字节，回调与转发的载体）

由 4.2(1) 的 24 字节拷贝 + 调试打印字段顺序可还原：

| 偏移 | 字段 | 证据 |
|---|---|---|
| +0x00 | `key_code`（**同时被当作 UI Event ID 使用**） | `ldr r1,[r5,#0]` → `createEvent(id,4)`；`[INFRAINPUT] key_code = 0x%08X` |
| +0x04 | `sub_key_code` | `[INFRATP] key_code = 0x%08X, sub_key_code = 0x%08X, status, ex_info` |
| +0x08 | `status` | → `addParameter(27, …)` |
| +0x0C | `ex_info` | → `addParameter(28, …)` |
| +0x10 | `sub_id` | `[INFRAINPUT] sub_id = 0x%08X`；→ `addParameter(32, …)` |
| +0x14 | 保留/时间戳 | 24 − 20 = 4 字节，未在日志中出现（**推测**） |

`InfraInputPhyKeyData`（`GetPhyKeyStatus` 用）是同一组字段 + `config_pos/internal_flag/timer_id/repeat_count/inh`
（日志 `InputPhyStatusTable` / `InputPhyKeyInternal data` @0x1012070 起）。

## 六、按键码线索

### 6.1 固件里**没有**静态按键枚举（这是结论，不是遗漏）

- 键码由副控制器/子系统下发：`INFRA_INPUT_UIPC_GETKEYCONFIG(subsystem)` 返回
  `config_table`，其元素是 `{key_code, local_code}`（日志 `[%04d]: key_code = 0x%08X, local_code = 0x%08X` @0x1011327）。
- 因此 `0x00000000` 这类数字是**运行期配置**，静态镜像里搜不到 MENU/UP/DOWN 的数值。
- 已确认的间接证据：`[INFRADIAL] ret = %d, local_key_code = 0x%08x`、`[INFRAINPUT] received … SETKEYINH (key_code=…)`
  —— 全部是"运行期取到的 key_code"。
- 唯一"命名空间"线索：TP 发送路径里出现 `mov.w r1,#0x0F000000`（0x859140）作为参数，
  **推测** 是 TP/输入事件 ID 的高字节域。

### 6.2 `infra_tp_key_emulation.txt`：9 个"模拟键"（**最有价值的注入面**）

`InfraTp` 构造函数（exidx 边界 0x8578AC 起、实际 ctor 约 0x857A30–0x8582B8）里：

```
8580e4  mov r0,r7 ; mov.w r1,#256 ; mov r2,r8 ; blx fgets(buf, 0x100, fp)
8580f8  mov r0,r7 ; movs r1,#0 ; mov r2,r1 ; blx strtol(line, NULL, 0)   ; ★ base=0（支持 0x… / 十进制）
858100  ldr r3,[pc] ; add r3,pc → base
858104  str r0,[r3, r6]                        ; table[i] = 值
858106  adds r6,#4 ; cmp r6,#36 ; bne loop     ; ★ 36/4 = 9 项
8582b2  mov r0,r8 ; blx fclose(fp)
```

- 文件路径字符串：`/usr/share/appfw_infra/infra_tp_key_emulation.txt` @0x100EC17（**该目录在固件中不存在 → 当前是死代码**）。
- 打开失败时只打日志继续（不 abort），所以**文件存在与否只影响这 9 个模拟键**。
- 9 项表的打印：`[INFRATP] key_emulation[%3d] = 0x%08X` @0x100EC77；
  换算坐标时打印：`[INFRATP]%s, key_emulation[%3d] (x, y) = (%3d, %3d)` @0x100F0EB。
- 文件格式（实测代码）：**最多 9 行，每行一个整数，`strtol(...,0)` 解析**（`0x` 前缀=十六进制），
  多余行忽略，缺失行保持 0。
- 值的语义有两种可能（**未定，需实测**）：(a) 9 个虚拟键的 key_code；(b) 打包坐标 `x<<16|y`。
  倾向 (b)：因为日志紧接着打印 `(x, y)`，且 TP 事件路径里有 `orr r3, r3, r2, lsl #16` 的坐标拼装
  （0x858F7A / 0x858F84），说明该模块习惯把两个 16 位量拼成 32 位。

### 6.3 iLog 录制/回放格式（把按键序列变成文件）

字符串证据（libObj）：

| 字符串 | VA | 含义 |
|---|---|---|
| `/tmp/appfw_infra/ilog_data_%010d.bin` | 0x101388E | 日志文件 |
| `[INFRAINPUT] header->` / `mark = %c%c%c%c` | 0x10118A9/0x10118BF | 4 字节 magic |

即：存在一条**官方的"按键事件录制 → 回放"通道**，文件里存的就是 `key_code/sub_key_code/status/ex_info/sub_id`。

## 七、两种注入方案评估

### 方案 A：客户机进程内调用导出函数投递事件（**推荐**）

**A1（推荐）复现物理键路径：`createEvent` + `pushFilterEvent`**

```c
// LD_PRELOAD 的 .so 里，延迟到 UI 起来之后执行（例如 hook 住某个已知初始化函数，或定时器轮询）
typedef void* (*createEvent_t)(void* self, unsigned long id, unsigned char dest);
typedef void  (*pushFilterEvent_t)(void* self, void* ev);
typedef void  (*addParameter_t)(void* ev, unsigned long pid, void* param);

void inject(unsigned long eventId) {
    void** pInst = (void**)dlsym(RTLD_DEFAULT, "_ZN12InputService13m_pMyInstanceE");
    void*  svc   = *pInst;                                   // 单例
    createEvent_t create = dlsym(RTLD_DEFAULT, "_ZN12InputService11createEventEmh");
    pushFilterEvent_t push = dlsym(RTLD_DEFAULT, "_ZN12InputService15pushFilterEventEP5Event");
    void* ev = create(svc, eventId, 4);                      // dest=4，与物理键一致
    push(svc, ev);                                           // 进入事件总线
}
```

- **可行性：高。** 所需符号全部是 libObj 的 `GLOBAL DEFAULT` 导出；单例指针是导出数据对象；
  `Event` 只用 `new(16)`，没有隐藏依赖；且项目已有 `/etc/ld.so.preload`（真机采集到 20 字节）证明
  preload 在本机可用。
- **前提**：`eventId` 必须是目标 View 认得的 ID。取法三选一：
  1. 在真机/模拟器上对 `InputService::createEvent`(0x3CFAEA) 下断点，按一次 MENU，读 `r1` → 得到真实 ID
     （最可靠，工作量最小，但需要运行环境）；
  2. 静态反查菜单 View 的 `attachEventId` / 触发器表（`ViewBase::transformByTriggerTable` 0x3EBE3C
     的数据源 `.data.rel.ro`），或 `share/app/*.uxc` 布局里的 event id 表（需另开工，未见现成表）；
  3. 绕过键：用 A2 的 TP 事件或 `dest=0` 路径。
- **风险**：跳过 `InfraInput` 的"键抑制/重复/朝向"判定（0x3D2D1C 的 isDest==0 分支），
  可能与物理键状态机不一致；对"打开菜单"这种一次性动作影响很小。
- **注意**：`pushFilterEvent` 需要 `InputService` 已构造完成（`m_pMyInstance != NULL`）；
  过早调用会崩，必须做空指针与时机保护。

**A2 更上层：`View::pushEvent(Event*)` / `AppWidgetBase::pushEvent(ulong, ParamList*)`**

- 0x841334 `bool View::pushEvent(Event*)`、0x3FEB78 `AppWidgetBase::pushEvent(ulong, ParamList*)`。
- 适合"直接触发菜单动作"而不模拟按键；但同样需要该动作对应的 event id，且需要能拿到
  当前 View/Widget 实例（`m_pMyInstance` 只覆盖 InputService）。
- **可行性：中**（缺实例获取路径），优先级低于 A1。

### 方案 B：uipc/数据层注入

| 变体 | 做法 | 可行性 | 阻碍 |
|---|---|---|---|
| **B1** 伪造 uipc 事件记录 | 向 InfraInput 队列发 `{command,size,params[]}` | **低** | 5.2 的 10 条命令都是控制类，**没有"投递事件"的命令字**；事件是"回调/osal 直发"，不在 uipc 记录层 |
| **B2** 走 test-cmd 通道发 `INFRA_INPUT_TEST_CMD_CB_SEND_EVENT` | 需要 testcmd 报文封装（libtestcmd + sen.elf/`/bin/testcmd.elf`） | **中** | 封装格式未逆（另一并行任务）；且要 key_code |
| **B3** 写 `infra_tp_key_emulation.txt` | 造 `/usr/share/appfw_infra/` + 9 行整数 | **中高**（纯数据、不改代码） | 目录/文件在固件中不存在，需重打包 usr 镜像（项目已有 `repack_a6600.py` 经验，但历史上 usr 改动曾导致启动卡住，见文档 60–63）；9 项语义待实测 |
| **B4** iLog 回放 | 造 `/tmp/appfw_infra/ilog_data_*.bin` + 触发 ILOG_PLAY(2) | **中** | 依赖 test-cmd 触发；格式已知（6.3），但 magic/`data_byte` 取值未确认 |
| **B5** 内核 kbd 字符/Proc 设备 | 向内核键盘驱动节点写一份按键报文 | **待评估**（不在本轮范围） | 另有并行任务在逆 `input.ko`/`usbg_sen.ko` 的 `kbd_init/kbd_read_proc/kbd_write_proc`（`udif_create_proc` 创建节点）；细节见 `01-文档/78-uipc协议逆向.md`。本报告的 A/B1–B4 均**不依赖**该设备 |

**B3 的报文/文件形态（最可能）**：

```
/usr/share/appfw_infra/infra_tp_key_emulation.txt
9 行，每行一个整数（strtol base=0，可用 0x 前缀），例如：
0x00000000        ← 键 0（推测=某个物理键对应的触摸坐标或 key_code）
0x00000000        ← 键 1
…（共 9 行）
```

**最可能的"按键报文"形态**（如果确实要在 uipc 层做）：
`_InfraInputEvent` 24 字节 = `{key_code, sub_key_code, status, ex_info, sub_id, reserved}`，
用 `osal_snd_sync_msg(0x014A0429, msg)` 发给输入仆人；由仆人反向调用枢纽回调。
即：**报文形态是明确的（24 字节 6 个字），但"投递"这一步不是 uipc 记录命令，而是函数回调/osal 直发**。

### 推荐

1. **首选 A1**（`createEvent`+`pushFilterEvent`），因为它完全绕开副控制器、uipc、字体等所有已知阻塞，
   且调用点就是真机物理键的必经之路，语义最干净。
2. 并行准备 **B3**（key_emulation 文件法）作为"真实按键路径"的验证手段：如果 key_emulation 的 9 个值
   确实能触发物理键等效行为，那么这条路连 event id 都不用知道。
3. **B1 不建议**（协议层没有投递命令，硬做等于自己发明协议）。
4. 无论走哪条，**第一步都建议先抓一次 `createEvent` 的 `r1`**（真机或模拟器断点），一次采集即可
   同时解决 A1 与 B2/B4 的"event id / key_code"缺口。

## 十、明确标注为推测的部分

1. **`InputServant` 是独立进程**：只由 `osal_snd_sync_msg(0x014A0429, …)` 与"同步等待"推断；
   也可能是同进程的另一个 OSAL 线程/端点。未验证。
2. **`_InfraInputEvent` 字段名**：`key_code/sub_key_code/status/ex_info/sub_id` 的顺序来自两处日志的
   打印顺序 + `createEvent(ev[0])` + `addParameter(27/28/32 ← ev[8]/[12]/[16])`；
   `+0x14` 的用途未知。字段**偏移**可信度高，**语义命名**是推测。
3. **`EventManager::push` 的 vtable 语义**：只确认"按 dest 选槽 + 调成员函数指针"，未确定 4 个 dest 的枚举含义
   （已知 0/1/3/4 出现过）。
4. **`dest=4` 的含义**：与 `createEvent(...,4)` 及"物理键走 isDest==0 分支"一致，但未与枚举定义对照。
5. **`key_emulation` 9 项值的语义**（key_code 还是打包坐标）与 `(x,y)` 的换算公式，均未实测。
6. **`0x0F000000`** 作为 TP/输入事件 ID 高字节域的猜测。
7. **MENU 是否能被"纯 UI 事件"打开**：取决于菜单 View 是否监听某个 event id（大概率是），
   未定位到该 id。
8. **与内核 `kbd_*` 驱动的关系**：副控制器的按键究竟是"经 libsencore→uipc→InfraInput"还是
   "经内核 kbd 设备→某守护进程→uipc"，两条链在 `InfraInput` 之前是否汇合，本轮**未定**
   （内核侧 `kbd_init/kbd_read_proc/kbd_write_proc` 由并行任务在逆，见 `01-文档/78-uipc协议逆向.md`）。
   但本报告的注入点（A1 的 `pushFilterEvent`、B3 的 key_emulation）位于**汇合点之后**，
   因此不受该未知影响。
