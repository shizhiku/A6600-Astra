## 问题 A · 物理键码 → UI 事件码的映射未知

### 现象

- 驱动层能确认 MENU 按下：`/proc/udm/input` 定向查询返回
  ```
  *** Getkey 0x1ac ***
  keycode:0x1ac
  value:0x1
  ```
- 但 `InputService::createEvent` 的 605 次调用中，eventId 只有
  `0x15010054`(579)、`0x17005007`(10)、`0x15070300`(10)、`0x150702c0`/`0x150700f0`/`0x150700c0`/`0x15010052`(各 1–2)

### 已知

- **`0x1AC` 是物理键码**（来自 `input.ko` 键表：ADC 端口 `0xF`、电平 `0..0x5B`）
- `libObj` 的 `InfraInput` 层**同时维护两个字段**，自带映射日志：

  ```
  [INFRAINPUT]  InfraInputKeyList event {
  [INFRAINPUT]   key_code   = 0x%08X = %10d
  [INFRAINPUT]   event_code = 0x%08X = %10d
  [INFRAINPUT]   status     = 0x%08X = %10d
  [INFRAINPUT][%3d]: key_code = 0x%08X, event_code = 0x%08X
  ```

  字符串偏移：`0x1012FB2`（映射行）、`0x1012DD3`/`0x1012DFD`（结构体 dump）
  证据：`03-证据/静态分析/input_sen/libObj.so.inventory.txt:9173-9187`

- 相关接口：`InfraInput::SetEventKeyList` / `RmEventKeyList` / `SendEventInitData`

### 未知（本条要解决的全部内容）

1. `key_code = 0x1AC` 对应的 **`event_code` 是多少？**
2. 该条目的 `status` 语义（`value:0x1` 代表按下？有效？）
3. 是否要求按下/释放的**边沿**，是否有**抑制（inhibit）**或重复（repeat）条件
4. 该条目对应的 **callback/list 是否已注册**

### 判定标准

拿到 `event_code` 后，在 `createEvent` 的 605 次命中里能观察到该值 → 本条解决；若观察不到，则问题转到 B。

### 具体做法（三选一，按可行性）

| 方式 | 做法 |
|---|---|
| A1 · 钩日志函数 | 找到打印 `[INFRAINPUT][%3d]: key_code = 0x%08X, event_code = 0x%08X` 的函数（引用字符串 `0x1012FB2`），用 `REA_BP_MEMREG` 抓其参数 |
| A2 · 读内存 | 定位 `InfraInput` 单例与 `key_list` 数组（结构体字段见上），直接 dump 出 `key_code=0x1AC` 那一项 |
| A3 · 静态表 | 在 `libObj` 的 `.data.rel.ro` 中找默认 event key list（`{key_code, event_code, ...}` 数组），静态读出映射 |

## 问题 B · 驱动是否把 MENU 发出去、发到哪一环，未定位

### 现象

- 只测了一条回调 `callback_direct`（指令地址 `0x05BB5EA6`），**一轮零命中**
- 其余四条回调**尚未测试**
- `input.ko` 的 OSAL 发送点**尚未钩取**

### 四种可能（一个都没排除）

1. 驱动**没有发送**（键表匹配 ≠ 上报）
2. 发送了但 **InfraInput 没订阅**该 key
3. 发了但被**过滤/抑制**
4. 已送达但 **UI 没消费**（例如当前提示页不接收 MENU）

### 判定标准

同一次运行内，按"按下前 / 按住 / 释放后"三个时刻，能观察到：

```
驱动发送点命中(t1) → InfraInput 接收/派发(t2) → createEvent(event_code)(t3)
```

任一环缺失即可定位。

### 断点地址表（Thumb 统一表示）

> `REA_BP_VA` 按实际 PC 比较 → 用**偶数指令入口**；作函数指针时才 +1。
> 每个地址加**当轮**确认的 load bias（第 79 轮实测 `0x057E3000`）。

| 函数 | libObj 内指令偏移 | 第 79 轮绝对地址 |
|---|---:|---:|
| `createEvent` | `0x3CFAEA` | `0x05BB2AEA` |
| `callback_direct` | `0x3D2EA6` | `0x05BB5EA6` |
| `callback_convert` | `0x3D2FB0` | `0x05BB5FB0` |
| `callback_panel` | `0x3D2C40` | `0x05BB5C40` |
| `callback_tp` | `0x3D2FC0` | `0x05BB5FC0` |
| `callback_convert_cap` | `0x3D248C` | `0x05BB548C` |
| `pushFilterEvent` | `0x3D1818` | `0x05BB4818` |

`input.ko`：模块基址 `0x5f07c000`，扫描线程 `kbd_timer_hndlr` 偏移 `0x21e4`（已确认在跑）；需静态定位其内对 `osal_snd_msg` 的调用点。

## 问题 C · 含注入器的预加载配置下黑帧，原因未隔离

### 现象

含 `libinject_menu.so` 的 `/etc/ld.so.preload` 配置下抓到黑帧；去掉预加载能画出「运行于NTSC。」。

### 已撤回

| 原说法 | 更正 |
|---|---|
| 「预加载本身破坏渲染」 | **尚未证实** |
| 「不是注入动作导致」 | **未排除**——声称"不注入"的对照组实际仍注入（`REA_INJ_DELAY` 设在宿主环境，客户机读不到，默认 `alarm(20)`） |
| 「不是注入器崩溃」 | **未排除** |

### 已知混杂因素

注入器在 **SIGALRM 处理函数**里做 stdio/加锁并调用 UI API —— 不符合异步信号安全。

### 判定标准

**空 DSO 对照**三组，同 vsync 抓帧：

| 组 | 预加载内容 | 期望 |
|---|---|---|
| C0 | 无 | 正常画面 |
| C1 | **完全空 DSO**（无构造函数动作/信号/线程/UI 调用） | 若正常 → 预加载无害 |
| C2 | 注入器 | 若黑 → 是注入器而非预加载 |

### 具体做法

```c
/* empty.c —— 只含一个无关符号，无构造函数 */
int rea_empty_marker = 1;
```

```bash
arm-linux-gnueabi-gcc -shared -fPIC -O2 -o libempty.so empty.c
# 放入 /tmp 分区，/etc/ld.so.preload 写 /tmp/libempty.so
```

每组跑 2 次，抓 vsync 1200/1800/2400/3000。

## 问题 D · 画面状态不可比

### 现象

同配置多次运行，同一 vsync 有时是「运行于NTSC。」、有时拍摄 OSD、有时全黑。

### 关键提醒

**单一 vsync 编号不是"应用处于同一状态"的证明。**

### 判定标准 / 做法

每次抓帧同时记录：

- 输入镜像 SHA-256、QEMU 二进制 SHA-256
- 抓帧时刻（vsync 与客户机时间）
- 当时 ch53 的 base/size、输出缓冲内容摘要

同配置连跑 3 次统计画面出现率，找可读的稳定状态判据。
