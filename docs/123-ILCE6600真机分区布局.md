## 三、对我们证据链的意义

### 3.1 F1/F3：分区几何得到真机确认

- **`nflasha15` = 307,200 KiB = 314,572,800 B = 300 MiB**，与我们 M1 镜像**完全一致**（`astra-m1-*.img` 均为 314,572,800 B）。这是第一次由真机直接证实 M1 尺寸语义正确。
- 之前 110 号报告遗留的疑点「M1 300 MiB 与 `part_image.sum` 的 size 字段 215,517,184 不一致」，现在可以解释：**300 MiB 是分区容量（307200 KiB），215,517,184 B（≈205.5 MiB）是 ext2 文件系统实际使用大小**，两者不是同一个概念，因此并不矛盾。
- `/usr` 与 `/` 均为 **`ro` 挂载**，说明原厂运行期本就不写入这两个分区 → 我们改 `/usr` 属于"替换只读内容"而非"改运行时状态"。

### 3.2 重要新事实：`/tmp` 与 `/etc` 确实共用 `nflasha10`

真机 `/proc/mounts` 直接证实了 A6400 项目文档的说法：
- 同一 `/dev/nflasha10` 同时挂载到 `/tmp` 和 `/etc`；
- 因此**任何写 `/etc` 的操作都会同时改变 `/tmp` 的内容**，反之亦然；
- 这也意味着「写 `/etc` 开机钩子」的风险面比想象更大（一个 inode 空间被两处共享）。

### 3.3 `nflasha16`（140 MiB）未挂载

- 这正是 `109` 号报告中 firmware-hunter 指出的、ZV-1M2 `firmware.tar` 里缺失的 `/android/system` 分区（同为 140 MiB）；
- 在 a6600 上它存在但**运行期不挂载**；
- 它很可能就是「某些 IMDB 表引用了但 `/usr` 里没有对应 .so」的藏身处之一 —— 值得后续只读 dump 验证。
