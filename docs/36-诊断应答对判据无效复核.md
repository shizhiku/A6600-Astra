# 36 · 诊断应答对判据无效（复核）

本轮为离线 QEMU 观测。无设备写入。

## 一、复核目的

上一轮推断：判据在等“对端帧的状态字段 == 4”，编码为 `0x40`。诊断性 ch0 应答钩子（`REA_CH0_REPLY=1`）会把接收缓冲第 3 字节改写为 `0x40`。

本轮复核：启用钩子后，**重试时刻读取的对象**是否真的变成 `0x40`，以及故障是否消失。

## 二、结果：故障现象完全不变

启用钩子运行，故障现场与未启用时逐项一致：

| 项目 | 未启用 | 启用钩子 |
|---|---|---|
| 故障时间 | 2.5614 s | 2.5618 s |
| 故障 PC | `0x63858ADC` | `0x63858ADC` |
| LR | `osal_snd_msg+0x150` | 相同 |
| r7（状态结构） | `0x6444E510` | 相同 |
| r6（模块基址） | `0x645DF53C` | 相同 |
| r5 / r3 | `0` / `0` | 相同 |

**应答钩子没有改变故障现场。**

## 三、解释

钩子的作用点在 SIO 从设备传输回调，而固件实际读取的是 **FIFO 寄存器窗口**（`0xF2405104` 起）的内容——驱动把 TX 数据写进去，没有对端消费，读回的就是 TX。钩子改写的缓冲区随后会被驱动自身的 TX 写入覆盖，因此**传不到判据所在的缓冲**。

这与之前观察一致：钩子确实改变了某些 memcpy 的落点内容（能看到 `39 0A FF 40`），但那不是重试采样的那一份。

## 四、观测工具问题（需修正）

本轮两次尝试在 `0x638615DE`（重试计数写入点）设序列断点采集，均以 `TimeoutError` 结束且 `sequence_events` 为 0；但同一地址此前能正常命中。

同一运行内故障照常发生（说明该代码确实执行过），因此这是**断点未命中**的工具问题，不是被测行为变化。可能原因：

- 序列模式的“撤断点→单步→重装”流程在该热点地址上与 QEMU 的断点复用存在竞争；
- 或该次运行中进程地址空间切换导致 Z1 断点落在未生效的 ASID。

下一轮需先用未加钩子的基线复测该断点是否稳定，再决定是否改用其它采集手段。

## 五、结论

1. **“改写接收缓冲即可让判据成立”的路走不通**：钩子的修改到不了判据缓冲。
2. 要影响判据，必须让**驱动读到的 FIFO 内容**改变，即在 SIO 模型层面把 RX 数据真正喂进去（而不是改从设备回调缓冲）。
3. 因此下一步应改为：在 SIO 模型中实现“**RX 数据源**”，让 `0xF2405100` 窗口的读取返回对端数据，而不是 TX 残留。

## 六、下一步

1. 在 `cxd90014_sio.c` 中为 ch0 增加接收数据源（可先用寄存器值来源标记，验证通路是否打通）。
2. 打通后再讨论应答内容的语义（仍需回到“解析 0x0D 类帧”的静态分析）。
3. 修好序列断点的命中问题，否则后续观测不可靠。
