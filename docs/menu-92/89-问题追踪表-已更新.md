## 二、关键新事实：物理键码与逻辑事件码是两个字段

`libObj` 内 `InfraInput` 层同时维护两个字段，并自带映射日志：

```
[INFRAINPUT]  InfraInputKeyList event {
[INFRAINPUT]   key_code   = 0x%08X = %10d
[INFRAINPUT]   event_code = 0x%08X = %10d
[INFRAINPUT]   status     = 0x%08X = %10d
...
[INFRAINPUT][%3d]: key_code = 0x%08X, event_code = 0x%08X
```

字符串偏移：`0x1012DD3`、`0x1012DFD`、`0x1012FB2`（证据：`03-证据/静态分析/input_sen/libObj.so.inventory.txt` 第 9173–9187 行）。

相关接口：`InfraInput::SetEventKeyList`、`RmEventKeyList`、`SendEventInitData`，另有回调表、抑制/重复状态。

**因此：**
- `0x1AC` 是**物理** MENU 键码（`get 0x1ac` 已证实）
- 但它**不一定**是传入 `InputService::createEvent` 的逻辑 `eventId`
- createEvent 里观察到的 `0x15010054` 等高位值**不能**因为"不等于 0x1AC"就判为 MENU 丢失，也**不能**反推其中某个就是 MENU

### 问题 2 · 物理 MENU 已验证，逻辑事件映射与分发位置待确认

| 项 | 内容 |
|---|---|
| **现象** | 驱动识别 MENU（`get 0x1ac`），但未观察到它派发到 UI |
| **状态** | 待定位范围：未发送 / 未订阅 / 被过滤 / 已送达但未消费 |
| **严重度** | 🔴 高 |

**已确认**

- 注入 ADC 通道 3 = `0x20` 并保持
- 模型日志 `[ADCRD] ch=3 val=0x0020`、`adc` 模式 `Ch1:Port 3 0020` → 驱动读到值
- **`get 0x1ac` 返回 `keycode:0x1ac`、`value:0x1`** → 物理键码匹配成功
- 扫描线程 `kbd_timer_hndlr` 断点持续命中

**已观察**

- `createEvent`（指令地址 `0x05BB2AEA`）命中 **605 次**，eventId 取值：`0x15010054`×579、`0x17005007`×10、`0x15070300`×10、其余各 1–2
- `callback_direct`（指令地址 `0x05BB5EA6`）**本轮零命中**
- 其余回调（`callback_convert` / `convert_cap` / `panel` / `tp`）**尚未测试**

> 措辞更正：以上只说明"**本轮未观察到 callback_direct 命中**"，不能推广为"所有 callback 都未收到"。

**下一步（按价值排序）**

1. **取得 `InfraInputKeyList` 中 `key_code=0x1AC` 那一项**，确认：对应的 `event_code`、callback/list 是否注册、所需 `status` 与按下/释放条件、抑制状态
2. 同一运行中记录**按下前 / 按住 / 释放后**三个时刻，同步采集：驱动发送点、InfraInput 接收/派发、目标逻辑 eventId，标注客户机时间
3. 钩其余回调入口（见下表地址）确认哪条被注册、哪条被调用
4. 钩 `input.ko` 的 OSAL 发送点（模块基址 `0x5f07c000`）确认驱动是否真的发出消息
