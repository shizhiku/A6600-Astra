# 08 · S2 宿主分析进展（a6600）

> 目标：把 ZVE10-Astra 那套改造"翻译"成 a6600 的具体字节操作。

---

## 1. 平台与原料（已确认）

| 项 | a6600 | ZV-1M2（源机） |
|---|---|---|
| 平台 | CXD90045（key 集 k0） | CXD90045（key 集 k8） |
| 固件 | 1.10（model `0x81030014`） | 2.01（model `0x21020010`） |
| `/usr` 镜像 | 215,517,184 B / 802 文件 | 530,345,984 B / 49,986 文件 |
| `libIMDB.so` | 33,924 B / **156 条** | 40,596 B / **185 条** |

**关键结论**：两者同属 CXD90045 世代，只有密钥集编号不同 → 库可加载，移植成立。

---

## 2. 模块表改造（已定案，3 处字节）

`libIMDB.so` 的模块表：**条目 44 字节**，字段布局：

```
+00 tag      = 0x20000004
+04 version  = 1
+08 mode     = 0xffffff9f
+12 me_psid
+16 file    （字符串偏移）
+20 init    （字符串偏移）
+24 sus / +28 res / +32 ? / +36 / +40  （其余字符串偏移）
```

**a6600 的入口条目 @ `0x70F8`**：

| 位置 | 原值 | 改为 | 作用 |
|---|---|---|---|
| `0x4CC9` 字符串 | `"testcmd_scn.so"` | `"appFwBoot.so"` | 借空闲槽（a6600 无条目引用它） |
| `0x70F8 + 12` | `0x07FB0083` | `0x00000083` | 去掉"已静态合入 libObj"标记 |
| `0x70F8 + 16` | `0x0000496F` | `0x00004CC9` | 指向新引导器 |

对照 ZV-1M2 的同名条目 @ `0x897C`：`psid=0x83`、`file→"appFwBoot.so"`，结构完全一致。

## 3. 跨代符号冲突（已扫描）

a6600 全局符号池 = 5,076（`libObj` 1,901 + `libmpr` 3,124 + 其他）。

| Gen5 库 | 导入 | 导出 | 与 a6600 冲突 |
|---|---|---|---|
| `libObj.so` → libOb5 | 688 | 569 | **490** |
| `libmpr.so` → libmp5 | 304 | 6,087 | **184** |
| `appFw.so` | 753 | 1 | **152** |
| `AdjChkConfig.so` | 180 | 194 | **95** |
| `appFwBoot.so` | 36 | 32 | **22** |
| **去重后唯一符号** | | | **683** |

**同码豁免**（两边函数字节完全相同，可跳过改名）：

- `libObj`：490 里 **127** 个同码 → 实改 **363**
- `libmpr`：184 里 **1** 个同码 → 实改 **183**

**估算实际需改名 ≈ 550 个**（ZV-E10 那次是 557）。

> `appFw.so` 只导出 1 个符号、导入 753 个 —— 它是纯消费者。它的 152 个冲突全在**导入侧**：
> 这些名字在 `RTLD_GLOBAL` 下会被 a6600 的旧实现抢走，必须在 `appFw.so` 的 `.dynstr` 里改名。

## 4. `im.elf` 补丁点（已定位 ✅）

ZV-E10 的补丁：文件偏移 `0x175E`（VA `0x975E`）`02 46` → `01 22`。
a6600 的 `im.elf` 只有 21,820 B（小型 launcher，通过 `libIMDB.so` 的
`IMDB_find_entry` / `IMDB_get_entries` 遍历模块表），`0x175E` 处不是同一指令。

### 定位方法（可复用）

抓一个**特征常量**：模块加载函数内部用 `movs r4, #0x2c` + `mla r4, r4, r5, r0`
把索引乘以 **44**（模块表条目大小）。这个特征两台机器完全一致：

```
ZV-E10  0xb91a  movs r4, #0x2c ; mla r4, r4, r5, r0     加载器 @0xb8e8
a6600   0xb61e  movs r4, #0x2c ; mla r4, r4, r5, r0     加载器 @0xb5ec
```

再找另一个特征：检查函数里的 `and r0, r0, #0x400000`（argv `'a'` 对应的标志位）：

```
ZV-E10  0xadac  ldr r3,[pc]; ldr r0,[r3,#0xc]; and r0,r0,#0x400000
a6600   0xaab0  同上
```

两处对齐后，补丁点自然浮现——**加载器调用前，把检查结果搬进 `r2` 的那条 `mov r2, r0`**：

```
a6600                                 ZV-E10
0x951c  bl 0xb5ec   加载器(msgid 5)   0x9750  bl 0xb8e8   加载器(msgid 8)
0x9522  bl 0xaab0   检查位             0x9756  bl 0xadac   检查位
0x952a  mov r2, r0  ← 补丁            0x975e  mov r2, r0  ← 补丁
0x952e  bl 0xb5ec   加载器(msgid 8)   0x9762  bl 0xb8e8   加载器(msgid 9)
```

### 结论

| 项 | a6600 |
|---|---|
| 补丁 VA | `0x952A` |
| 文件偏移 | **`0x152A`** |
| 原字节 | `02 46`（`mov r2, r0`） |
| 改为 | `01 22`（`movs r2, #1`） |
| 效果 | 让模块表第 `0x2c` 索引的入口在无 `'a'` 参数时也加载 |

> message id 差 1（a6600 5→8，ZV-E10 8→9），因为 a6600 的表少 29 条。

### `libMWF.so` 的影子继承补丁（已定位 ✅）

ZV-E10 在 VA `0x2D2AC` 把 `cbz r0`（`a0 b1`）改成 `nop`（`00 bf`）。

用 ZV-E10 的 `libMWF.so`（247,776 B）做对照，上下文逐字节一致：

```
ZV-E10  ee f7 0c ed | 06 46 | a0 b1 | 19 49 | 02 20 | 79 44 | ff f7 22 ff | 04 f1 10 03 | 28 46 | 00 93
a6600   ec f7 34 ec | 06 46 | a0 b1 | 19 49 | 02 20 | 79 44 | ff f7 22 ff | 04 f1 10 03 | 28 46 | 00 93
                      ↑mov r6  ↑补丁
```

只有第一条 `blx` 的偏移不同（本来就该不同），其余全等。

| 项 | a6600 |
|---|---|
| 补丁 VA | `0x2DD70` |
| 文件偏移 | **`0x2DD70`**（该库 `.text` 的 VA == 文件偏移） |
| 原字节 | `a0 b1`（`cbz r0`） |
| 改为 | `00 bf`（`nop`） |
| 效果 | 五代组件重复注册同一 `mgrId` 时走影子继承，而不是触发 `overlap generation!!` 断言 |

## 6. S2 交付物汇总（全部定案）

| # | 文件 | 文件偏移 | 原字节 | 新字节 | 作用 |
|---|---|---|---|---|---|
| 1 | `libIMDB.so` | `0x4CC9` | `testcmd_scn.so\0` | `appFwBoot.so\0` | 借字符串槽 |
| 2 | `libIMDB.so` | `0x70F8+12` | `83 00 FB 07` | `83 00 00 00` | 去掉静态合入标记 |
| 3 | `libIMDB.so` | `0x70F8+16` | `6F 49 00 00` | `C9 4C 00 00` | 指向 appFwBoot.so |
| 4 | `bin/im.elf` | `0x152A` | `02 46` | `01 22` | 强制加载模块表入口 |
| 5 | `lib/libMWF.so` | `0x2DD70` | `a0 b1` | `00 bf` | 影子继承，避免断言 |
| 6 | 5 个五代库 | `.dynstr` | — | 等长同哈希改名 | 解除约 550 个符号冲突 |

### 已做

- 反汇编 `.text`（4,883 条），列出全部 12 处 `mov r2, r0` 候选
- 通过 `.rel.plt` 映射出 58 个 PLT 符号，定位 `strncmp`/`putenv` 调用点

### 卡点

缺少 **ZV-E10 的 `im.elf`** 做对照。ZV-E10 2.03 的 `.exe` 是索尼 **Packman 容器**
（GUID 头 + 私有格式），不是 a6600 那种明文 UFU DAT，7z 只能取出 375 MB 的 `[0]` 载荷，
里面没有 UFU magic。

### 三条可选路径

1. **拿 ZV-E10 的 `im.elf`**：从 ZVE10-Astra 作者处要一份，或找 `Update_ZVE10V203.dmg`
   （macOS 包可能含明文 DAT）试解
2. **纯静态定位**：继续在 a6600 的 `im.elf` 里按语义找——定位"遍历 156 条表 + 检查 argv 含 'a'"
   的循环，再找把结果送进加载调用的那一步（可行，但慢）
3. **绕过它**：不依赖 `im.elf` 的自动加载，改用别的启动路径（例如让 `appFwBoot.so` 被
   `libIMDB` 直接调度，或借 `bootin.elf` 的 `preload`——但 a6600 是 warm boot，此路已实测不通）
