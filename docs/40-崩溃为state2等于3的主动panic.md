# 40 · 崩溃是「state[2]==3」的主动 panic

本轮为离线 QEMU 观测 + 本地备份解析。无设备写入。

## 一、故障点是代码故意制造的 panic

反汇编 `0x63858ADC` 周边：

```
63858abc  ldrb  r3, [r7, #2]     ; r3 = state[2]
63858abe  subs  r2, r3, #1
63858ac0  uxtb  r2, r2
63858ac2  cmp   r2, #1
63858ac4  bhi   0x63858AD0       ; state[2] 不在 {1,2} → 继续判断
...                              ; state[2] ∈ {1,2} 时走正常分支
63858ad0  cmp   r3, #3
63858ad2  bne   0x63858AE8       ; 不是 3 → 跳过
63858ad4  movs  r0, #9
63858ad6  bl    0x63D3B9C2
63858ada  movs  r3, #0
63858adc  str   r3, [r3]         ; ← 主动写空地址 = 有意的 panic
```

**结论：这不是空指针意外解引用，而是固件“检测到致命状态后主动崩溃”的设计。**

## 二、`state[2]` 的初值来自相机自己的备份属性

读取相机备份 `Backup.bin` 属性 `0x00170000`（256 字节）：

```
00 00 03 02 01 00 01 01 00 00 00 01 00 00 00 02 ...
```

即：

- `state[0] = 0x00`
- `state[1] = 0x00`
- **`state[2] = 0x03`** ← 正是触发 panic 的值
- `state[3] = 0x02`

这与 QEMU 中断点读到的状态结构 `00 00 03 02` 完全一致，来源确认。

## 三、关键：这个字节在启动过程中从未被改写

对状态结构设写监视（4 字节粒度，覆盖 `[2]`），整轮启动只捕获到**一次**写入：

```
PC = 0x60258BD0（内核地址）  VALUE = 00000302
```

即只有初始化那一次把整字写进去，此后**再没有任何代码把 `state[2]` 改成 1 或 2**。

而代码要求 `state[2] ∈ {1,2}` 才走正常分支。于是必然走到 `==3` 的 panic 分支。

## 四、因果链重新成立（并更精确）

```
初始化：state[2] = 3（来自 Backup 0x00170000）
        ↓
正常启动路径本应把 state[2] 置为 1 或 2
        ↓
本模拟中该转换从未发生
        ↓
某处代码看到 state[2]==3
        ↓
主动写空地址 → panic → 异常监视器停机
```

这也解释了上一轮观察到的矛盾：钩子若只让判据偶然成立一次，并不足以完成 `state[2]` 的状态转换，因此故障照旧。

## 五、下一步

1. **找到把 `state[2]` 置为 1/2 的代码**：它应当位于判据成功分支之后（`0x63861080` 状态机）或其它初始化路径。
2. 确认该转换依赖什么条件——若依赖 SIO 对端应答，则回到“补对端模型”；若只是本地状态推进，则可能是模拟器缺少某个初始化调用。
3. 定位后即可判断本问题的真正修复点。
