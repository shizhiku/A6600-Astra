# 58 · 中文字体来自副控制器（subsystem）通道

本轮为离线字符串分析。无设备写入。

## 一、找到引用方：`/lib/libsencore.so`

在 `/usr` 中扫描引用 `MYingHeiC-GB18030` 与 `/tmp/images` 的文件，仅 3 个：

| 文件 | 说明 |
|---|---|
| `/share/app/fontlist.dat` | 字体映射表 |
| `/share/app/global.xdb` | 全局配置数据库 |
| **`/lib/libsencore.so`** | 关键：同时含字体路径与 `/tmp/images`（6 处） |

## 二、`libsencore.so` 是什么

其字符串上下文非常明确：

```
[send]osal_snd_msg() error:%d
[recv]osal_rcv_msg_tmo() error:%d
Receive Pkt Err : resCode=0x%x, Adrs=0x%x, DataSize=0x%x
Error - Trans(to Subsystem) size 0x%X is larger ...
mmap Failed ( ADRS=0x%08X, SIZE=%u )
libSnr.so
BEF_SONAR_CALL / AFT_SONAR_CALL
FileNotFound
```

即：**它是与「Subsystem」（副控制器）通信的库**，通过 osal 消息收发数据包，并带 `FileNotFound` 之类的文件请求语义。

紧邻这些通信字符串的就是字体路径清单：

```
/tmp/images/MYingHeiC-Big5HKSCS-SJ_wIcon.ltt
/tmp/images/MYingHeiC-Big5-SJ_wIcon.ltt
/tmp/images/MYingHeiC-GB18030-SJ_wIcon.ltt
/tmp/images/MYingHeiC-GB2312-SJ_wIcon.ltt
/tmp/images/UniversOTS-SJ_wIcon.ltt
/tmp/images/Sony_DI_Icons.ttf
```

## 三、结论：字体由副控制器提供

结合此前事实：

- 固件 `/usr` 里只有 Univers / Heisei / KSX1001 三种 `.ltt`，**没有中文 GB18030/Big5**；
- `fontlist.dat` 把中文指向 `/tmp/images/`；
- 负责把文件放进 `/tmp/images` 的是 `libsencore.so`，它通过 **Subsystem 通道**取数据。

**即：中文字体存放在副控制器侧，主控在运行时向它请求并写入 `/tmp/images`。**

## 四、统一了两个阻塞点

这与之前的 av-cam 等待问题**同源**：

| 现象 | 根因 |
|---|---|
| av-cam 等待 SIO 帧状态 | 副控制器通道未建模 |
| 中文字体加载失败 → UI abort | 副控制器通道未建模（取不到字体） |

模拟器目前只对 **ch3** 做了副控制器帧回放（`submicro-frames`），且只回放固定 384 字节，**没有文件传输能力**。

## 五、两条可行路径

### 路径 A：把字体直接预置到 `/tmp/images`（绕过通道）

若能从相机把中文 `.ltt` 取出来，直接写进模拟器 initrd 的 `/tmp/images/`，即可跳过该通道。

- 需要：相机在线，读取 `/tmp/images/MYingHeiC-GB18030-SJ_wIcon.ltt`（运行时该目录应存在）；
- 代价低、见效快，属于**模拟环境搭建**而非改固件。

### 路径 B：建模副控制器的文件传输协议

- 需要逆向 `libsencore.so` 的包格式（`Receive Pkt Err` 等提示了字段：resCode/Adrs/DataSize、0x300 字节分片）；
- 工作量大，但能同时解决 av-cam 等待问题。

建议先做 A 验证“UI 是否只因字体而中止”，再决定是否投入 B。
