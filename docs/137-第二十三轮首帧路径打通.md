# 137 · 第二十三轮：首帧路径已打通到 drawFramebuffer 调用点

> 时间：2026-11-22。离线 QEMU。**本轮取得实质性突破**：fbrm 补丁验证生效，帧函数与 draw 调用点均首次命中。

## 一、上一轮"环境回归"确认为实验纪律问题（已修复）

之前 6 次失败都是因为**漏加栈扩容 preload**。五代 init 栈帧 ≈3.4 MiB，超过 glibc 默认 2 MiB 线程栈，`THREAD_APP` 撞上 PROT_NONE guard page（`08249000-0824a000 ---p`）。

**此后所有运行必须带 `--preload 04-产物/libcrashtrace.so`（含 6 MiB 栈扩容）。**

## 三、门控值证据（说明补丁为什么有效）

探针点：
- `G1 0x54FA40` `cmp r0,#2` — `0x54F2CA()` 状态分类
- `G2 0x54FA6C` — 64 位时间差 vs `0x62F4` 阈值
- `G3 0x54FA7A` `cmp r0,#0` — `0x54F2AE()` 门控结果
- `G4 0x54FAA4` `cmp.w r8,#0` — 状态复核

| 探针 | 未打补丁 | 已打补丁 |
|---|---|---|
| `G1 r0` | `0x0`（≠2，不跳过） | `0x0` |
| `G2 r0=0x62f4, r2=0x123b5` | `0x62f4 < 0x123b5` → 不跳过 | `0x62f4 < 0x169ef` → 不跳过 |
| **`G3 r0`** | **`0x0`（门控失败）** | **`0x1`（门控通过）** |
| **`G3 r3`** | **`0xFFFFD8F1`（fbrm 未完成）** | **`0x0`（成功）** |
| **`G4`** | ✗ 未命中 | **✅ 命中** |

**`r3=0xFFFFD8F1` 正是 `GRM_fbrmCheckUpdateFinished` 的"未完成"返回值。补丁后变为 0，门控 `0x54F2AE` 从返回 0 变为返回 1，绘制段被放行。**

这完整证实了文档 136 的分析：
```
0x54FA76  bl 0x54F2AE
0x54FA7A  cmp r0, #0
0x54FA7C  beq 0x54FAE6      <- gate==0 跳过绘制
```

## 四、跨代绑定假设已被静态排除

| 库 | `GRM_fbrmCheckUpdateFinished` |
|---|---|
| 五代 `appFw` | **IMPORT（undefined）** |
| 五代 `a5bObj` | **DEFINED** `0x115619`，size 24 |
| **四代 a6600 `libObj`（20,889,004 B）** | **符号根本不存在** |

**四代库没有这个符号**，所以不存在"绑定到四代实现"的问题。五代 `a5bObj` 是唯一实现，我们的补丁必然被使用（运行时 `r3` 从 `0xFFFFD8F1` 变为 `0` 也直接印证）。

## 六、当前剩余缺口

`C_draw_call` 命中（调用点到达），但：

- `[DMPCOUNT] draw=0` —— 没有 P3D draw kick
- `ch53 still 0` —— 显示通道仍未编程
- 无帧

也就是说：**`drawFramebuffer` 被调用了，但它内部没有产生 GPU 命令。**

这是下一层的独立问题，需要按文档 136 第 7 节第 4-7 步继续：
1. 读 `drawFramebuffer` GOT 槽的**运行时实际值**，确认绑定到五代 `libObj+0xE565A`；
2. 记录 `UXEngine::gfxeng()` 返回的 `this` 与 vptr；
3. 追踪 `drawFramebuffer` 内部（`libObj+0xE565A`）是否走到 `gemini` 绘制/提交；
4. 检查 `/dev/dmpgles2` 的 open/ioctl/mmap 是否成功。
