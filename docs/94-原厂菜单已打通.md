## 二、两处关键修正（我方此前判断有误）

### 2.1 MENU 是 `0x1AB`，`0x1AC` 是 ENTER

此前（我方 84a/89/91/93 与协作者早期复核）都写 `MENU=0x1AC`，**错误**。

键表行结构是 `{code, name_pointer}`，不是 `{name_pointer, following_code}`：

| 原厂物理键 | physical code | 逻辑基码 | 按下 | 释放 | 重复 |
|---|---:|---:|---:|---:|---:|
| **MENU** | `0x1AB` | `0x15010100` | `0x15010102` | `0x15010101` | `0x15010104` |
| **ENTER/中心确认** | `0x1AC` | `0x15010050` | `0x15010052` | `0x15010051` | `0x15010054` |

libObj 中的原始项：

- `0x13E8924 = {0x1AB, 0x01014593}` → `KEY_TACT_MENU`（VA `0x13F0924`）
- `0x13E892C = {0x1AC, 0x010145A1}` → `KEY_TACT_ENTER`（VA `0x13F092C`）

产品默认表在 `viewUnified2`（不是 libObj）：

- MENU：文件 `0x9580FC`、VA `0x9600FC`，原始 12 字节 `ab010000000101 15feffff7f`
- ENTER：文件 `0x957FA0`、VA `0x95FFA0`，原始 12 字节 `ac010000500001 15feffff7f`

**这解释了此前"605 次 createEvent 里 0x15010054×579 / 0x15010052"——那不是无关事件，正是 ENTER 的重复/按下链。当时按 `0x1AC` 去比对，方向本身是对的，只是以为它是 MENU。**

### 2.2 NTSC 提示需要 ENTER 确认，MENU 不能替代

「运行于NTSC。」由 `ViewCaution` 消费：

```
ActionNtscCaution → caution trigger 0x089E
→ 资源类型1 → ViewCaution state3
→ 接收 ENTER 功能按下 0x15010052
→ local event 3 → action 10 → 清除当前 caution trigger
```

MENU 不产生这条确认分支。**正确顺序：先按 ENTER 并释放 → 提示退出 → 再按 MENU 并释放。**

## 三、两种可复现解法

### 解法一：纯硬件注入（推荐，无需 LD_PRELOAD）

机器属性保持已验证配置：

```
-M sony-a6400,rear-controls=on,submicro-frames=<384B 回放文件>
```

注入参数（客户机虚拟毫秒，非宿主墙钟）：

```
REA_ADC_SEQ=3:32        # 第二 ADC 单元 ch3 短按 ENTER（不设 HOLD，短按后释放）
REA_ADC_T0=12000
REA_FRONT_BTN=4,0,0,4   # 前面板 bit2 才是真 MENU
REA_FRONT_T0=25000      # 25s 按一次、40s 再按一次
```

每槽 5 秒、前 1.5 秒按下。序列 = 先 ENTER 确认提示 → 25s MENU 开菜单 → 40s MENU 关菜单。

### 解法二：普通 pthread 调用原厂 `callback_convert`

- 不用 SIGALRM
- 显式链接旧 `pthread_create@GLIBC_2.4` / `pthread_detach@GLIBC_2.4`
- 构造函数只在 `im.elf` 中建 worker；worker 等 libObj 与 InputService 就绪后动态读当轮 load bias
- 调用原厂 `callback_convert`（指令偏移 `0x3D2FB0`，Thumb 指针 `load_bias+0x3D2FB1`）

最小 ABI：

```c
struct InputEvent24 {
    uint32_t logical_base, sub, status, prev_status, ex_info, repeat_count;
};
// MENU 按下：{0x15010100, 0, 1, 0, 0, 0}
// MENU 释放：{0x15010100, 0, 0, 1, 0, 0}
callback_convert(0, &event);
```

ENTER 用 `0x15010050`。**不应**向 `callback_direct` 直接传物理码 `0x1AB/0x1AC`。

## 四、驱动发送合同（已定位，供参考）

```
input.ko .text+0xC40:
  r0 = qid 0x007A0020
  r1 → 16 字节 { physical_key, 0, value/status, aux }
  消息前 4 字节 = 0x00410025
  .text+0xC44 返回 r0=0 表示发送成功
```

MENU 走 **front 6000 bit2** 路径（不经 ADC），经去抖、pending 后进入该包装器。

## 五、对照结论（预加载争议正式关闭）

| 条件 | 独立次数 | 结果 |
|---|---:|---|
| 无预加载 | 2 | 各 6 帧均为同一 NTSC 提示 |
| 完全空 DSO | 2 | 各 6 帧与基线 NTSC 哈希一致 |
| 旧 SIGALRM v7 | 2 | 各 6 帧仍为 NTSC 提示，未开菜单 |
| 正确普通线程注入 | 2 | 均在 vsync 1800 捕获相同原厂菜单 |
| 无预加载 + 纯 ADC/front 输入 | 2 | 均在 vsync 1800/2400 捕获相同原厂菜单 |

**"多加载一个 DSO 必然导致黑屏"的过强判断被否定。** 但也不能推出"任意 DSO / 任意信号处理里调 UI 都安全"。
