# 51 · 回溯 abort 调用者：两次尝试未成功，需条件断点

本轮为离线 QEMU 实验。无设备写入。

## 一、尝试 1：在崩溃时刻读栈

对 `0x041CC796` 下断并读取 `sp` 处 512 字节。

结果读到的地址是 `0x5EFFFxxx` 区间——这是**内核栈**，不是用户栈（此前崩溃现场用户栈为 `0x12201014`）。

原因：`0x041CC796` 是所有进程共用的 **syscall 桩**，断点命中的**第一次调用**并非 abort 那次（可能是动态链接器或其它进程的早期调用）。

## 二、尝试 2：多点采样后筛选

改为在同一个桩上连续采样 40 次，期望其中出现 `r2 == 6`（SIGABRT）的那次。

结果：该运行以 `status: error`、`sequence_events` 为 0 结束（未取得有效数据）。

## 三、结论：需要条件断点支持

问题本质：目标事件是**特定一次 syscall 调用**（`tgkill(_, _, 6)`），而断点地址被成百上千次无关调用共享。

现有观察器只能“命中即停”，因此：

- 要么被无关调用淹没；
- 要么计数被无关调用耗尽。

**需要给观察器加条件过滤**：命中后先比较指定寄存器的值，不匹配则直接继续、不计入事件。只有匹配时才记录并停止。

## 四、下一步（具体实现点）

在 `qemu_fault_breakpoint.py` 的序列（sequence）分支中加入：

```
--seq-filter-reg  R      # 例如 2 (r2)
--seq-filter-value V     # 例如 6
```

逻辑：`c` 命中 → 读寄存器 → **若不匹配**：重新装回断点并直接 `continue`，不记录、不占用计数；**若匹配**：按现有流程记录。

这样即可稳定捕获 `tgkill(_, _, 6)` 那一次，并读取其调用者栈与寄存器。

## 五、当前已知事实（不变）

- 应用通过 `raise(SIGABRT)`（`tgkill(0, tid, 6)`）自我终止；
- `lr` 指向相机 libc 的 `raise` 内部（偏移 `0x24D8F`）；
- Sony 监视器把信号 6 渲染成 “Illeagle Instruction”，措辞有误导性。
