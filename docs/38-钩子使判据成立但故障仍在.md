# 38 · 钩子使判据至少成立一次，但故障仍在

本轮为离线 QEMU 观测。无设备写入。

## 一、上一轮被忽略的关键数据

启用 ch0 诊断应答（`REA_CH0_REPLY=1`）后，在重试例程入口 `0x63861584` 采样到：

```
对象 0x640E46A0 = 39 0D 00 40      → [obj+3] = 0x40
global 0x644C4E43 = 04 00 00 02    → global   = 0x04
```

代入判据：

```
r5 = (0x40 ^ (0x04 << 4)) & 0x7F = (0x40 ^ 0x40) & 0x7F = 0
```

**即该次采样判据成立（r5 == 0）**，应走“清零并继续”的成功分支。

对照：未启用钩子时同一位置为 `39 0D 00 04` → `r5 = 0x44`，必然走累加。

## 二、但故障依然存在，且现场完全相同

| 项目 | 无钩子 | 有钩子 |
|---|---|---|
| [obj+3] | `0x04` | **`0x40`** |
| 判据 r5 | `0x44` | **`0`** |
| 故障时间 | 2.5614 s | 2.5618 s |
| 故障 PC | `0x63858ADC` | 相同 |
| 故障时 r7/r6/r5/r3 | `0x6444E510`/`0x645DF53C`/`0`/`0` | 完全相同 |

## 三、这意味着什么（重要）

此前链条是：**判据超时 → 写状态 7 → 发消息 0x3A → 空写故障**。

现在判据至少有一次成立，故障却一模一样，说明：

1. 要么**真正触发空写的是另一次采样**（在钩子生效之前发生，或来自另一个实例）；
2. 要么**空写故障与判据结果无关**，是这条路径上另一个独立缺陷；
3. 要么存在多处相同的判据调用，钩子只影响了其中一部分。

这三种可能都需要进一步区分，不能因为“钩子让判据成立”就认为根因已解决。

## 四、下一步（区分三种可能）

1. 统计判据调用**次数**与**结果分布**（需修好序列断点，见下）。
2. 确认故障发生时是否已经计满 30 次（若未计满就崩溃，则故障与超时路径无关）。
3. 在故障点回溯调用栈，确认它是否由同一状态机分支触发。
