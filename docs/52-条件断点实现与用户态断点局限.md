# 52 · 条件断点已实现，但用户态断点跨进程不可靠

本轮为工具改进与实验。无设备写入。

## 一、工具改进：序列模式支持条件过滤

给观察器增加了：

```
--seq-filter-reg R         # 按寄存器过滤
--seq-filter-value V
```

行为：命中后先比较寄存器；**不匹配则重新装回断点直接继续**（不记录、不消耗计数）；匹配才记录。

已编译通过。

## 二、实验一：在通用 syscall 桩上过滤 `r2 == 6`

断点：`0x041CC796`（libc syscall 桩返回处），过滤 `r2 == 6`（SIGABRT）。

结果：700 秒超时，未命中。

原因明确：该地址**被每个进程的每次系统调用命中**，过滤意味着每次都要「停止→撤断点→单步→重装→继续」，开销极大，根本走不到目标时刻。

## 三、实验二：在 `raise` 入口过滤 `r0 == 6`

断点：`0x041DBD65`（相机 libc `raise` = 偏移 `0x24D65`），过滤 `r0 == 6`。

结果：500 秒超时，未命中。

这次不是开销问题（`raise` 调用很少），而是**断点没有生效**。

## 四、暴露的问题：用户态断点跨进程不可靠

QEMU gdbstub 的 `Z1`（执行断点）在启用 MMU 后需要**按当前 CPU 的页表把虚拟地址翻译成物理地址**再插入。

当目标地址属于某个用户进程（如 libc 的 `raise`）时：

- 若断点插入时**当前进程不是 im.elf**，翻译结果指向错误的物理页；
- 之后 im.elf 运行到该虚拟地址时，断点并不存在；
- 因此「偶发命中」（如 `0x041CC796` 曾命中多次）与「完全命中不到」（`raise`）并存。

这解释了此前多次 `TimeoutError`——不全是墙钟预算问题，也有断点插错位置的问题。

## 五、下一步方向

1. **改用 QEMU 内部钩子**：在 QEMU 源码里加“当 PC 等于某虚拟地址时记录并可选暂停”的逻辑，直接在每个 CPU 执行循环里比较 VA，绕开 gdbstub 的翻译问题；
2. 或**在物理地址上下断**：先算出 libc `raise` 所在物理页（需读客户机页表，或利用首次命中时记录的翻译结果）；
3. 或在目标进程启动后立刻重新下断（需要知道进程创建的时机）。

方案 1 最可靠，工作量中等（改 QEMU + 重编）。

## 六、当前已知事实（不变）

- Sony 监视器把信号 6 渲染为 “Illeagle Instruction”。
