# 72 · 决定性发现：/tmp/images 在运行期不存在

本轮为客户机内 shell 检查结果复核。无设备写入。

## 一、检查结果

在客户机 BusyBox 内执行（经串口）：

```
ls -l /tmp/images 2>&1
ls: /tmp/images: No such file or directory
```

**`/tmp/images` 在运行期不存在。**

## 二、这意味着什么

我们此前把中文字体放进 initrd 的 `/tmp/images/`（`initrd-font6`，6 MB，镜像内确认存在 1,958,432 字节文件），但启动后该目录不可见。

因此：

| 之前结论 | 修正 |
|---|---|
| “字体放进 `/tmp/images` 后 abort 位置未变 → 文件存在不足以满足加载” | **该结论无效**：文件根本没被看到。`/tmp` 在启动过程中被重挂（很可能是 tmpfs）或清空 |

## 三、与相机实际情况一致

- 相机上 `/tmp/images/` 确实存在，且里面有中文 `.ltt`（已采集 1.96 MB）；
- 但相机上该目录与文件是**运行期由副控制器传输路径创建并填充**的；
- 模拟器中该路径从未被创建。

**即：`/tmp/images` 的存在本身就是副控制器传输链路工作的副产物。** 这与第 70、71 轮的结论完全一致，并进一步强化。

## 四、唯一剩下的文件式绕行方案与其风险

若要让 UI 从文件读取字体，只能让 `fontlist.dat` 指向一个**不依赖 `/tmp`** 的位置（例如 `/usr/share/app/`），并同时把字体放进 `/usr`。

此方案此前试过（`nflasha15-font3`），但**启动会在更早阶段停滞**（无 `im.elf` 输出，eMMC 调优反复重试）。该停滞与 `fontlist.dat` 被修改相关（同尺寸只改超级块不影响启动，改文件内容则停滞），原因未查明。

## 五、结论

- 字体问题的根因不是“缺文件”，而是**副控制器 → `/tmp/images` → 注册**这条链路未工作；
- 该链路是本次移植的核心阻塞；
- 以剩余轮次无法完成该链路的逆向与实现。
