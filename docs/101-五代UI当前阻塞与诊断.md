# 101 · 五代 UI 当前阻塞与诊断（2026-11-22）

## 一、已经打通的链路

在离线镜像 `astra-m1-mwf.img` 基础上，按顺序验证：

1. **线程栈**：五代初始化函数栈帧约 3.4 MB，四代 libc 默认栈 2 MB。用 GLIBC_2.4 preload 把栈提高到 6 MB 后，`appFwBoot::Application_System_Init` 能完整返回。
2. **MWF 初始化**：五代 IMDB 在 Application 之前会调用 `libMWF.so:MWF_Init`，我们的四代 IMDB 路由跳过了它。在桥接器里先加载 `a5pFw.so` 并调用 `MWF_Init` 后，MWF 空指针崩溃消失。
3. **应用断言**：之后应用主动报 `lib::assert::notify_model_system_error(): Assertion 'false' failed`。这是应用在报告“模型/系统错误”，不是库缺失。
4. **断言绕过（诊断）**：`appFw.so` 以 `RTLD_DEEPBIND` 加载，preload 的 `__assert_fail` 抢不到 libc 的实现；改为在 preload 构造函数里直接给 libc 的 `__assert_fail` 打 `bx lr` 补丁，断言被绕过。
5. **段权限**：绕过断言后应用往自己的 `.rodata`（运行时 `0x23a1cxxx`）写数据，触发权限错误——说明五代应用默认它的模块 loader 把 code/rodata 段映射为可写。把 `a5pFw.so` 的 PT_LOAD 段改成 RWX 后，该权限错误消失，应用不再崩溃（无异常）。

## 二、当前状态

最近的运行（`m1-rwx2`）：

- `a5pFw.so` 映射为 `rwxp`；
- `appFwBoot` 入口调用并返回；
- **无异常、无崩溃**；
- 但显示控制器 ch53 一直是 0（`[VPH] ch53 still 0 at vsync 600`），没有产生任何一帧；
- 应用没有继续走到提交显示缓冲的路径。

结论：五代 UI 目前卡在**应用侧等待模型/硬件响应**。断言被绕过只是让它不再 abort，并没有让它进入正常的渲染流程。继续补符号或改权限不会解决这个问题。

## 三、为什么这符合“模型错误”的判断

- 断言函数名是 `notify_model_system_error`，由应用主动调用；
- 绕过它之后应用没有崩溃，而是静默停住，说明它原本要走的错误处理/重试路径被打断，正常路径的前置条件仍不满足；
- 显示层（ch53）从未被编程，说明问题在 UI 引擎初始化之前或之中，不在绘制/合成。

## 四、下一步建议

1. **定位 `notify_model_system_error` 的触发源**：回溯它之前的调用链和等待对象，确认缺的是 av-cam、LIRO、UPM、sensor 还是 submicro 消息。
2. **补对应模型响应**，而不是继续打补丁：目前 QEMU 对 av-cam 只提供了固件 blob，缺的可能是某条应答/心跳。
3. **仿真 Sony 模块装载器的段映射**：五代应用明显假设 code/rodata 可写（RWX）。长期方案是在加载器层面模拟这一行为，而不是逐个改 ELF 段标志。
4. **保留诊断补丁为可选开关**：栈放大、libc 断言绕过、RWX 段都只应存在于“诊断镜像”，不能进入最终的常规运行路径。

## 五、边界

- 本轮的断言绕过、RWX 段修改都是**离线诊断手段**，不代表正确修复；
- 没有连接或写入真机；
- 五代 UI 仍未渲染出画面，原厂 UI 的交互演示不受影响。
