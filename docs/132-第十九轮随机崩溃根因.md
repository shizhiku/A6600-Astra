# 132 · 第十九轮：找到约 12% 运行随机崩溃的真正原因

> 时间：2026-11-22。纯离线 QEMU 分析。

## 一、统计事实

161 次 ASTRA 运行中，**19 次（≈11.8%）**出现 `im.elf` 找不到 / 进入 exception monitor。

这解释了此前所有"探针结果不一致"的现象 —— 不是阻塞点漂移，而是**约 1/8 的运行从一开始就崩了**。

## 三、关键判读

### 3.1 `file not found: im.elf` 是诊断信息，不是根因

`im.elf` 在真机/QEMU 里映射于 `0x8000-0xd000`。崩溃点 `pc=0x04217210` 位于：

- `ld-2.11.2.so`：`0x04000000-0x04018000`
- 崩溃 pc `0x04217210` 超出该段，落在 `libstdc++` 等后续库区域附近

exception monitor 想报告"崩溃在哪个模块"，但查表失败，于是打印了 `file not found`。**所以这是诊断失败，不是崩溃原因。**

### 3.2 真正的错误：USR 模式 ARM 执行异常

`cpsr = 0x80000010` → Thumb=off（ARM 模式）、USR 模式、IRQ/FIQ 开启。`pc=0x04217210` 触发异常通常意味着：

- 跳到了未映射/无执行权限的地址；
- 或访问了非法地址导致的取指异常。

### 3.3 `/tmp/shared.ryEXGA (deleted)` 是重要线索

这个文件已删除但仍在被引用，说明：

- 动态链接器（`ld.so`）或某些库打开了一个 tmpfs 上的共享文件；
- 该文件被删除后，仍有代码尝试访问它；
- 这是**典型的多进程/多实例共享内存生命周期问题**。

在我们环境里，`/tmp` 是 tmpfs，且每个 QEMU 实例的 overlay 是新建的。**如果 guest 内部有跨进程共享（im.elf 与子进程间的 `/tmp/shared.*`），而某个进程先退出了，就可能留下这种 dangling 引用。**

## 四、修复方向（按可行性排序）

| # | 方向 | 具体做法 | 预期 |
|---|---|---|---|
| 1 | **降低并发/延后启动** | 让 `bridge7` 的 init 与 `appFwBoot` 之间加延迟，避免多线程同时访问 `/tmp/shared.*` | 可能显著降低崩溃率 |
| 2 | **给 `im.elf` 的异常加定位** | 用 `libcrashtrace.so`（已有）捕获 SIGSEGV，打印真实 pc/lr/模块，替代 exception monitor | 拿到第一次崩溃的准确位置 |
| 3 | **检查 tmpfs `/tmp` 容量** | 真机 `/tmp_bt` 是 `size=1024k` tmpfs；我们 QEMU 里是否给了 `/tmp`？若 `/tmp` 落在 overlay 上可能行为不同 | 消除环境差异 |
| 4 | **重复运行取多数结果** | 既然只有 88% 稳定，任何实验都跑 3 次取一致结果 | 避免被随机崩溃误导（**必须做**） |

## 五、立即要做的两件事

1. **给所有后续实验加"3 次重复 + 只接受一致结果"的规则**；
2. **用 `libcrashtrace.so` 跑一次，抓这次崩溃的真实 pc/lr**（exception monitor 的诊断信息不可靠）。
