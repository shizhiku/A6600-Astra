# 81 · 四问复核：sen 不是当前最短路径，MENU 可直接注入

> 2026-11-21，纯离线静态分析；未运行或修改真机。eMMC 问题已由现有补丁解决，本报告不再讨论。

## 结论摘要

1. **目前没有证据证明 UI 第一帧在等 sen 的 `SYSTEM_STATE_READY`。** `/dev/uipc` 是通用 OSAL IPC，不是副控制器物理协议；`sen.elf/libsencore.so` 是 SENSER CORE/USB 子系统通信栈，不能仅凭名字等同于 UI 系统状态源。
2. 当前 nofont 实验不能证明“sen 未就绪导致不绘制”：`TextRM_loadFont` 被补成 `mov r0,#0; bx lr` 后，没有写成功路径要求的 `*outHandle`，调用者会把未初始化栈值写入全局字体 handle 槽。
3. 按键链已确认：`input.ko` 采 ADC/GPIO/front/vgrip，构造 OSAL 消息；`libObj::InfraInput` 接收并扇出；`InputService` 把 `ev->key_code` 直接作为 UI Event ID。
4. 静态键名表已找到：**`KEY_TACT_MENU = 0x000001AC`**；UP=`0x13`、LEFT=`0x20`、DOWN=`0x41`、ENTER=`0x1AD`、RIGHT=`0x1BF`、PLAY=`0x1F8`、FN=`0x7096`。
5. 字体注册不等 sen “字体就绪”回调。TextRM 在一次性初始化中从 Backup ID `0x810000` 取得字体列表路径并解析 `name/path/id/flag`；注册阶段不检查 `.ltt` 是否存在。`registerFontFaceFile(0x63E2DC)` 是另一套 ux 引擎转发 API，全 `/usr` 没有调用者，也不写 TextRM 名字链表。

## Q1 · UI 第一帧最少需要 sen 回什么？

**当前答案：未知，而且“必须先回 sen 消息”这个前提尚未成立。**

三个反证/替代解释：

- OSD ch53 与 YUV ch51 是不同层；`YUV layer still off` 不能单独证明 OSD 被门控。
- `input.ko` 可独立从 GPIO/ADC/前面板通道产生按键，不要求 UI 打开 evdev，也不要求 `libsencore` 生成按键。
- nofont 补丁伪造成功却不返回 handle：`loadFontSlot @0x647924` 在返回 0 后读取 `[sp+...]` 的 outHandle，并写到全局数组。当前值未初始化，足以破坏后续文本/布局状态。

因此，不建议先实现假想的 `SYSTEM_STATE_READY + battery`。最短判定顺序：

1. 恢复原 `TextRM_loadFont`，让 TextRM 读到完整 `fontlist.dat` 并提供中文 `.ltt`；或至少让补丁返回一个真实、已加载的 handle，不能只返回 0。
2. 等 `InputService::m_pMyInstance != NULL` 后注入 `KEY_TACT_MENU=0x1AC`。
3. 观察是否出现首次真实 draw kick。若仍无绘制，再在 View 激活/事件队列/GraphicsEngine update 处采样，而不是从 sen opcode 猜起。

## Q2 · `/dev/uipc` 如何收发？

它是 **ioctl + mmap**，不是普通 `read/write` 数据流，也不是环形 slot 协议。

初始化：

```text
open("/dev/uipc", O_RDWR)
ioctl(fd, 0x80000010, {0, ptr_to_16_byte_config})  // connect
mmap(NULL, 0x100000, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0)
```

- 共享区必须恰好 1 MiB。
- ioctl 形式固定为 `0x80000000 | opcode`，参数是一块 8 字节 `{u32 a0,u32 a1}`。
- 重要 opcode：4 send、5 sync send、7 receive、8 register callback、10 alloc message、11 free、12 dynamic id、16 connect。
- 消息分配块为 12 字节内部头 + payload；payload 最大 4096 B。
- 队列是按优先级插入的单链 head/tail，不是 ring buffer。

如果只是注入 UI，不需要自己重写 `/dev/uipc`。直接调用原 `libosal_uipc.so` 的 `osal_valloc_msg_wait/osal_snd_msg`，或在更上层调用 InputService 导出函数，工作量更小。

## Q3 · 按键路径与 MENU 注入

内核侧 `input.ko` 的完整符号/字符串证明它处理：

- `gpio_get_data_bit`
- ADC key config
- front key
- vertical grip key
- `osal_valloc_msg_wait` / `osal_snd_msg` / `osal_snd_sync_msg`

UI 侧结构：

```c
struct InfraInputEvent { // 24 B
    uint32_t key_code;     // +0x00，也直接作为 UI Event ID
    uint32_t sub_key_code; // +0x04
    uint32_t status;       // +0x08
    uint32_t ex_info;      // +0x0C
    uint32_t sub_id;       // +0x10
    uint32_t reserved;     // +0x14
};
```

最短注入点有两个：

1. **物理键等效路径**：调用导出函数
   `_ZN12InputService15callback_directEiP16_InfraInputEvent`，传 MENU 的 24 B event，先 `status=1` 再 `status=0`。
2. **直接事件总线**：取导出全局 `_ZN12InputService13m_pMyInstanceE`，调用
   `InputService::createEvent(0x1AC,4)` 再 `pushFilterEvent(event)`。

已生成诊断 preload：`04-产物/inject_menu_preload.c`。它轮询 InputService 单例，等待 View 初始化后发送 MENU press/release；若物理回调的同步转发发生阻塞，可定义 `A6600_MENU_DIRECT_EVENT` 改用直接事件路径。

键码表位于 libObj `.data.rel.ro` 约 `0x13E8898`，每项为 `{name_ptr, code}`。MENU 项在 `0x13E8928`：字符串 `KEY_TACT_MENU`，值 `0x1AC`。

## Q4 · 字体 API 三参数与真实注册时机

`ux::core::TextLayout::registerFontFaceFile(u8,char const*,u8)`：

- 只取得运行期单例的 `instance+0x30` 子对象，再调用其首个虚函数；三个参数原样透传。
- 静态上无法确定第 1/3 参数的确切语义；第 2 参数确定是路径。
- 全 `/usr` ELF 扫描没有任何导入者；libObj 内也没有直接调用者/函数指针引用。
- 它不写 TextRM 的名字链表 `0x13F64FC`，所以不能修复 `TextRM_loadFont("FONT_S_CHINESE")` 的 `-16`。

真实 TextRM 注册发生在一次性初始化 `0x54F3A0 -> 0x54E94C`：

```text
Backup_get_datasize(0x810000)
Backup_read(0x810000, path_buf)
fopen(path_buf, "r")
fallback: fopen("TEXTRM_FONT_LIST", "r")
逐行解析 name<TAB>path<TAB>id<TAB>flag
```

关键结论：

- `/tmp/images` 当时不存在**不会阻止注册**；文件存在性在后续 `TextRM_loadFont` 时才检查。
- `libsencore` 负责文件传输的可能性很高，但它不 import TextRM/TextLayout，不能触发 TextRM 注册。
- 如果运行时只看到 FONT_ICONS 节点，说明当次解析器实际打开的列表内容不完整，或观测点/链表解释有误；不是因为中文 `.ltt` 当时不存在。
- 最直接诊断点：`0x54E99A` 读 `r5` 的实际列表路径；`0x54EA46` 统计建节点次数。
