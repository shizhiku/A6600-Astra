### 1.2 方法

1. **文件系统级全量枚举**（不是推断）：ext2 分区复制到 WSL `/tmp` 后 `mount -o ro,loop` + `find`；
   vfat `/system` 同样只读挂载。得到每个分区的**全量路径清单**，再对文件名做 `libInfraInput/...` 命中统计（**符号链接也算文件名命中**，若有人用 `ln -s` 伪造过库名也会被抓到）。
2. **内容级分块扫描**：Python 以 8 MiB 块 + 64 B 重叠读取，搜索 6 个库名、`libOb5/libOb4/a5bObj/a5bFw/libSTMcmdexecute/libInfraSKD` 及 18 个 init/sus/res 符号串，记录偏移、上下文、SHA-256；不整文件载入内存。
3. **tar 全量成员**：`tar -tvf` 三个 `firmware.tar`，逐成员核对是否含独立库文件；未解分区再提取、挂载枚举。
4. **ELF 符号核验**：对所有 `.so`/可执行文件跑 `readelf -Ws`，筛选"已定义（非 UND）"的 FUNC/OBJECT 目标符号——`dlopen/dlsym` 目标必须是动态导出符号，因此该口径足够。
5. **来源核验**：对 `Downloads/BODYDATA.DAT` 只解密第 1 帧（1020 B 头，AES-ECB/CBC，硬编码偏移与团队 `decrypt_zv1m2.py` 相同），确认它就是本工作区 ZV-1M2 固件的来源；**不落盘任何解密镜像**。
6. **交叉对照**：三代原厂 `libIMDB.so` 的表条目 vs 该机型本机文件系统，量化"引用但本机没有"的比例（§五）。

不做的事：不运行 QEMU、不刷写、不修改既有镜像/脚本/文档；解包只落到 `03-证据/静态分析/firmware_search/` 与 WSL `/tmp`（用后删除）。

## 五、为什么"没有"是正常的：三代原厂固件的交叉证据

### 5.1 三代 `libIMDB.so` 的初始化表 vs 本机文件

| 机型/代 | IMDB 大小 | 表条目 | 本机有同名独立文件 | 本机没有 |
|---|---:|---:|---:|---:|
| a6600（四代，2019） | 33,924 B | 164 | 72 | **92** |
| ZV-E10 v2.03（四代，2020 机身/2025 固件） | 37,204 B | 182 | 78 | **104** |
| ZV-1M2（五代，2023） | 40,596 B | 192 | 74 | **118** |

- a6600 的表中同样引用 `libInfraInput.so`、`libCoreSync.so`、`libgrm.so`、`libDDS.so`、`libuxengine.so`，
  且 a6600 固件里同样**没有**这些文件——但 a6600 原厂可正常开机（本工作区此前已多轮验证）。
- ZV-E10 v2.03 的表中引用**全部六库**（含 `libgpe.so`/`GpeInit`），ZV-E10 固件里也**没有**任何独立文件——原厂可正常开机。
- 结论：`libIMDB` 的库名表是**跨机型/跨代超集**，"表里有引用但本机没有文件"是原厂常态；把这些名字当成
  "本机缺了文件"的判据不成立。完整差集见 `03-证据/…/imdb_refs/*_missing_libs.txt`。

### 5.2 目标符号的实际归属（`readelf -Ws`，已定义符号）

| 符号 | ZV-1M2 libObj.so | a6600 libObj.so | ZV-E10 libObj.so | 其他本地 ELF |
|---|---|---|---|---|
| `infra_input_init/sus/res`（+`_exit`） | ✅ 导出 | ✅ | ✅ | 无 |
| `uxengine_init`、`_sus/_res/_exit/_app_fw_init` | ✅ | ✅ | ✅ | 无 |
| `uxengine_init2` | ✅ | ❌ | ❌ | 无 |
| `grm_init/sus/res` | ✅ | ✅ | ✅ | 无 |
| `DDSUserInit/Sus/Res` | ✅ | ✅ | ✅ | 无 |
| `core_sync_set_event` | ✅ | ✅ | ✅ | 无 |
| **`GpeInit/Sus/Res`、`core_sync_user_init/sus/res`** | **❌ 未定义** | ❌（表只引用 `core_sync_*`） | **❌ 未定义** | **无** |

即：所谓"缺失库"中，
- `libInfraInput` → 符号在 `libObj.so`；
- `libuxengine` → 符号在 `libObj.so`（ZV 还多一个 `init2`）；
- `libgrm` → 符号在 `libObj.so`；
- `libDDS` → 符号在 `libObj.so`；
- `libCoreSync` → 只有 `core_sync_set_event` 在 `libObj.so`，`core_sync_user_init/sus/res` 无实现；
- `libgpe` → `GpeInit/Sus/Res` 无实现。

因此，"IMDB 列表里的符号"只有 12/18 能从 `libObj.so` 解析，另 6 个（`GpeInit/Sus/Res`、`core_sync_user_init/sus/res`）
在本机所有分区/所有 ELF 中都没有定义；但 a6600 与 ZV-E10 的原厂启动证明"缺条目"本身不致命（§5.1）。

> 交叉验证（`03-证据/.../symbols/all_elf_target_symbols.txt`）：对当前工作区 + 旧工作区全部 `.so/.elf/.bin`
> （按 ELF magic 过滤）逐个跑 `readelf -Ws`，**只有各份 `libObj.so` 副本**导出了上述 12 个 init/sus/res 符号；
> `GpeInit`、`GpeSus`、`GpeRes`、`core_sync_user_init/sus/res` 在**所有** ELF 中均无定义（只有 IMDB 字符串表引用）。

### 5.3 参考项目如何处理同一问题（本机旧工作区 repo）

旧工作区 `${WS_ROOT}/repo`（"ZV-E10 ASTRA Port"，公开复现项目，不含索尼专有固件）：

- `manifests/prod_image_manifest.json` 把 `build_out/libOb5.so` 描述为
  **"五代 UI 引擎核心 libOb5.so (3,931,624 B)"**——3,931,624 B 正是 ZV-1M2 `libObj.so` 的大小，即它只是改名后的 `libObj.so`；
- 然后创建两个**符号链接**：`/lib/libuxengine.so → libOb5.so`、`/lib/libgrm.so → libOb5.so`（`prepare_astra_qemu.sh` 同）；
- 对 `libInfraInput/libDDS/libCoreSync/libgpe` **连链接都没有**——因为它用自研 `appFwBoot` 宿主直接驱动 `libOb5.so`，绕开了五代 IMDB 初始化表
  （与 103 号文档"参考项目从 gen4 基底出发、自定义宿主"的判断一致）。

这独立佐证：**这些库名背后没有真实文件；公开项目也只能用"改名+符号链接"或"绕开 IMDB"两种办法**。

## 六、最终结论

1. **本机确实没有** `libInfraInput.so`、`libuxengine.so`、`libgrm.so`、`libgpe.so`、`libDDS.so`、`libCoreSync.so` 的真实文件（0 个），
   也没有 `libOb5.so`/`libOb4.so`/`a5b*.so` 文件；9 个分区、3 个 firmware.tar、13 GB 全量扫描、旧工作区、Downloads、WSL 实验目录均已覆盖。
2. **这不是档案缺少**：三代原厂固件本身都不发布这些独立 DSO；同名组件符号由 `/lib/libObj.so` 导出
   （ZV-1M2 的 libObj 为 3,931,624 B，SHA-256 `4cd654f1…`），IMDB 表里的库名是跨机型超集元数据。
   继续在本机找这些 `.so` 不会有收获。
3. **仍需留意的残余未知**：
   - `GpeInit`、`GpeSus`、`GpeRes`、`core_sync_user_init/sus/res` 在本地无任何实现，只作为 IMDB 字符串存在；
     ZV-E10 v2.03 同样"只引用无实现"且原厂正常，倾向属"可跳过项"，但 ZV-1M2 的 `nflasha16`（`/android/system`，140 MB，**不在 firmware.tar 内，本机没有**）
     是本机唯一未覆盖的可能载体，无法离线证伪。
   - ASTRA 当前卡点是初始化序列/ABI（见 103 号），不是缺文件。

### 建议的下一步（供 lead 决策）

1. **按 `libIMDB` 表顺序，直接调用 `libObj.so` 已导出的 init/sus/res 符号**（`infra_input_init`、`uxengine_init`/`init2`、
   `grm_init`、`DDSUserInit`、`core_sync_set_event` 等），这正是"补五代表顺序"路线的正确落点；
   可先用 `dlsym(RTLD_DEFAULT, ...)` 做一次全表可解析性检查，把"能解析/不能解析"列成表。
2. 对 `GpeInit/Sus/Res`、`core_sync_user_init/sus/res` 采取"原厂可跳过"假设并记录为残余未知；若要闭环，只能真机只读 dump `nflasha16`（不在更新包内）。
3. 若五代 IMDB 路线继续受阻，参考项目 `appFwBoot_g4host`（本机 repo 源码在旧工作区）可作为绕开 IMDB 的备选宿主路线。

## 八、边界与局限

- 只读检索；未运行 QEMU、未刷写、未修改任何既有镜像/脚本/文档；WSL 挂载副本用后即删。

- ELF 符号核验针对动态/静态符号表（`readelf -Ws`）；被完全 strip 且不从动态表导出的符号不可见——但 `dlopen/dlsym` 目标必须是
