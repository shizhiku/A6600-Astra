# 96 · ASTRA 移植任务书（v3 · 执行修订）

> 发布：2026-11-22（第 84 轮）
> 依据：`93`（黑屏真因）、`94`（原厂菜单已打通）、`95`（ASTRA 静态评估）
> 性质：本文件为当前阶段**唯一权威任务书**，替代 v1 全部内容
> v3执行修订（2026-11-22）：下列修正优先于保留的v2历史表格。原件、真机与基础emmc盘均不写入。
>
> - 任务A已用原厂/ASTRA各2次隔离对照证实：两者`/usr`均实际挂载；`dnflasha15 errno(6)`是压缩设备回退提示，不能作为挂载失败判据。ASTRA-lite当前停在应用启动/加载链。
> - 实际SDM的`/usr`分区为300MiB，205.5MiB只是现有ext2文件系统大小。M1改为不改SDM几何、文件系统扩至300MiB；M2为512MiB新副本并迁移后续分区，仅作QEMU对比。
> - 五代`/share`约197.6MiB为屏幕朗读音频；M1保留全部82.1MiB非朗读资源，不再任意删除ASTRA图片或布局；M2携带全资源。
> - “全库导出并集只缺5–6个符号”不代表实际依赖闭包；未定义弱符号默认不补stub。四/五代同名DSO必须择一或隔离，未知真实函数不得伪造成功。
> - 保留四代im及IMDB任务表，仅更改Application路由；原厂基础任务仍需四代libObj。五代私名DSO通过显式依赖边与DEEPBIND开展隔离实验，不能仅凭dlopen成功认定ABI隔离完成。
> - 当前必须补入的五代root库已实证为`libSTMcmdexecute.so`（4688B，GLIBC_2.4）；不会为此直接换用依赖ssl3/crypto3的五代im。
> - `part_image.sum`不匹配可能在分区写入后才被读回校验发现；不得视为安全的“写前拒绝”。未完成签名、接受与恢复证据前，不制作可刷结论，更不进行真机写入。
> - 任务书分工中的阶段二仅允许并行离线研究；阶段三仍须阶段一/二完成且另获用户明确授权。

## 〇、最终目的与阶段划分

**最终目的：把 ZV-1M2（第五代 ASTRA）UI 移植到 a6600，并能刷入真机。**

为此把工作分为三个阶段，**只有阶段一完成才进入阶段二**：

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| **阶段一 · 模拟器验证**（当前） | 五代库加载 → 符号隔离 → 界面渲染 | 模拟器里截到可辨识的 ASTRA 界面 |
| **阶段二 · 可刷入性验证**（并行） | CRC / 签名 / 分区几何 / 恢复路径 | 能明确回答"改的镜像 updater 收不收""刷坏能不能救" |
| **阶段三 · 真机刷写** | 仅在阶段一二都完成、且用户明确授权后 | 真机跑起 ASTRA UI |

### 当前硬边界（不可逾越）

1. **纸面验证，不碰真机** —— 阶段一/二期间不做任何真机写操作
2. **不刷未验证镜像** —— 任何刷写必须先在阶段二拿到"可被接受 + 可恢复"的证据
3. **所有实验在离线镜像副本 + 隔离 QEMU 覆盖层内完成**

### 任务 D · 镜像策略对比实验（对应 P4）

**按决定：两种方案各做一次，用数据对比。**

| 方案 | 做法 | 观察指标 |
|---|---|---|

| **M2 · 扩分区** | 离线 `emmc.img` 改分区表 + ext2 大小至可容纳 279.8 MB 资源 | 内核是否接受新几何、`/usr` 能否挂载、对可刷入性的影响 |

| 项 | 内容 |
|---|---|
| 产物 | 两方案镜像 + 空间账目 + 对比结论（含"哪个更接近可刷状态"） |

### 任务 F · 可刷入性（并行，全离线）

| 编号 | 问题 | 方法 | 产物 |
|---|---|---|---|
| F1 | `part_image.sum` 的 CRC 算法与覆盖范围？该文件是否被签名？ | 提取 `0701_part_image_sum/part_image.sum`（在 `firmware.tar` 内），对比原厂/修改镜像的实际 CRC32 | CRC 算法说明 + 能否重算通过 |
| F2 | updater 包（`firmware.tar`/fdat）签名链，签名覆盖包级还是分区级？ | 分析 fdat、`updatershell`、`*.hdr` | 签名覆盖范围结论 |
| F3 | 扩 `nflasha15` 时分区表在哪、谁校验、后果 | 解析 `partinf.conf`、`nflasha7` 引导代码 | 分区几何改动可行性 |
| F4 | 刷坏后能否恢复？条件是什么 | 分析官方 updater 恢复流程、PMCA service mode 能力 | 恢复路径清单 |
| F5 | 有哪些刷写通道，各能写什么 | 官方 updater / PMCA service mode / 其他 | 通道能力表 |

**已知障碍**：`part_image.sum` 记录的 nflasha15 期望 CRC = `520fff36`，我们修改后实际 = `129576f8`，updater 会拒绝。

**F 的验收**：能明确回答"改的镜像 updater 收不收""刷坏能不能救"。**在 F1/F2/F4 有结论前不做真机刷写。**

## 七、风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| eMMC 时序抖动导致启动失败 | 实验不可复现 | 每组 ≥3 次；失败即重试；记录成功率 |
| 五代 UI 依赖 a6600 没有的内核接口 | 无法移植 | 任务 B 早期暴露；必要时放弃部分功能 |
| 分区扩容改变几何 | 破坏可刷入性 | M1/M2 对比时把"几何一致性"列为核心指标 |
| 签名/CRC 无法通过 | 无法刷入 | F1/F2 优先出结论；若不可绕，则本目标需重新评估 |
| 真机变砖 | 不可逆 | 阶段二未完成前禁止刷写；F4 必须先有恢复证据 |
