# 41 · 用备份状态绕开 panic 后：UI 启动，暴露第二个问题

本轮为离线 QEMU 实验。无设备写入。

## 一、实验设计

`state[2] = 3` 会触发固件主动 panic（上一轮结论）。该值来自备份属性 `0x00170000`：

```
原始: 00 00 03 02 01 00 01 01 ...
改造: 00 00 01 02 01 00 01 01 ...   （仅第 3 字节 3 → 1）
```

备份文件带字节求和校验和（`0x20` 处，校验范围为除该 4 字节外的全部内容），已重算使文件合法。

这是**只改喂给模拟器的输入副本**，相机与原始备份均未改动。

## 二、结果：av-cam 的 panic 消失，启动继续

| 项目 | 原始备份 | state[2]=1 |
|---|---|---|
| `Unhandled fault` | 1 | **0** |
| 异常监视器 | 是（2.56 s） | 是（**3.33 s**，原因不同） |
| 最后 guest 时间 | 2.565 s | **3.331 s** |

**这证实 `state[2]` 正是 panic 的开关**：值为 3 → 主动崩溃；值不为 3 → 错误被容忍，启动继续。

## 三、启动继续后到了哪里

新故障点的日志显示 UI 进程已启动：

```
program: im.elf(Appframework) (pid: 368, cpu:3, tid: -1, stackpage: 0x68f59040)
Illeagle Instruction at 0x04253796
```

同时已加载 UI 资源：

```
image_cmn_169.uxc / image_EVF.uxc / image_DSLR_Only_169.uxc
```

## 四、关键：这是与 av-cam 无关的第二个问题

`0x04253796` 与之前“跳过 av-cam 初始化（noinit）”路径下的故障地址**完全相同**，都落在 libc 偏移 `0x15796`。

也就是说：

- **问题 A**：av-cam 的 SIO 等待失败 → 因 `state[2]=3` 而主动 panic；
- **问题 B**：UI 进程 `im.elf` 在 libc 处触发 SIGILL（应用自身 abort 路径）。

**两者独立。** 在 noinit 路径和 state1 路径下，A 被绕过/消除，B 都照样出现。

## 五、意义

1. 证明 UI 栈本身能启动到加载资源、进入 Appframework 的阶段；
2. 当前**挡在菜单前的直接障碍是问题 B**，而不是 av-cam；
3. 需要强调：改备份状态只是**诊断输入变化**，不是真实修复——真机上 `state[2]` 就是 3 且能正常启动，说明真机的 SIO 等待是成功的，问题 A 仍需按“补对端模型”解决。

## 六、下一步

1. 优先剖析问题 B：`im.elf` 为何在 libc `0x15796` 处走 abort 路径。已知该处是 Thumb 系统调用桩的 `pop {r7,pc}`，且此前抓到过 `raise` 调用。
2. 需要关掉 ASLR 后在该地址稳定下断，取完整寄存器与调用栈（工具已支持 `norandmaps` 与 `--wall-seconds`）。
3. 判明 B 是“缺少某个服务/初始化”还是“模拟器缺少某个系统调用/特性”。
