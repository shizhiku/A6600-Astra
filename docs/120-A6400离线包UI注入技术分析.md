# 120 · A6400/A6100 V3.9 SSLF 离线包技术分析（UI 进程注入）

> 时间：2026-11-22。素材：`<UPDATER_DIR>\...\A6400-A6100-v3.9-SSLF-3Sound-Win-WSL-Offline\` 离线包 + GitHub `PCIEARIA/A6400-Extra-Menu`（本地 `/root/astra/aria`）。

## 一、最重要的发现：它不是"替换 appFw"，而是「向运行中的 im.elf 注入 UI .so」

这与我们目前"把 Application 路由到五代 appFw"的路线正交，是一条**已被实机验证的替代路线**。

运行链路（`local-boot-package-tc/persistent/a6400-film-boot-v15.tar` 内 `runtime-start.sh`）：

1. 开机早期由 `/etc/a6400-autoexec.so`（配合 `/etc/ld.so.preload`）拉起 `/tmp/autoexec.sh`；
2. `bootstrap-local.sh` 把 boot tar 复制进 `/tmp_bt`（RAM，`size=2048k` tmpfs），逐文件 SHA-256 校验后解到 `stage`；
3. `prepare.sh` 再校验 12 个产物（`ui`/`menu_job`/`worker`/`native`/`ram_job`/`ui_load_guard` 等）并复制到 `/tmp_bt`；
4. `runtime-start.sh` **等待 `im.elf` 就绪**：`/proc/<pid>/comm == im.elf`，`maps` 里同时有 `/usr/bin/im.elf`、`/usr/lib/libObj.so`、`/usr/lib/viewUnified2.so`；再等**线程数 ≥ 174 并稳定 2 次采样**；
5. 然后跑 `a6400-ui-load-guard.elf`，读 `/tmp_bt/a6400-ui-load.req`，**用 ptrace 把自定义 UI payload 注入 `im.elf`**；
6. 最后 `exec a6400-film-capture-daemon.elf watch` 常驻。

## 二、注入器（`camera/native_ui_load_guard.c`）技术细节

这是整个包对我们最有价值的部分：

| 项 | 内容 |
|---|---|
| 目标进程 | 动态查找 `im.elf`（不写死 PID） |
| 权限 | `ptrace(PTRACE_POKETEXT)` 直接改写目标进程内存 |
| 目标库 | `/libObj.so`（RX 段），hook 偏移 **`0x5F1D48`** 与 **`0x5F1DC0`** |
| 识别方式 | 12 字节函数序言 `2D E9 F0 47 88 B0 4F F0 14 08 01 22`（`push.w {r4-r10,lr}; sub sp,#0x20; mov.w r8,#0x14; movs r2,#1`）；找不到则 `0x580000..0x680000` 区间扫描唯一匹配 |
| 代码落点 | 各 RX 模块**页尾空洞**（`rx_hi - CODE_REGION_BYTES`，2296 B），要求文件末尾该区全 0 |
| 数据落点 | 各 RW 模块页尾空洞（`rw_hi - STATE_REGION_BYTES`，1760 B，state 1184 B） |
| 依赖符号 | 从 `libdl` 的 `.dynsym` 解析 `dlopen`/`dlsym` 地址（动态基址 + `st_value - first_PT_LOAD_vaddr`） |
| 载荷协议 | `/tmp_bt/a6400-ui-load.req`：头 8 个 u32（magic `0x4D544852`、ver=1、op≤2、payload 长度、…、state 大小 1184）+ payload + FNV-1a 校验（`h[5]`） |
| RX 白名单 | `libObj.so`、`libptp.so`、`libmprctrl.so`、`libInfraMscServer.so`、`libInfraFsys.so` |
| RW 白名单 | `libObj.so`、`libcompassutil.so`、`libBizFw.so`、`libMWF.so`、`viewUnified6.so`、`libInfraNfc.so`、`viewUnified4.so` |
| 一次性 | install 后再以 `is_branch_stub`（`df f8 00 f0`+`00 bf 00 bf`）识别"已注入"状态，避免重复注入 |

**关键含义**：`0x5F1D48`/`0x5F1DC0` 是 4 代 `libObj.so` 里**会被周期性调用**的函数（否则注入的 UI 不会刷新）。这正好印证我们之前对 4 代 `libObj` 的触屏/WidgetSystem 分析：`sys_getInstance` 0x5F1299、`postMousePress` 0x5F26D1、`postMouseMove` 0x5F2641、`postMouseRelease` 0x5F2739 都在同一区间。也就是说，**这一段就是 4 代 UI 的输入/绘制回调区**。

## 三、对我们的三条可复用结论

### 3.1 替代路线：注入五行 UI，而不是路由 Application

我们目前卡在"五代 Application_Start 进入 `0x54F664` 后阻塞"。而这个项目证明：**可以让四代 `im.elf` 完整跑起来（显示/触摸/帧循环都由四代原厂负责），只把"要画的东西"作为一个 `.so` 注入进去**。

对 ASTRA 移植的映射：

- **离线可行**：在 QEMU 里用同样的 ptrace 注入思路，把**五代 `viewUnified`/`libOb5` 的 UI 模块**加载进四代 `im.elf` 进程，让四代负责 ch53/DMP 出帧，五代模块负责画 ASTRA 的界面；
- **不需要**让五代 `Application_Start` 跑通——绕过了当前最大阻塞点；
- 但需要五代 UI 模块能在四代 libObj 的符号环境下构造出来（五代 `viewUnified` 是独立 `.so`，理论上可加载，只是它内部依赖五代 libObj 的类；这需要验证）。

### 3.2 UI 进程的"就绪判据"可以直接用

`runtime-start.sh` 的判据很有用，可作为我们 QEMU 里判断"UI 是否真的起来了"的标准：

```
/proc/<pid>/comm == im.elf
maps 含 /usr/bin/im.elf、/usr/lib/libObj.so、/usr/lib/viewUnified2.so
/proc/<pid>/status 的 Threads >= 174 且连续两次采样不变
```

我们在 ASTRA 实验里目前 `draw=0`，可以用同一判据衡量"四代 UI 是否已达可注入状态"。

### 3.3 恢复与安全边界（对 F4/F5 的补充）

这个项目给出的**实际可用的急停/回滚手段**，比我们 110 号报告的推测更具体：

- SD 卡根目录放空白 `/disable_hook` + `/A6400/DISABLE` → 下次开机完全不加载（**离线可用、不需要 USB**）；
- `pmca_deploy_v3_clite.py --rollback` → 还原 `.pre-v3c-backup` 或干净移除挂勾并 `sync`；
- PMCA `serviceshell` 里 `/bin/busybox touch /tmp/disable_hook && sync` → 持久化临时停用；
- 重要架构事实：**`/etc` 与 `/tmp` 共用 `/dev/nflasha10` 同一 inode**，误删 `/tmp/a6400-autoexec.so` 会同时删掉 `/etc` 的挂勾。

这几点应并入 110 号报告的 F4/F5 证据（但注意：它验证的是"改 `/etc` 挂勾后可回滚"，仍不等于"任意 `/usr` 改造可救砖"）。

## 四、仍需核实（离线可做）

1. `0x5F1D48`/`0x5F1DC0` 在 4 代 `libObj.so` 里到底是哪两个函数（用我们的 `a6_libObj.so` 反汇编确认，并与 `viewUnified2` 的绘制调用对齐）；
2. `a6400-film-ui-v3-persist.so` 的导入表：它只依赖 4 代 libObj 导出的哪些符号，能否作为"最小可绘制 .so"模板；
3. 五代 `viewUnified`/`libOb5` 的依赖闭包是否能在四代进程里满足（这是 3.1 路线成立的前提）。
