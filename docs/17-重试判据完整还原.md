# 17 · 重试判据完整还原（含动态验证）

本轮全部为离线 QEMU 观测与本地静态解析。未连接相机、未改固件、未写内存。

## 一、先修正两个解析错误

1. **GDB 寄存器宽度**：本机 QEMU 的 `g` 包对 32 位 ARM 使用**每寄存器 4 字节**。此前按 8 字节解析，寄存器全部错位。
2. **Thumb 字面量读取**：
   - 16 位 `ADD Rd, PC` 的 PC 取 `指令地址 + 4`，**不做 4 字节对齐**；
   - `ldr Rd,[pc,#imm]` 的字面量是 **32 位**，此前只读了 16 位。

修正后所有地址自洽，并与运行时实测一致。

## 二、判据的完整结构

例程 `0x638529d8`（由 liro 工作线程 `kliro` 回调驱动）：

```
r4 = 0x645C710C                      ; 模块数据基址
obj    = *(0x645C710C + 0x6054) = *(0x645CD160)
state  = *(0x645C710C + 0x4FDC) = *(0x645CC0E8)
g      = *(0x644AE3A5)               ; 全局字节

r5 = ([obj+3] ^ (g << 4)) & 0x7F

if (r5 == 0)                -> 计数器清零，走正常路径
if ([state+1] == 1)         -> 计数器清零，走正常路径
else                        -> 计数器 0x644AE3AA 加一
                               当 > 0x1D(29) 时：写状态 7，发消息 0x3A
```

## 三、动态实测值

在增量写入点 `0x63852A32` 断下读取：

| 项目 | 地址 | 实测值 |
|---|---|---|
| 对象指针槽 | `0x645CD160` | `0x640D26A0` |
| 状态指针槽 | `0x645CC0E8` | `0x64437E98` |
| 全局字节 | `0x644AE3A5` | `0x04` |
| 对象前 4 字节 | `0x640D26A0` | `39 0D 00 04` → `[obj+3] = 0x04` |
| 状态结构前 4 字节 | `0x64437E98` | `00 00 03 02` → `[state+1]=0`、`[state+2]=3` |
| 增量计数器 | `0x644AE3AA` | 递增中 |

**验算**：

```
r5 = (0x04 ^ (0x04 << 4)) & 0x7F = (0x04 ^ 0x40) & 0x7F = 0x44
```

与断点处实测寄存器 `r5 = 0x44` **完全一致**。两个清零条件均不成立（`0x44 ≠ 0`、`[state+1]=0 ≠ 1`），所以进入累加分支。

## 四、计数器确实会累加到上限

对 `0x644AE3AA` 设写监视，连续记录到：

```
1, 2, 3, 4, 5, 6, 7, 8, 9, 0x0A, ... 0x16, 0x18, 0x1A
```

单调递增，直到观察预算或超时耗尽。这与静态代码的 30 次上限一致，也印证了此前观察到的一次 `0x1E`（30）写入。

**更正**：上一版报告曾称“计数被反复清零、不会累加到 30”，那是上述两个解析错误造成的假象，现已撤回。正确结论是**会累加**，直到 30 次触发错误状态 7。

## 五、当前结论

固件在**等对象 `0x640D26A0` 的第 3 字节变成 `0x40`**（即与 `全局字节 << 4` 相等），或等状态结构第 1 字节变成 1。两者都不发生，于是 30 次后写入状态 7、发消息 `0x3A`，随后被另一处读到 7、结合状态字节 3，触发显式空地址陷阱。

这把问题精确收敛为：**谁应当把 `[0x640D26A0+3]` 写成 `0x40`，以及为什么在模拟中没有发生。**

## 六、对象 `0x640D26A0` 的性质（新增）

对该对象第 3 字节（`0x640D26A3`）设写监视，观察到它**并非只读**：启动过程中有持续写入，写入点集中在 `0x63A73ABC`。

该处代码是一个按 4 字节搬运的循环：

```
63a73ab6  ldr  r7,[r5],#4
63a73aba  adds r3,#1
63a73abc  str  r7,[r0],#4      ; 目的指针递增
63a73ac0  cmp  r3,r6
63a73ac2  bne  63a73ab6
```

结合前后的 `lsls r0,r0,#9`（索引 ×512），这是一段**把数据块搬入 512 字节槽位**的复制逻辑。也就是说 `0x640D26A0` 是某个缓冲区表中的一个槽，判据读到的 `[obj+3]` 是该槽内容的一个字节。

监视中该 4 字节区域出现过 `0x00`、`0x36`、`0x3e00`、`0x7c00` 等值，说明槽内容随复制变化；而在重试判据执行时它是 `0x04`。

在 av-cam 文件里该区域是 `0`（属 .bss），运行时才被填充。

## 七、槽内容的来源（新增）

继续监视该槽（`0x640D26A0` 4 字节），观察到它被填充成：

```
39 0E 00 00   →  39 0F 54 00  （此后保持不变）
```

而同一次启动的 SIO ch0 日志中，主机侧发送的帧开头正是：

```
39 0F 54 00   ; mode=0x71000000 len=256
39 0F 54 3E
39 0F 54 7C
...
```

两者一致。因此 `[obj+3]` 很可能是**某条 SIO 帧缓冲的第 3 字节**，而不是一个设备“就绪”标志。

这与整段判据的性质相符：它在比对通信缓冲里的某个字节是否等于由全局字节推出的目标值（`0x40`）。

需要注意：SIO ch0 帧的第 3 字节按 `0x3E` 步进（`00, 3E, 7C, BA, F8, 36…`），这些取值都不等于 `0x40`。所以要么该判据并不对应 ch0 帧，要么它期望的是另一路数据的值。**此点尚未确定。**

## 八、未完成的测量

原计划用多断点记录“轮询”与“填槽”的先后顺序，但观察器分支顺序写错，实际执行的是写监视，**顺序仍未测到**。该测量需要重做。

## 九、待验证假设（更新）

- 槽内容来自 SIO 通信缓冲；
- 判据期望该缓冲出现特定值 `0x40`；
- 可能是等待某条应答帧，而模拟中该帧的对应字节始终不是 `0x40`。

以上均未验证，不能作为结论。

## 十二、崩溃发生在哪个线程（重要）

启动日志显示 LIRO 的加载握手**已经正常完成**：

```
[2.490] LIRO (liro) rev:4-MUSASHI
[2.490] start entry_pre(635c6044) → end entry_pre
[2.495] start entry_main(635c6058) → end entry_main
[2.561] Process liro-kliro_66 (pid: 219, tid: 66, cpu:2)
```

`entry_pre` 与 `entry_main` 都返回了。约 63 ms 后，故障发生在 **liro 创建的工作线程 `liro-kliro_66`** 中。

因此：

- 问题**不是** av-cam 加载失败或 LIRO 握手失败；
- 而是该内核工作线程在执行 av-cam 代码时，进入前面那套“等待 → 30 次重试 → 写状态 7 → 空地址陷阱”的路径。

这也解释了为什么此前反复检查设置、副控制器帧、时序偏移都没有效果——那些都不是这个线程在等的东西。

## 十三、顺序测量未完成

原计划记录“重试轮询”与“缓冲填充”的先后。实测中缓冲复制循环 `0x63A73ABC` 连续触发 30 次，而重试增量一次也没出现，说明该复制循环活动频率远高于重试。用这种粗粒度断点顺序无法覆盖两者关系，需要更定向的方法（如条件断点或按目标地址过滤），当前方式不足。
