## 二、已经打通的部分（可复现）

### 1. 启动链

`nflasha3-Image`（内核） + `nflasha3-initrd`（ext2 根文件系统，2.18 MB）+ emmc overlay + `Backup.bin`（作为 `/setting`）。

关键参数（来自 `kemco.txt`）：`root=/dev/ram0 rootfstype=ext2 initrd=0x700000,8M`、`wdt.timeout=500`、`exception.console_option=115200n8`。

### 2. 绕开 av-cam 的主动 panic

`Backup.bin` 属性 `0x00170000` 的 byte[2] 由 `3` 改为 `1`（`Backup-state1.bin`），可绕过 av-cam 对副控制器 SIO 帧状态的等待失败。

> 这是**诊断用输入变化**，不是修复。真机该值为 3 且工作正常，说明真机侧该等待能成功。

### 3. UI 框架确实起来

日志出现 `im.elf(Appframework)` 进程、加载 `image_cmn_169.uxc` / `image_EVF.uxc` / `image_DSLR_Only_170.uxc`，并有 `[VPH]` 显示层输出。

### 4. 崩溃点已精确定位

```
im.elf → libObj.so → TextRM_loadFont("FONT_S_CHINESE")
      → 在「已注册字体链表」中找不到 → 返回 -16
      → libObj 错误上报 → abort() → raise(SIGABRT) → tgkill(_,_,6)
      → Sony 异常监视器打印 "Illeagle Instruction"（措辞误导，实为 SIGABRT）
```

相关地址（libObj 偏移）：`TextRM_loadFont` = `0x54ED58`；查找助手 = `0x54E7A8`；节点创建 = `0x54E7D4`；注册函数 = `0x54E94C`（由一次性初始化 `0x54F3A2` 调用一次）；字体链表头 = `0x13F64FC`（运行期 `0x06BD94FC`）。

## 三、根因（已确证）

**中文字体由副控制器在运行期提供，模拟器未实现该链路。**

证据链：

1. `/usr` 内只有 3 个 `.ltt`（Univers / Heisei / KSX1001），**无中文**；
2. `fontlist.dat` 把 `FONT_S_CHINESE` 指向 `/tmp/images/MYingHeiC-GB18030-SJ_wIcon.ltt`；
3. 相机 `/tmp/images/` 中确实存在该文件（**已采集 1,958,432 字节**）；
4. `libsencore.so`（副控制器通信库）含这些 `/tmp/images/...ltt` 路径 + `Trans(to Subsystem)` / `resCode/Adrs/DataSize` / `Offset > 300Byte` 等报文线索；
5. 客户机内实测：**`/tmp/images` 在运行期根本不存在** → 目录与文件是传输路径的副产物；
6. 字体注册由一次性初始化完成，**不遍历 `fontlist.dat`**，故仅放文件不会触发注册。

## 四、明确的死路（已排除的假设）

| 假设 | 结论 |
|---|---|
| 内核禁用 syscall 191 导致 SIGILL | 否（BusyBox 使用 191 正常） |
| CPU 用 ARM 态误解释 Thumb 字节 | 否（内存与文件一致） |
| 用错了 libc（相机与更新包不同构建） | **构建确实不同**（libc 仅 10/241 块相同），但换成相机 libc 后崩溃点不变 → 不是成因 |
| 实现库缺失于 `/system` | 否，实现在 `libObj` 内部 |
| 把字体放进 `/tmp/images` 即可 | 否，运行期该目录不存在 |
| 改 `/usr` 内 `fontlist.dat` 指向 `/usr/share/app` | 启动会在 3.27 s 后停滞（600 s 预算仍无 `im.elf`），原因未明 |

## 五、下一步（按优先级）

### A. 逆向并实现副控制器文件传输（根本方案）

- 目标库：`libsencore.so`（349,760 B，`/usr/lib`）
- 已知线索：应答字段 `resCode/Adrs/DataSize`；分片窗口 `0x300`；命令 `FIN_SEND_DATA`；`TransType` 8 位；共享内存 `mmap`
- 需要：确认硬件通道（SIO 通道号/FIFO 窗/中断）→ 在 QEMU 侧实现应答 → 验证 `/tmp/images` 被创建、字体注册被触发

### B. 查明「改 `/usr` 后启动停滞」的原因

- 现象：同尺寸仅更新超级块可正常启动；改动文件内容后停在 3.27 s
- 怀疑：`qemu-io` 写入 overlay 时的稀疏/分配差异；或镜像元数据差异触发内核路径问题
- 验证：保留 `overlay.log`、比较写入后 overlay 的差异、用逐块校验确认分区内容

### C. 提高模拟保真度

- 用相机真实 `/usr` 替换更新包内容（已证实为不同构建）
- 补齐 `/system` 分区（`nflasha3` 内未找到对齐 FAT32；可能需从相机侧确认）
