# 12 · LIRO 故障指令与设置来源

本轮仅离线静态分析和 QEMU 原厂固件调试，没有访问或写入相机。没有修改固件指令、寄存器、设置值，也没有跳过错误分支。

## 已验证结论

此前日志中的 PC `0x63849f30` 位于原厂 av-cam.bin。按加载地址 `0x635c6000` 映射到文件偏移 `0x283f30`；原文件 SHA-256 为 `c17bdd14bb3f51ab14b6ffcd385b81786c4201ab5a0d2bea8a2c7be5c6aed8b5`。

原指令：

```
63849f24  cmp  r3, #3
63849f26  bne  63849f3c
63849f28  movs r0, #9
63849f2a  bl   63d2aaf2
63849f2e  movs r3, #0
63849f30  str  r3, [r3]
```

硬件断点实际停在 `0x63849f30`，读到 r3=0；内存指令与原始固件字节相同。因此可以确定这里有显式的向零地址写入序列，属于主动触发致命异常的代码路径，而不是证据不足的“随机空指针”。这种主动触发不说明更早的状态为何异常。

进入该段之前，`0x63849f10` 从 `[r7+2]` 读取状态字节。断点时 r7=`0x64437e98`，该字节为 3。这只是进入分支的一个局部条件，不是所有前置条件。

## 设置来源的动态核对

在同一原厂固件、真实设置和独立 qcow2 覆盖层下，观察对 `0x64437e9a` 的写入：

1. 首次命中在原厂内核拷贝代码 `0x60258bd0`，目的区尚为零。
2. 读取该次拷贝的源区 `0x62ee7f54`，96 字节与捕获的 Backup.bin 文件偏移 `0x67f54` 开始的 96 字节完全相同。
3. 移除模拟器写监视点后，只单步执行原来的存储指令；目的区前 32 字节与源区相同，目标字节从 0 变为 3，PC 前进到 `0x60258bd4`。
4. 用现有 PMCA BackupFile 只读解析原始备份，整体备份校验通过。偏移 `0x67f54` 属于属性 `0x00170000`，长度 256，属性标记 0x8。所观察字节是该属性的偏移 2。

这说明运行状态的 3 有真实设置数据来源，不是我们手写的假成功响应或临时注入值。**不说明属性损坏，也不说明把它改成别的数就正确。**
