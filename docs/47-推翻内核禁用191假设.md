# 47 · 推翻“内核禁用 191”假设

本轮为离线分析 + QEMU 内实验。无设备写入。

## 一、决定性对照：BusyBox 用的是 191，且成功

在 initrd 中搜索系统调用号编码：

| 模式 | 含义 | 命中 |
|---|---|---|
| `4f f0 bf 0c` | Thumb `mov.w ip,#0xBF`（191） | **命中 1 处（offset `0x9782A`）** |
| `4f f0 4c 0c` | Thumb `mov.w ip,#0x4C`（76） | 0 |
| `bf c0 a0 e3` | ARM `mov ip,#0xBF` | 0 |
| `4c c0 a0 e3` | ARM `mov ip,#0x4C` | 0 |

即 initrd 里的 BusyBox 使用的是 **191 号（`ugetrlimit`）**。

而上一轮的 shell 实验：

```
ulimit -a        →  getrlimit_rc=0
ulimit -n 123    →  setrlimit_rc=0
```

**所以 191 号系统调用在该内核上可用，且返回成功。**

## 二、假设被推翻

此前推断：“内核把 191 判为 bad syscall 并投 SIGILL”。

现在证据表明该推断**不成立**：

1. BusyBox 用 191 成功；
2. 故障前的内核日志里**没有**出现 `undefined instruction` 或 `bad syscall` 字样（若走内核陷阱路径，这两条 printk 应当出现）。

## 三、对故障性质的新认识

故障报告为：

```
trap_no: 00000006
[Exception Syndrome]  Illeagle Instruction at 0x04253796
```

`trap_no = 6` 有两种可能解释：

- 若为**信号编号**：6 = **SIGABRT**（`abort()`），而非 SIGILL（4）；
- 若为 Sony 自定义的陷阱编号：含义未知。

结合此前函数追踪里出现过 **`raise`** 调用，**“应用调用 `abort()`/`raise(SIGABRT)` 主动终止”** 这一解释更自洽：

- 信号投递不会产生内核 printk，与“日志无 undef 记录”吻合；
- 现场 PC 落在 syscall 桩、LR 落在 `getrlimit` 附近，只是**被信号打断时的位置**，不代表崩溃原因。

## 四、当前结论

| 项目 | 结论 |
|---|---|
| 191 号系统调用是否可用 | **可用**（BusyBox 实证） |
| 故障是否为内核 bad-syscall 陷阱 | **否** |
| 更可能的原因 | 应用侧主动 `abort()`（或其触发的信号），具体触发条件仍未知 |

## 五、下一步

1. 确认 Sony 异常处理里 `trap_no` 的语义（信号号 vs 陷阱号）——可从内核字符串里找 `trap_no` 的打印格式语句反推；
2. 在 QEMU 中对 `abort`/`raise` 的实际入口下断（需先由符号表定位 libc 中 `abort` 偏移），确认是否真的被调用、调用者是谁；
3. 若确为 `abort`，再查触发它的断言条件。
