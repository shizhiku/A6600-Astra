# 103 · 五代 UI「模型/系统错误」触发点定位

日期：2026-11-22。离线镜像 + QEMU，无设备写入。

## 一、定位到的代码

在镜像实际加载的 `a5pFw.so`（由原 gen5 `appFw.so` 改名并加依赖边，64,484,389 B）中：

| 对象 | 地址（文件内 VA） | 说明 |
|---|---:|---|
| `lib::assert::notify_model_system_error()` | **0x2BC3174** | 断言函数本体：加载 `lib_assert.cpp`、行号 30（`movs r2,#0x1E`）、`void lib::assert::notify_model_system_error()` 字符串后 `blx __assert_fail` |
| 直接调用者 | **0x2BBA4CC** | 在 0x2BBA91A 处 `bl 0x2BC3174` |

断言函数地址由运行时栈反推：

- 捕获崩溃时的 `sigcontext`（寄存器在 `uc_mcontext + 0x14 + 3*4` 起：r0..r10、fp、ip、sp、lr、pc、cpsr）；
- 栈上出现 `0x2FDA83B`（`lib_assert.cpp` 字符串）与 `0x2FDA84A`（函数名字符串）指针，位置紧邻断言调用帧；
- 返回地址换算到实际镜像的 appFw 偏移，落在 `0x2BC31xx`，反汇编确认与断言调用完全吻合。

## 二、调用者是一个“状态/命令码分发器”

`0x2BBA4CC` 函数开头先把入参结构体字段读出来，然后按两个字段做多级比较：

- 第一字段（进入 `r6`）支持集合：`0,1,2,4,6,7,8,9,0xB,0xD,0x10,0x11,0x12,0x14,0x16,0x18,0x1A,0x1C,-1`；
- 第二字段（进入 `sl`）支持集合：`1,2,4,8,-1`；
- 另有第三处 `r1-1 > 3` 的默认错误分支。

**每一个默认分支的处理都是：**

1. 用 `add-pc` 加载字符串做日志（解出的字符串片段包括 `"...status.cpp"`、`"status:%d"`、`"...callback"` 等）；
2. 调用 `0x2CE8654`（参数 0x186A0 = 100000，疑似延时/重试）；
3. **调用 `0x2BC3174`（notify_model_system_error）**。

也就是说，五代 UI 并不是“缺库”或“硬件不存在”才报错，而是**收到了一个不在支持集合里的状态/命令码**，进入默认错误分支后主动断言。

该分发器没有直接 BL 调用者（扫描全 `.text` 的 BL 目标为 0 次），说明它是通过**回调/函数指针注册**被调用的，符合“模型状态回调”的实现方式。

## 三、下一步（明确）

1. **抓实际收到的码值**：在 `0x2BBA4CC` 入口做运行期陷阱（例如把首字节替换为 `svc #0xFF`，SIGSYS 处理器记录 `r0..r3` 指向的结构体字段后恢复原指令并跳回入口）。这样能看到进入默认分支的到底是哪个字段、什么值。
2. **判断是“环境缺消息”还是“结构体 ABI 不匹配”**：
   - 若是某条本应由 av-cam/UPM/传感器返回的状态消息缺失，就补对应模型响应；
   - 若是 4 代 IMDB 环境下消息结构布局与 5 代期望不同，就修正消息转换层。
3. 该结果也能解释为什么绕过断言后 ch53 一直不编程：分发器在错误分支里 100 ms 级延时/重试后断言，正常渲染路径没有被进入。

## 四、第二轮运行期验证（入口陷阱）

在客户机内由 preload 找到 `a5pFw.so` 的映射基址，把分发器入口（`0x2BBA4CC`）或分发比较点（`0x2BBA52C`）临时改为 Thumb `UDF`，SIGILL 处理器记录寄存器后恢复原指令并从原地址继续执行。

已验证：

- 入口陷阱命中：`r0=0x34324d34 r1=0x34324d10 r2=0x2dee1320 r3=0x2dee1212`，`lr` 指回 appFw 的调用者，说明分发器确实被调用；
- 分发比较点陷阱命中：首次调用时 **`r6=0x00000000`、`sl=0x00000004`**，两者都在支持集合内，说明第一次分发是合法的；
- 把陷阱放到错误分支（`0x2BBA8F0`）时出现**时序依赖**：多数运行在该陷阱被改写前就已经走到断言；把轮询缩短到 5 ms 后的一次运行里**没有触发断言**，但也**没有编程显示控制器**（`[VPH] ch53 still 0`、`[DMPCOUNT] draw=0`）。

## 五、当前判断

1. “模型/系统错误”来自分发器对某个后续状态/命令码的默认分支，不是第一次分发；
2. 该错误路径存在**时序/竞争**：同一镜像有时断言、有时静默卡住；
3. 静默卡住时 UI 根本没有开始绘图（ch53=0、draw=0），说明它在等一条**不会到达或到达顺序不对**的状态消息；
4. 下一步应在分发器的所有错误分支前记录消息码（或直接 hook 该回调的注册点），并定位状态消息的来源（av-cam/UPM/传感器）。

## 六、第三轮：子系统与坏字段已定位

在断言调用点（`0x2BBA91A`）下陷阱，抓到触发时现场：

- `sl=0x00000004`（第二字段合法）；
- 栈上局部值里 **`msg+0x20 = 0x005081e8`**（指针形态），而代码在该处要求 **0 或 1**；
- 分发器由 appFw 的 thunk `0x2B1E4BC` 调用，thunk 是 **event 9** 的处理入口（同一组 thunk 还处理 event 4~10）；
- thunk 的上层调用者 `0x2B44978`。

结合 appFw 内字符串：

- `10key_status`
- `assert at %s:%d`
- `000_main/key_status.cpp`
- `function:%s`
- `virtual void key_status::inhbit_key_strobe(bool, i_ke...`

**结论：报错子系统是 `key_status`，触发点是它处理 event 9 时收到的消息结构体 `+0x20` 字段不是期望的 0/1。**

`0x005081e8` 呈指针形态，而四代 `_InfraInputEvent` 约 24 字节（文档 79），`+0x20` 已超出该结构；这强烈指向**四代内核输入驱动/四代输入服务产生的事件布局，与五代 `key_status` 期望的事件布局不一致**。这正是任务书里“必要 ABI/符号适配”要解决的那类问题，而不是缺少硬件。

## 七、下一步

1. 对比四代 `input.ko`/InfraInput 事件结构（`_InfraInputEvent`，约 0x18 字节）与五代 `key_status` 期望的结构（至少访问到 +0x20），确认字段错位；
2. 找一个事件进入路径做运行期抓包，记录 5 代 `key_status` 实际收到的完整结构；
3. 在四代→五代之间加一个事件转换层（或改用五代的输入服务/驱动事件定义），把 +0x1C、+0x20 等字段补齐/翻译；
4. 修好后应能通过 key_status 初始化，继续向 ch53 编程推进。

## 八、第四轮：绕过 notify 后显示控制器首次被编程

把 `notify_model_system_error` 函数入口（`0x2BC3174`，首字节 `05481e22`）改成 `bx lr`（`70 47`），让 key_status 的错误分支直接返回、不再 abort，生成镜像 `astra-m1-rwx5.img`（appFw 还带 RWX 段补丁）。

运行结果（`m1-nonotify2-20261121T195708Z-9925-1`）：

- **首次出现 `[VPH] ch53 base=0x23b16000 ctrl=0x2 lb=0x500 lines=480`** —— 显示控制器被编程；
- 抓到 `frame.0.ppm`（vsync 1200）；
- 该帧内容为**全黑**，`[DMPCOUNT] draw=0`，说明只完成了显示缓冲初始化，绘制提交尚未发生；
- 无异常、无崩溃。

**意义**：`key_status` 的错误路径确实在阻塞显示初始化；绕过它之后，五代应用已经能走到显示控制器初始化阶段。这是 M-E（可辨识 ASTRA 界面）方向上第一个确定的运行时里程碑。

## 九、可重复性观察（第五轮）

- notify 入口改成 `bx lr` 后，有一次运行确实编程了 ch53 并抓到黑色帧（见第八节）；
- 但后续同配置运行出现波动：有的运行没有 ch53 编程、也没有抓到帧，`im.elf` 在 20 秒的 maps 扫描前就已不在；
- 用析构函数打点（`[EXITTRACE]`）没有观察到正常退出标记，说明进程不是走 `exit()`，更可能是被信号结束或任务提前终止；本轮准备的 `exit()` 拦截因版本符号问题一度破坏启动，已放弃该做法；
- 结论：**“绕过 notify → ch53 编程”这一步存在时序/竞争**，还不是稳定路径。需要先解决根因（key_status 事件结构/Packet 内容），而不是依赖绕过。

## 十、第六轮：事件到达性验证

把 key_status 分发比较点（`0x2BBA52C`）改成可重复布防的 UDF 陷阱，每次命中记录 `r6/sl`：

- 全程只命中 **2 次**，两次都是 `r6=0x00000000`、`sl=0x00000004`（均在支持集合内，属合法事件）；
- 12s/25s/40s 的 ENTER/MENU 注入之后**没有新的分发命中**；
- 该轮 shell 探针标记未出现（`guest_usr_mounted=false`），存在启动波动，命中次数只能作为趋势参考。

结合线程状态（`THREAD_APP` futex、多个 `AppFw` 线程 `osal_wai_sem_tmo`/futex、`THREAD_INFRA0` 在 `sugilite_ioctl`）：

**UI 进程活着但事件驱动地空转，按键注入没有进入五代 key_status 分发器。**

一个合理解释：同一个进程里同时存在四代 `libObj` 的 `InfraInput` 和五代 `libObj` 的输入服务，两者从同一条 `/dev/uipc`/驱动队列取事件；四代 UI 先消费掉了 MENU/ENTER，五代 key_status 收不到。下一轮需要验证并处理这个“双消费者”问题（或直接把事件注入五代队列）。

## 十一、第七轮：输入服务对比与根因收敛

在 4 代 `libObj` 的 `InputService::createEvent(m, h)`（符号 `_ZN12InputService11createEventEmh`）上下可重复布防的 UDF 陷阱，比较原厂镜像和 ASTRA 镜像：

| 镜像 | 70 s 内 createEvent 命中 |
|---|---|
| 原厂 a6600 | **9 次**（含 `r1=0x150700c0`、重复 `0x17005007`，`r2=4`） |
| ASTRA（Application 路由到五代） | **0 次**（陷阱已成功改写 `0x07dd3aea`，但从未执行） |

结合线程表（ASTRA 进程里已有 `I-InputMain/I-InputRecv/I-InputEvent` 等四代 InfraInput 线程，但 `createEvent` 不调用）：

- 四代 `InfraInput` 线程仍在运行、仍会从驱动取事件；
- 但四代 `InputService`（真正把事件转成 UI Event 的消费者）在 ASTRA 镜像里**没有被启动**——因为它的调用方是四代 Application，而我们把 Application 换成了五代；
- 五代 `key_status` 侧也只看到 2 条合法内部事件、没有 MENU/ENTER（第六轮）。

**根因收敛**：我们的混合启动只跑了四代 IMDB 链到 Application 分流点，跳过了五代 IMDB 自带的初始化任务（`infra_input_init`、`uxengine_init`、`grm_init`、`GpeInit`、`core_sync_user_init`、`MWF_Init` 等）。因此四代输入服务没有消费者、五代输入/模型栈也没有初始化，按键事件在两边都到不了 UI。

参考项目（nolan2628/ZVE10-Astra-Public）的做法是从 gen4 基底出发，用一个**自定义 appFwBoot 宿主**手动初始化并驱动五代 `libOb5`/WidgetSystem 渲染循环，而不是依赖五代 IMDB。两种路线都指向同一结论：**必须把五代初始化任务序列（或等价 Host 驱动）补上**。

## 十二、第八轮：补齐五代 init 序列

发现 `infra_input_init/uxengine_init/grm_init/DDSUserInit` 等初始化符号其实导出于 **五代 libObj.so**（静态合入），不需要缺失的独立 .so。桥接器 v5 改为每个 init 独立线程 + 2.5 s 超时后依次调用：

```
dmp_allocator_lib_init -> 0
dmp_allocator_mmap_init -> 0
DDSUserInit -> 0
uxengine_init -> 0
WidgetLayouter::sys_initialize -> 1
infra_input_init -> 5137520（非 0 视为已执行）
MWF_Init -> 5195392
grm_init -> -1
appFwBoot entry -> 返回
```

运行结果（`m1-init5-threads-...`）：

- 初始化确实生效：线程表新增 `uxengine_res1/uxengine_res2`、`StlDateEvtLoop`、`IWrapperBB/IWrapperBBSub/IWrapperHDMI` 等五代线程；
- `THREAD_APP` 有线程停在 **`sugilite_ioctl`**（GPU 驱动等待），另一个在 nanosleep；
- 仍然 `ch53 still 0`、`draw=0`、无帧；
- `grm_init` 在独立线程里返回 -1（此前直接调用会卡住，说明它依赖的初始化顺序/线程上下文不同）。

结论：init 序列补上后，五代 UI 的线程骨架更完整，但渲染仍未启动；`THREAD_APP` 卡在 GPU ioctl 是下一个明确观察点（可能在等 GPU 任务完成/中断，或等某条事件）。

## 十三、第九轮：UPM boot-factor ABI 修复（部分生效）

keystatus-analyst 的静态结论：`0x2BBA4CC` 不是按键事件消费者，而是 **UPM→model boot-factor 枚举转换器**；它用 OSAL uipc 同步消息向 qid `0x00924127` 发 mid `0x00920111` 的请求，四代 `upm.ko` 只回填 0x1C 字节（7 字），五代 appFw 按 0x28 字节（10 字）读取，`+0x1C/+0x20/+0x24` 为五代新增，`+0x20` 读到残留 `0x005081e8` → 断言。

- 应用补丁 A：`0x2BBA520` 的 `0A 6A 4B 6A`（`ldr r2,[r1,#0x20]; ldr r3,[r1,#0x24]`）→ `00 22 00 23`（`movs r2,#0; movs r3,#0`），即把两个五代新增字段固定为合法默认 0；
- 镜像：`astra-m1-upmfix-b5.img`（`aec39f15…` → bridge5 后 `69a15824…`）；
- 结果：经 `0x2BBA4CC` 的断言路径不再触发；但运行期出现**新的断言**，调用链变为 `0x2B359F7 / 0x2B20821 / 0x2B20DA9 / 0x1D58FC1`，说明同一族还有其他转换器在读四代缺失的五代字段；
- 另一个尝试：把五代 `upm.ko` 换进 /kmod（两代 vermagic 相同 `3.0.27_nl-rt106+ SMP preempt mod_unload ARMv7`），断言链不变，说明该模块未被加载/未生效（启动脚本未加载它或加载失败，待查 /proc/modules）。

下一步：等 keystatus-analyst 给出「同族全部检查点」补丁清单后统一打补丁；同时确认 upm.ko 的实际加载路径。

## 十四、第十轮：appFwBoot 实际加载的是谁（重大发现）

appfwboot-analyst 反汇编结论（`107-五代appFwBoot初始化调用分析.md`）：

- `appFwBoot::Application_System_Init` **不做任何迁移前初始化**；它只 `dlopen("appFw.so")` + `dlsym("Application_Start")`，创建 `AppFw` 线程，线程体 `Main` 内才做 `uxengine_init2 → initializeArena → /usr/share/app/ → area_check → global.xdb → 字体命名空间 → Application_Start()`；
- 其内部 dlopen 的是**字面量 "appFw.so"**。我们镜像里 `/usr/lib/appFw.so` 已被移除/改名，因此原桥接实际**从未启动五代 Application_Start**；
- 修正：把 appFwBoot.so 中 `appFw.so\0` 等长改成 `a5pFw.so\0`（8 字符同名长），镜像 `astra-m1-astra3b.img` 后串口首次出现五代 stella 日志：`I/stella(144): Created HeapAllocator`、`Replaced log-hook ...` ——**五代 Application_Start 第一次真正运行**；
- 随后崩溃：`sig=11 pc=0x07DF0A2A lr=0x2D7D64F7`，pc 属于**四代 libObj.so**（base 0x07804000）偏移 0x5ECA2A = `ux::gfxeng::GraphicsEngine::getAreaCheckExtensionManager()`；
- 原因：appFwBoot 自身导入的 22 个 `ux::gfxeng/resmgr/Kernel` 符号在全局作用域里先命中四代 libObj（DEEPBIND 只优先它自己的依赖，而 appFwBoot 没有 a5bObj 依赖）；
- 修正尝试：把 appFwBoot.so 的 `DT_NEEDED libgcc_s.so.1` 原地改名为 `a5bObj.so`（同长字符串、不改布局），让 a5bObj 进入 appFwBoot 的 DEEPBIND 局部作用域，从而优先解析到五代实现；镜像 `astra-m1-astra5.img` 正在验证。

## 十五、第十一轮：输入通道与双消费者定论

input-driver-analyst（`112-input驱动事件通道分析.md`）静态确证：

- `/kmod/input.ko` 事件仅通过 **qid `0x007A0020`、16 B 异步消息** 发出：`{code,0,value,opt}`；驱动另有同步 RPC `0x720018/0x280132/0x18A04D1` 与自有服务队列 `0x410025`；
- 两代 InfraInput **使用完全相同的队列**（四代 RecvThread←0x7A0020、MainThread←0x7A804C；五代同为 0x7A0020/0x7A804C），单条取走、非广播 → 同进程双实例必然抢队列，四代先创建先赢，事件被取走后因四代 InputService 未启动而**静默丢弃**；
- 直接修正方案：
  - A2（推荐、外科式）：四代 libObj 三处字面量改 qid（`0x86270C`、`0x86301C`、`0x863150`），四代实例改为读空队列，五代保留真实队列；
  - A1：把四代构造器 4 处线程创建 NOP（agent 已生成 `imdb4_libObj_noInputThreads.so`）；
  - B/C 为改驱动或进程内直投，风险/侵入更高。

本轮据此生成镜像 `astra-m1-astra7.img`：appFwBoot 修正（加载 a5pFw + NEEDED a5bObj）+ UPM 补丁 + notify 兜底 + A2 输入队列重定向 + bridge7（按原厂顺序 MWF→infra_input→grm→DDS→uxengine 后启动 appFwBoot），用于验证「五代 Application_Start 运行 + 五代 InfraInput 独占事件」是否能出画面。

## 十六、第十轮运行结果：五代应用真正启动、无崩溃、但仍不绘制

镜像演进：

1. `astra-m1-astra3b.img`：appFwBoot 字符串改 `a5pFw.so`（**首次真正运行五代 Application_Start**），串口首次出现 `I/stella(144): Created HeapAllocator` / `Replaced log-hook ...`；随后 `sig=11 pc=0x07DF0A2A`，pc 属四代 libObj `GraphicsEngine::getAreaCheckExtensionManager`（appFwBoot 导入符号解析到四代）。
2. `astra-m1-astra5.img`：appFwBoot 的 `DT_NEEDED libgcc_s.so.1` 原地改名 `a5bObj.so`（同长不改布局），让五代 libObj 进入其 DEEPBIND 局部作用域 → **崩溃消失、无断言**，stella 日志仍出现。
3. `astra-m1-astra7.img`：再叠加 A2（四代输入队列重定向）+ bridge7（原厂顺序 MWF→infra_input→grm→DDS→uxengine 后启动 appFwBoot）→ 全链路无崩溃、无断言，但 `ch53 still 0`、`draw=0`、无帧。
