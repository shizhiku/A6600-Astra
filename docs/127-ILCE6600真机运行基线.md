> 采集时间：2026-11-22 07:0x。设备：`ILCE-6600` / FW `1.10`。

## 一、im.elf 进程画像（关键基线）

```
PID   = 149

State = S (sleeping)
VmPeak= 576500 kB
VmSize= 526460 kB        (~514 MB)
VmRSS =  50540 kB        (~49 MB 常驻)
```

**意义**：

- 证实 `im.elf` **以 root 身份运行** —— 这解释了为什么 ptrace 注入（A6400 项目）和 `/proc/149/*` 读取都可行；
- **181 线程**是我们 QEMU 里"UI 是否真正就绪"的权威判据。此前 ASTRA 运行里线程数远低于此，说明 UI 未达就绪态。

## 三、重大结论：五代"缺失库"确实不存在（再次证实）

真机 `im.elf` 的 101 个已加载库中，**没有**：

- `libgrm.so`、`libgpe.so`、`libDDS.so`、`libuxengine.so`、`libCoreSync.so`、`libInfraInput.so`

这与 `109` 号报告（firmware-hunter）的判断完全一致：**这些库在原厂 a6600 上也不作为独立 .so 存在**，它们要么静态合进 `libObj.so`，要么根本不在本机型上使用。

**因此**：`106` 号报告里 IMDB 表引用的那些库名，属于"跨机型超集"，缺失是**原厂常态**，不是我们的镜像做错了。

## 五、内核命令行（`/proc/cmdline`，关键片段）

```
wdt.timeout=500  wdt.mode=1  xrstreq=1  exception.reboot=1
ramdisk_size=8192  rw noatime noalign
rootfstype=ext2  root=/dev/ram0  init=/sbin/init  initrd=0x700000,8M
mem=1G@0  mem=256M@0x80000000@1
memrsv=704M@0x14000000:uc
cmpr.path=/system/sabin/ssboot.bin
cmpr.path2=/system/sabin/ssboot_any.bin
basic.prof_path=/log/ssbi_prof.bin
exception.console_option=115200n8
cfg.uart=9  error.led=0,0  cfg.poff=10,5
```

**对 F4/F5 的意义**：

- `wdt.timeout=500`、`wdt.mode=1`、`xrstreq=1`、`exception.reboot=1` —— 直接证实看门狗配置存在且启用；
- `cmpr.path=/system/sabin/ssboot.bin` —— **压缩引导镜像路径**，说明 `/system` 里确有启动相关二进制；
- `memrsv=704M@0x14000000:uc` —— 704 MB 保留给 U C（可能是 camera/DSP 侧），解释了我们 QEMU 里为什么内存模型复杂。

## 六、这批数据怎么"加快"移植

| 用途 | 具体帮助 |
|---|---|
| **UI 就绪判据** | 真机 181 线程、VmRSS 49 MB。我们 QEMU 里 ASTRA 运行线程数远低于此 → 可定量衡量"卡在哪一阶段" |
| **库基线** | 101 个库的清单可用于检查我们镜像缺了哪些（尤其 `viewUnified6.so`） |
| **五代缺失库问题终结** | 原厂也没有那 6 个库 → 不必再纠结，可把精力放回 `0x54F664` 阻塞 |
| **F2 反汇编目标** | 真机确实加载 `libupdaterufp.so` / `libupdatertalk.so`，是 F2 的正确分析对象 |
| **F4/F5 证据** | `wdt.timeout=500`/`wdt.mode=1`/`xrstreq=1` 与 owner 经验（60s 挂起→USB）互相印证 |
