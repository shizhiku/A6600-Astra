# 35 · global=4 是状态机刻意发布的状态

本轮为离线分析与 QEMU 观测。无设备写入。

## 一、实参已确认（修正上一轮）

从监视回执的寄存器记录中直接读出（不再依赖易错的反汇编）：

| 命中 | 写入 PC | LR | r0 | r1 | 写入结果 |
|---|---|---|---|---|---|
| 0 | `0x63861ADE` | `0x63D48C53` | 0 | 0 | `00 00 00 00` |
| 1 | `0x63861140` | `0x5F0492BC` | 0 | `0x60000093` | `00 00 00 00` |
| 2 | `0x638614CC` | `0x63860F9F` | `0x6433544C` | 0 | `00 00 00 01` |
| 3 | **`0x63860240`** | `0x6386118D` | **`0x4`** | **`0x10`** | **`04 00 00 01`** |
| 4 | `0x638614CC` | `0x638601D9` | `0x6433544C` | 0 | `04 00 00 02` |

**结论：`global = 0x04` 是调用方显式传入的实参，不是偶然值。**

## 二、反汇编对齐问题已定位

上一轮怀疑的“实参矛盾”源于对齐：`0x638610B0` 起的一串 `01 f0` 重复字节是 `tbh` **跳转表的数据**，不是指令。

从函数起点 `0x63861080` 正确反汇编后可见其真实结构：

```
63861080  push {r3, r4, r5, r6, r7, lr}
...
638610a4  ldrb r3, [r3]        ; 读取状态字节
638610a6  cmp  r3, #0x41       ; 状态范围 0..0x41
638610ac  tbh  [pc, r3, lsl #1] ; 按状态查表分派
638610b0  ...                  ; 跳转表（数据）
```

即这是一个**状态机分派函数**，我们关注的调用发生在某个状态分支内，该分支发布 `state=4, 0x10`。

## 三、判据的语义推断

判据：

```
r5 = ([obj+3] ^ (global << 4)) & 0x7F ; 成功 ⇔ r5 == 0
```

当 `global = 4` 时，要求 `[obj+3] ∈ {0x40, 0xC0}`。

结合状态机发布 `state=4` 的行为，最自然的解释是：

- `global` 是当前期望的**状态/类型编号**；
- `[obj+3]` 是对端帧里对应的**状态/类型字段**；
- 判据在等“对端帧的状态字段 == 4”，编码到字节上就是 `0x40`（`4 << 4`）。

而实测该字节为 `0x04`（低半字节），对应的“类型”是 0。

## 四、与 SIO ch0 缺失对端一致

观测到的帧：`39 0F 54 xx`（第三字节按 0x3E 步进，像序号）、`39 0D 00 04`（第三字节 0x04）。

这些帧在模拟器里来自 **ch0 的 TX 回显**（该通道无对端）。因此：

- 固件发请求 → 读回自己的请求 → 状态字段自然是 0（`0x04` 的低半字节）；
- 期望的 `0x40` 只有真正的对端应答才会带来。

**结论：`global=4` 与判据本身都是自洽的；缺的是对端应答。** 这进一步确认根因，并且说明“把 global 强制改成 0”之类的做法没有依据，不应采用。
