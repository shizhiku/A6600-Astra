# 89 · 对88号待求助清单的证据复核

2026-11-21。复核范围：88号清单、86/87号报告、实际inject_menu7.c和boot_inject.sh、两次注入日志，以及input.ko的既有反汇编。本轮没有启动QEMU，没有修改原清单或固件。

## 结论

清单对“GPU已能绘制、中文界面已出现”的更新应保留。但目前不足以写成“预加载本身破坏渲染”或“ADC已确认不产生事件”。发现四处会影响这些结论的实验问题。

## 1. 所谓不注入的对照组实际仍然执行了注入

88号把 `REA_INJ_DELAY=900` 那组标为“预加载+不注入”。但对应日志：

- `03-证据/模拟器运行/inject-20261121T134254Z-1243/serial.log:570`：`INJ7: armed`
- 同文件`:6751`：`INJ7: MENU pushed`

因此这不是成功排除注入动作的对照。

代码解释与该现象吻合：inject_menu7.c通过 `getenv("REA_INJ_DELAY")` 读取的是**客户机im.elf的进程环境**；宿主给QEMU/启动脚本设置同名环境变量，不会自动出现在客户机进程里。已读的boot_inject.sh没有把这个值写入客户机启动环境；注入器读不到时默认 `alarm(20)`。

建议把清单现有结论改为：

> 在含注入器的预加载配置下，两次运行抓到黑帧；声称禁止注入的对照仍打印MENU pushed，故尚不能区分加载器布局变化、构造函数副作用和注入动作的影响。

真正的第一组对照应是**无构造函数、无线程、无信号注册、无UI调用的最小空DSO**。之后逐步增加被动观测和普通执行上下文中的注入；不要用只改变宿主环境变量来假定客户机禁用了注入。

## 2. SIGALRM注入方式本身需要先排除

实际源码 `<LEGACY_WORKSPACE>\inject_menu7.c`：

- 66–96行：on_alarm内打开并解析 `/proc/self/maps`，读singleton，调用createEvent、pushFilterEvent，最后用stdio写日志。
- 104–114行：安装SIGALRM处理函数并调用alarm。

它不是“仅多加载一个SO”。即使尚未触发注入，也已经修改了进程的信号处理设置和alarm定时器。

SIGALRM处理函数中的stdio、内存分配和加锁路径没有异步信号安全保证。如果信号中断了持有同一锁的线程，处理函数再次加锁就可能卡住。当前证据不能证明这正是本次黑屏的根因，但它是源码中可直接指出、应先去掉的混杂因素。

Linux man-pages直接说明stdio不属于异步信号安全调用；参见：
https://man7.org/linux/man-pages/man7/signal-safety.7.html

建议由普通执行上下文或经过验证的原厂事件队列执行注入。信号处理函数最多只置 `sig_atomic_t` 标志，或用安全write通知既有worker，不直接调用UI API。即使换成普通worker，也仍要核对UI线程/队列契约，不能仅因避开signal就认为任意线程调用都安全。

“只依赖GLIBC_2.4”只验证符号版本这一项，不能推出信号、线程、锁和UI调用契约全部兼容。

## 3. createEvent断点地址算错了

88号第80行给出：

```text
base = 0x057E3000
createEvent offset = 0x003CFAEA
claimed runtime = 0x05BD2AEA
```

实际计算：

```text
0x057E3000 + 0x003CFAEA = 0x05BB2AEA
```

原文地址比正确和式高 `0x20000`。如果实际断点确实设置在0x05BD2AEA，则零命中没有诊断意义。

还要区分Thumb入口：指令地址为base+0x3CFAEA；作为函数指针调用时为base+0x3CFAEB。运行基址必须取当轮目标进程maps/ELF的load bias，不跨运行复用。

该项目前只能确认**清单的算术错误**；尚未核对那次实际启动环境里的REA_BP_VA是否也用了错误地址。

## 4. `get`正在查询键码0，不是订阅最近任意事件

88号记录的输出已显示 `*** Getkey 0x0 ***`。

input.ko写处理：

- `.text+0x270..0x280`：解析命令后附带的数值参数，保存到 `.bss+4`。
- 未给参数时 `.text+0x430..0x438` 将该值置0。

读处理：

- `.text+0x1534`：用 `.bss+4` 打印Getkey标题。
- `.text+0x1548..0x1558`：把同一查询键码传给内部查询助手0xE74。
- `.text+0xEB4..0xEC4` 等位置：对照表项的key code，仅在匹配时处理。

因此，普通 `echo get` 是查询0；输出为0不能证明MENU没有产生，也不是“最近一个任意事件”的全局队列。

至少先改成：

```sh
printf 'get 0x1ac\n' > /proc/udm/input
cat /proc/udm/input
```

在已确认的MENU电平保持期间读取，再在释放后读取；同时记录原始ADC快照。定向get是状态查询，不要把它当成不会丢边沿的事件记录器，仍需要在驱动发送点或InputService入口核对上报。

`value=0x7ffffffe`目前不应自行命名为“无事件”：需要结合内部查询函数的匹配/有效性分支解释。

## 5. `MENU pushed`仅证明函数路径返回，不证明事件有效并消费

v7调用createEvent后直接push，没有复现原厂物理键转换器附加的参数：status(27)、ex_info(28)、sub_id(32)。还需要验证目标消费者对这些字段的要求，以及当前提示页是否接收MENU。

不能据此直接认定事件无效，但也不能把打印 `MENU pushed` 写成“注入器本身工作正常”。更准确的是：

> 已执行到create/push调用之后的日志点；目标事件是否被正确消费、菜单是否激活，尚未证明。

## 建议的求助优先级

先在本地修正四个可验证问题：

1. 用完全空DSO建立真正的“只预加载”对照；核对每组是否出现MENU pushed。
2. 禁止signal handler直接调用UI。
3. 修正createEvent断点地址，记录当轮基址与最终地址。
4. 定向查询 `get 0x1ac`，同时追驱动上报和UI消费。

这些完成后，如果**空DSO仍稳定导致黑屏**，才优先对外询问固定映射、PT_LOAD/堆/共享区布局假设；如果空DSO正常而注入版失败，则优先查执行上下文和事件契约。

建议把对外最高优先问题改为：

> a6600 Appframework中，向InputService投递MENU的已验证执行上下文与最小完整事件结构是什么？我们原先用SIGALRM处理函数直接调用createEvent/pushFilterEvent，现已识别其信号安全风险。另一个声称不注入的对照实际仍执行了注入，正在用空DSO重做隔离。

问题3关于NTSC提示持续时间和待机判据可以保留为待求助项；目前不能从单次vsync截图反推固定状态机顺序。
