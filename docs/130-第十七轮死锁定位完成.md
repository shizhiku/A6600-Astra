# 130 · 第十七轮：死锁定位完成（sched_lock 锁 ID 冲突）

> 时间：2026-11-22。纯离线 QEMU + 静态分析。

## 一、本轮最终定位：`sched_lock(0xf, 0xa)` 死等

用 4 点探针（点已按 capstone 校验为合法指令边界）实测：

```
L_after_schedlock    #1  ← sched_lock(0xf,0xf) 成功返回
M_after_munmap_wrap  #1  ← 0x2B749CC（munmap 封装）返回（第一轮成功）
N_after_9257D8       ✗   ← 0x60E2AE 再未到达
O_after_924500       ✗   ← 0x60E2C2 从未到达
```

**结论**：`0x60E2BE` 的 `blx 0x924500` 阻塞。

## 二、阻塞调用解析：不同锁 ID 的嵌套加锁

`0x924500` → veneer → **`0x2B1B470`**：

```asm
02b1b470  push {r4, r5, r7, lr}
02b1b472  mov  r5, r0
02b1b474  add  r7, sp, #0
02b1b476  mov  r4, r1
02b1b478  movs r0, #0xf
02b1b47a  movs r1, #0xa        ; ← group=0xf, id=0xa
02b1b47c  bl   0x2C2E46C        ; sched_lock(0xf, 0xa)
02b1b480  mov  r0, r5
02b1b482  mov  r1, r4
02b1b484  bl   0x2B7450E        ; 业务函数
02b1b488  movs r0, #0xf
02b1b48a  movs r1, #0xa
02b1b48c  pop.w {r4, r5, r7, lr}
02b1b490  b.w  0x2C2E3C0        ; sched_unlock(0xf, 0xa)
```

而上一层 `0x9257D8` → `0x2B1B524` 用的是 **`sched_lock(0xf, 0xf)`**。

### 关键结构性发现

`0x60E274` 的循环体内，**依次**调用：

| 顺序 | 调用点 | 锁 |
|---|---|---|
| 1 | `blx 0x9257D8` → `0x2B1B524` | `sched_lock(0xf, **0xf**)` … unlock |
| 2 | `blx 0x924500` → `0x2B1B470` | `sched_lock(0xf, **0xa**)` … unlock |

第一轮（`0x60E2AE`）两组都返回；第二轮即在 `0x924500` 处阻塞 → **锁 `id=0xa` 被其他线程占用且未释放**。

## 三、`0x2C2E46C` 确认是 OSAL 调度锁原语

```asm
02c2e46c  push {r4,r5,r6,r7,lr}
02c2e46e  sub  sp, #0x24
02c2e476  bl   0x2C2A7E0        ; 取时间戳
02c2e480  uxth r5, r5           ; group 截断为 16 位
02c2e484  uxth r4, r4           ; id 截断为 16 位
02c2e48e  bl   0x2C2E3B4        ; 内部状态检查
02c2e496  bl   0x2C2C554        ; 取当前线程上下文
02c2e4a4  bl   0x2C2B520        ; 判定结果
02c2e4a8  cmp  r0, #0
02c2e4aa  ite  ne
02c2e4ac  movne r6, #3          ; 失败 → 状态 3
02c2e4ae  moveq r6, #0          ; 成功 → 状态 0
02c2e4bc  movs r2, #6
02c2e4c2  strh r5, [r7, #0xe]   ; 记录 group
02c2e4c4  strh r4, [r7, #0x10]  ; 记录 id
02c2e4c8  mov  r0, r6
02c2e4ca  bl   0x2C2AF70        ; 锁表操作
```

`group=0xf` 是固定的（该模块使用同一组），`id` 区分具体锁对象。**`id=0xa` 与 `id=0xf` 是不同的锁**。

## 四、为什么这是"必须修"的根因

五代 `Application_Start` 的这个 reset 循环需要依次获取 `id=0xf`、`id=0xa` 两把锁来释放对象映射。在**原厂完整系统**里，`id=0xa` 由某个已初始化的子系统短暂持有后释放。

在我们的混合环境里：
- 我们只启动了部分五代子系统（bridge7 的 5 个 init）；
- **持有 `id=0xa` 的那个子系统从未被初始化**，或初始化后线程未运行 → 锁无人释放；
- 因此第二轮 `sched_lock(0xf,0xa)` 永久等待。

## 五、下一轮的三个可行方向（按优先级）

| # | 方向 | 做法 | 预期 |
|---|---|---|---|
| 1 | **找出 `id=0xa` 的持有者** | 静态扫描全 `.text` 中所有 `sched_lock` 封装，统计 `(group,id)` 组合出现的模块与调用者，定位 `id=0xa` 归属哪个业务子系统 | 直接知道要补哪个 init |
| 2 | **探针测锁状态** | 在 `0x2C2B520`（锁判定）处读返回值，确认返回的是"超时/占用"而非其他错误 | 区分死锁 vs 参数错误 |
| 3 | **强制绕过** | 在 `0x2B1B470` 里把 `bl 0x2C2E46C` 的返回值忽略、或直接跳过 lock/unlock | 能让流程继续，但可能导致数据竞争，仅作诊断 |

## 六、本轮方法学沉淀（重要）

| 教训 | 说明 |
|---|---|
| **探针必须落在指令边界** | 用 capstone 逐条列出 `(addr, size)`，探针点 = 调用指令地址 + 其长度。打在 32-bit 指令中间 → `sig=11` 崩溃 |
| **一次最多布 4 点** | 12 点同时布会崩（已验证）；4 点稳定 |
| **`b.w` 尾调用不压返回地址** | 所以"调用点+长度"不一定是有效返回点，遇到尾调用要跟到目标函数内部布点 |
| **veneer 公式** | ARM veneer：`target = V + 12 + word`；不要用 `V+8+word`（偏 4 字节导致反汇编全乱） |
| **Thumb `add rX,pc`** | 16 位编码时 PC = `(addr+4) & ~3` |
