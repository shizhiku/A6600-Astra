# 90 · 对89号问题追踪表的复核

2026-11-21。只读复核89号追踪表、新增两组日志及libObj/input.ko既有静态证据；本轮未启动模拟器、未改固件，也未改89号原文。

## 已经成立的新进展

- `procinput-20261121T141146Z-568/serial.log` 6917–6922明确出现 `Getkey 0x1ac`、`keycode:0x1ac`、`value:0x1`。此前“驱动不识别MENU”的判断应撤回。
- 同轮stderr确实在正确指令地址0x05BB2AEA记录createEvent命中；追踪表报告605次命中。
- 第二轮 `procinput-20261121T141808Z-836` 的callback_direct未命中，至少表明该轮尚未观察到这一条回调路径。

## 仍需修正的四处

### 1. 物理key_code不应直接等同UI event_code

libObj在InfraInput层明确同时存在两个字段，而不是只有一个键码：

- `InputEventList / InfraInputKeyList event`日志分别列出 `key_code`、`event_code`、`status`。
- 另有逐项映射日志：`key_code = 0x%08X, event_code = 0x%08X`。
- 相关接口为 `InfraInput::SetEventKeyList`、`RmEventKeyList`、`SendEventInitData`，并有回调列表、抑制/重复状态。

直接证据：`03-证据/静态分析/input_sen/libObj.so.inventory.txt` 9173–9187行，对应原始libObj字符串0x1012DD3、0x1012DFD、0x1012FB2。

因此，0x1AC已确认是当前物理MENU键码，但还没有证明它也是传入 `InputService::createEvent` 的逻辑eventId。观察到0x15010054等高位事件号，不应只因“不等于0x1AC”就判为MENU丢失；也不能反向声称其中某个就是MENU。

下一步最有价值的是取得当前注册的 `InfraInputKeyList` 中 `key_code=0x1AC` 那一行，确认：

1. 对应的event_code；
2. callback/list是否已注册；
3. 所需status、按下/释放条件及抑制状态。

此前建议直接 `createEvent(self,0x1AC,4)` 的示例也应降级为未验证实验，不能继续当成已确认的MENU事件契约。

### 2. 一条callback零命中不能推广成所有callback未收到

当前新增实验只列明 `callback_direct` 零命中，其余 `callback_convert/panel/tp/convert_cap` 仍在下一步计划里。因此，89号第68、122、144行的“任何callback_*”或“各入口均未收到”过强。

建议改成：

> MENU物理状态查询成功；本轮未观察到callback_direct命中。createEvent已捕获活跃事件，但尚未建立物理MENU与逻辑eventId的映射，尚不能确定丢失环节。

“断在驱动→UI之间”也应改为“待定位的范围”，不能称已定位到具体派发故障点。必须检查驱动真正发送与InfraInput接收，才能区分未发送、未订阅、过滤/抑制和转换后已送达。

### 3. 表内还保留着被顶部撤回的旧结论

89号顶部已经纠正，但问题1正文仍写：

- 第91行“不注入”对照；
- 第95行“不是注入动作导致”；
- 第97行“不是注入器崩溃”；
- 第101行优先推测固定地址布局；
- 汇总第214行“已定位未解决”。

这些与顶部的待复核状态冲突。建议把旧实验行明确标为“原标注，实际仍发生注入”，删除或划为撤回上述排除项，把问题1改名为“含注入器的预加载配置下黑帧，原因待隔离”，状态写“空DSO对照未完成”。

“预加载本身破坏渲染不成立”更准确的表述也是“尚未证实”，并非已经证明预加载绝无影响。

### 4. 下一批断点需统一Thumb地址表示

表中 `callback_convert=0x3D2FB1` 等是带Thumb标志的函数指针值。若现有REA_BP工具按实际PC比较，使用其偶数指令入口：

| 函数 | libObj内指令偏移 | 用作函数指针时 |
|---|---:|---:|
| callback_direct | 0x3D2EA6 | 0x3D2EA7 |
| callback_convert | 0x3D2FB0 | 0x3D2FB1 |
| callback_panel | 0x3D2C40 | 0x3D2C41 |
| callback_tp | 0x3D2FC0 | 0x3D2FC1 |
| callback_convert_cap | 0x3D248C | 0x3D248D |

以上都还需加**该轮**确认的load bias；不能只复制另一轮的绝对地址。callback_direct在表中给的0x05BB5EA6和base0x057E3000的和式相符。

## 建议新的实验顺序

1. 先确认MENU的物理码→逻辑event_code映射以及该条订阅/状态条件。
2. 在同一运行中记录按下前、按住、释放后；同步采集驱动发送、InfraInput接收/派发和目标逻辑eventId，标明客户机时间。
3. 独立重做空DSO对照；它不依赖上述按键映射研究，也不必先实施ptrace远程UI调用或镜像跳转补丁。
4. 对黑帧/提示页差异记录输入镜像与QEMU二进制哈希、抓帧时刻及当时输出缓冲；单一vsync编号不是应用处于同一状态的证明。

现阶段最准确的结论是：**物理MENU状态已验证，逻辑事件映射与分发位置尚待确认；预加载导致黑屏的原因仍未隔离。**
