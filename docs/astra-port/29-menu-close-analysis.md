# 29 · 关闭菜单偶发把屏幕栈写坏（`next=0x0`）

> 时间：2026-11-24
> 现象：按 MENU 关闭菜单后，界面彻底不响应（MENU / FN / LEFT 全部被忽略）

---

## 一、证据

正常关闭菜单时：

```
open screen: scr7001_1001 -> rep_shooting
open screen: rep_shooting -> scr0132_0001        ← 干净地回到拍摄界面
```

出问题时（同一操作，不同时刻）：

```
PCM_OPEN #13: cur=0x27f next=0x2ec opt=0x27f
PCM_OPEN #14: cur=0x2ec next=0x0   opt=0x2ec     ← 目标屏幕 = 0（非法）
（此后不再有任何 open screen / PCM_OPEN）
```

`next=0x0` 之后：

- `KEY_HOST ... rc=0` 仍然出现（事件投递成功）
- 但 `open screen` 再也没出现
- MENU、FN、LEFT 全部无效果
- 渲染泵仍在跑（`RENDER_DRIVER [轮次 N]` 持续）
- 画面冻结在最后一帧

**⇒ 应用层的屏幕栈被写入非法值 0，之后所有导航失效。不是模拟器死机。**

---

## 二、触发条件（目前掌握）

| 观察 | 数据 |
|---|---|
| 全新启动后连按 3 次 MENU | **正常**（17485 → 34694 → 15180 → 34694） |
| 经过若干操作（含 MENU 开关、FN、S1）后再关菜单 | **偶发** `next=0x0` |
| 出现次数 | 本次运行 1 次；另一次运行也有 1 次 |

**不是必现，也不是按键错误**——事件都投递成功（`rc=0`）。

---

## 三、推测原因

`next=0x0` 出现在从 `0x2ec` 关闭菜单的路径上。
`0x2ec` 是 `rep_shooting` 的屏幕 ID；关闭菜单时应用本应算出 `0x1b3`（拍摄主屏），
却算出了 `0`。

可能与应用内部的"返回栈"深度有关：
若当前栈里存在一个未正确弹出的层级（例如之前某次屏幕切换被中断），
关闭时就会取到空项。

相关线索：关闭前出现过 `cur=0x27f`（菜单子屏），说明当时的屏幕层级比平时更深。

---

## 四、影响与应对

| 项 | 说明 |
|---|---|
| 是否影响真机 | **未知**。真机不存在我们的注入时序，可能不复现 |
| 是否可恢复 | 不能靠按键恢复，**必须重启** |
| 对测试的影响 | 每次卡住要重启（约 3~4 分钟） |

### 建议的测试习惯

1. 出现"按什么都不动"时，先让我看日志确认是否是 `next=0x0`；
2. 尽量**少用 MENU 开关菜单**，改用点击/滑动导航（触摸路径目前最稳）；
3. FN 之后不要接着按 MENU —— FN 之后 MENU 一定无效（这条是必现的）。

---

## 五、待查

1. 复现 `next=0x0` 并抓取当时的完整屏幕栈（`g_cached_top_scr`、PCM 内部状态）；
2. 判断是否与"菜单子屏 0x27f 未正常退出"有关；
3. 若能在垫片侧拦截 `next==0` 并替换为合法值（如 `0x1b3`），即可根治。

> 第 3 条是可行的缓解方向：垫片已经 hook 了 `pcm::open_screen`，
> 在 hook 里检测 `*next_scr == 0` 时改写成拍摄主屏，就能避免卡死。
