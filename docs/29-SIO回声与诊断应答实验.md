# 29 · SIO ch0 回声机制与诊断性应答实验

本轮为离线 QEMU 源码修改、编译与运行。无设备写入。

## 一、确认：对象内容来自 SIO ch0 寄存器

在写对象的位置 `0x63A82884` 抓取拷贝源与目的：

```
源 r5 = 0xF2405104 / 0xF2405108     ← SIO 控制器数据寄存器窗口
目的 r0 = 0x640E46A0 / 0x640E47B0   ← 判据对象缓冲区
```

即判据对象是**从 SIO ch0 寄存器窗口读回来的接收数据**。

`cxd90014_sio.c` 的模型注释写明：

> a channel without a slave transfers nothing (receive data stays as is)

本板**只给 ch3 挂了副控制器从设备**（`sony_a6400.c:2017`），ch0 没有从设备，因此固件读到的“接收数据”其实是**它自己写进 FIFO 的发送数据**——回声。

这解释了对象里出现的 `39 0A/0E/0F …` 都是固件自己的帧格式。

## 二、诊断性应答实验（明确标注为假设）

在本地 QEMU 增加仅诊断用的 ch0 应答钩子（`REA_CH0_REPLY=1` 才启用，默认关闭），把收到缓冲的第 3 字节置为 `0x40`。

**这不是保真模型，也不能当作固件真实行为**；目的只是测量“缺少 ch0 对端”对启动的影响。

编译通过后验证钩子确已生效——拷贝出来的内容变为：

```
39 0A FF 40
39 0E 00 40
```

第 3 字节已是 `0x40`。

## 三、结果：故障依旧

| 项目 | 无钩子 | 启用钩子 |
|---|---|---|
| 故障次数 | 1 | **1** |
| 故障 PC | `0x63858ADC` | 相同 |
| 最后 guest 时间 | 2.565 s | 2.564 s |

**注入 `0x40` 并没有让判据通过。**

## 四、这意味着什么

- 判据在重试时刻读到的缓冲区（内容 `39 0D 00 04`）**不是**这次被钩子修改的那份拷贝；
- 缓冲区是**复用的**，重试采样到的可能是更早一帧的内容，或另一个槽位；
- 因此“缺 ch0 应答”虽然是事实，但**不是简单补一个字节就能解决**的。

## 五、当前对故障的完整认识

1. `liro-kliro_66` 线程周期性调用一段判据；
2. 判据读取 `[obj+3]` 与 `global<<4` 比较，期望相等；
3. `[obj+3]` 来自 SIO ch0 的接收窗口，而该通道没有对端，读到的是自身回声；
4. 等待超时后写状态 7、发消息 `0x3A`，随后触发空地址陷阱；
5. 内核进入内置异常监视器并停机，启动终止。

## 六、下一步

1. 精确定位重试**实际读取的那份缓冲**是哪个槽/哪一帧（需要同时记录对象指针与内容变化历史）。
2. 判断该帧应当由哪个对端产生（ISP 核心？另一 RTOS 核？）。
3. 只有在明确对端语义后，才谈设备模型实现；**不应以伪造应答当成修复**。
