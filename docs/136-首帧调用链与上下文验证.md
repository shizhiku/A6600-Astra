## 2. 已找到 drawFramebuffer 的跨库调用者

```text

  0x54FAAE: BL 0x54ED12
    0x54ED36: WidgetSystem::processEvent()，返回非零则循环

      GOT VMA 0x377AFE0

        预期五代 GraphicsEngine::drawFramebuffer 位于 libObj+0xE565A
```

证据：`03-证据/静态分析/136b_appfw_original.txt`，`136b_frame_loop.txt`。

帧函数内 `isFrameDelay` 的计数重试上限为 10；但它调用的 updateFrame 或其他前序调用本身仍可阻塞。不能把计数上限等同于整个函数有超时保证。

因此无需再猜一个 Widget 定时器直接调用 drawFramebuffer。直接调用来自 appFw 的帧函数。更上游如何使其进入仍要看主循环的状态、队列、时间与退出条件。

## 3. 主循环已核实的门控及退出条件

`03-证据/静态分析/136b_frame_schedule.txt`：

- `0x54FA3C` 调 `0x54F2CA`，结果存入 r8；结果为 2 时跳过绘制段。
- `0x54FA64..0x54FA72` 比较时间差与 `0x62F4`；未满足条件时跳过绘制。本轮不推断时间单位或目标帧率。
- `0x54FA76` 调 `0x54F2AE`，结果为 0 时跳过绘制。
- `0x54FAA4..0x54FAA8` 再检查 r8，非零跳过 `0x54FAAE`。
- `0x54FB42` 调 `GraphicsEngine::processSystemMessage()`；返回非零则回主循环，返回 0 则进入 `0x54FB4C..0x54FB5E` 的清理与返回。
- **初始化后 `0x54F6FE` 直接跳 `0x54FB3E`，第一次先执行 processSystemMessage，再决定是否进入循环主体。该函数若首次返回 0，尚未运行到任何帧函数就会退出。**
- `Application_Start+0x2C`（`0x54D5AC`）同步调用 `0x54F664`，不是在此调用点另起一个永久渲染线程。用户观察入口返回时，优先验证是否就是这条首轮退出路径。

所以 Application_Start 被调用并返回，只能证明入口及退出路径执行；不能证明帧循环持续存活。用户报告的 UDF 入口/返回验证不等于本轮新增动态证据。

进一步核实五代 `processSystemMessage`：入口 `libObj+0xE5610` 尾跳 `0x113F4C`；后者读取全局指针 VMA `0x3C82D0` 所指表的 `+0x34` 回调，非空则调用并透传返回；该槽为空时明确返回 **1**，并非 0。因此不能说“缺回调就导致这里退出”；若观察到五代实现返回 0，应追踪实际 `table+0x34` 回调及其返回。全局地址由 `0x113F64` 的字面量 `0x2B437C` 加 `0x113F54` 算得。证据：`136_message_pump.txt`。

另在 `0x54EFE8` 确有 `GRM_fbrmRegisterTriggerFrameworkCb` 注册，参数 r0 来自 GOT `0x37D3A08`，R_ARM_RELATIVE 原始值 `0x54E77B`，即 Thumb 回调入口 `0x54E77A`；r1 为外层对象。回调的全部动作是把传入对象 `+0x890` 置 1 后返回。它没有直接调用 drawFramebuffer，也不能仅由名字认定是 vsync。

`0x54F2AE` 的实际门控：`this+0x890 != 0` 时直接返回 1；否则调用 GRM_fbrmCheckUpdateFinished，把其等于 0 的结果转为 1。`0x54F2CA` 的状态分类：`this+0x890 != 0` 或全局 dirty 标志非零时返回 0；其他分支读取辅助对象 `+0x1AE/+0x1B0` 和外层 `+0x870`，可返回 0、1、2。具体字节的业务意义仍需运行验证。

这说明 fbrm 强制成功只放行 `54F2AE` 的一条门；不会覆盖 `54F2CA` 状态、时间阈值、前序阻塞或主循环退出。证据：`136b_gates.txt`、`136b_final_verified.txt`。

## 5. 两代均含 Gemini-OGL，不能由 ko 大小判不支持

`03-证据/静态分析/136_backend_inventory.txt` 核实：

- 四代和五代 libObj 均含 `source/GraphicsSystem_gemini.cpp`、`GraphicsContext3DOGL`、`/dev/dmpgles2`、`eglCreateContext`、`eglMakeCurrent` 名称。
- 两者 dynsym 均无 egl*/gl*，DT_NEEDED 也均未列出 libEGL/libGLES。
- 名称存在证明静态内容存在，不证明本次活动后端、上下文创建成功或两代 ABI/命令流兼容。
- 五代文件 offset `0x352FE8`（VMA `0x35AFE8`）是 `eglCreateContext` 的 48 字节名称槽；offset `0x353048`（VMA `0x35B048`）是 `eglMakeCurrent` 名称槽；均不能当函数入口或已恢复的函数指针表。

GLES 是用户态图形接口；P3D 是当前模型处理的设备提交路径，两者可以是同一条链的上下层。DMP 模型的 reg0x202 draw、list 提交及 IRQ 合同不能证明完整 GLES 已可用，也不能反过来证明 GLES 不会走这些寄存器。模块仅 9348 字节不能证明缺失用户态 GLES。

## 6. 本地 bridge7 的独立线程风险

`04-产物/97_astra_bridge7.c` 的 `run` 在调用 init 后立即返回；每个 call_init 创建一个新 pthread 并 detach。MWF、infra_input、grm、DDS、uxengine 因此在不同临时线程执行，后续 AppFw 另有线程。

这只重现调用先后，不重现原厂线程/TLS/上下文生命周期。若图形 init 在临时线程 make-current，而实际渲染线程从未绑定同一上下文，可出现创建日志正常而渲染不可用。必须实测创建、绑定、绘制线程的 TID；不能仅凭这份代码断言根因已定，也不能未经核实把所有 init 任意挪到同一线程。

grm_init 返回 -1 也不能直接解释为 EGL 失败：本地反汇编有入口早退、115824 判零早退和末尾 116AA8(0x4000) 位测试；需要采实际退出路径及相关全局，确定该位领域语义。现有桥接还把所有 init 统一强转为 int(const char*)，返回寄存器应结合真实 ABI 解释。

## 7. 最小动态实验顺序

1. 固定已知可复现镜像及 6 MiB 栈扩容 preload；每轮只布 2–3 个低输出探针，避免既有时序问题。记录库身份、load bias、TID、命中次数与首次若干寄存器。
2. 第一轮：appFw+54ED12、appFw+54ED82、主循环 processSystemMessage 返回点 54FB46。读取解析后的 draw GOT。若 54ED82 到而五代入口不到，先查实际绑定/跳转。
3. 若帧函数不到：在 54FA3C 返回、54FA76 返回、54FAA4 采状态；必要时上移到主循环等待/回调注册。按轮分开。
4. 若帧函数到但调用点不到：首先核对 54ED36 的 processEvent 是否持续返回非零或阻塞，再逐段检查资源处理、updateFrame、notifyDraw。不要继续用底层 fbrm patch 代替上游到达验证。
5. 图形上下文另做一条证据链：实际后端对象/虚表 → create 结果 → render TID 上 current/bind 结果 → 小图 clear/readback → 提交 → IRQ/完成 → present。若提供标准 EGL，则核对 initialize、config 数量、surface/context handle、makeCurrent 返回和同线程 getCurrentContext；若静态私有实现，探其真实入口和返回，不能期待 preload 自动拦住同库直接调用。
6. 对 /dev/dmpgles2 的 open/ioctl/mmap 做低噪声跟踪：fd、request、入出结构、返回值、errno（仅失败时有解释力）、映射结果和线程。仅 syscall 返回成功不能证明模型已经实现命令流。
7. 上下文与首个命令提交均证实后，再判断 dmp_smaph 是否缺状态、shader/texture、同步或呈现协议。没有到达硬件前，不以 GPU kick=0 归咎缺某条 GPU 指令。
