## 问题 1（最高优先）：`ld.so.preload` 会破坏渲染

### 现象

我们在 `/etc/ld.so.preload` 里放了一个自制 ARM 共享库（只依赖 `GLIBC_2.4`，与相机 glibc 2.11 兼容），用于向 UI 注入事件。三组对照实验：

| 配置 | 抓帧时刻（vsync） | 结果 |
|---|---|---|
| **无预加载**（基线） | 3000（约 50 秒） | ✅ 显示「运行于NTSC。」 |
| 预加载 + 注入 MENU | 1200 / 1800 / 2400 / 3000 | ❌ **四帧全黑** |
| **预加载 + 不注入**（`REA_INJ_DELAY=900` 使注入不触发） | 3000 / 3600 | ❌ **两帧全黑** |

注入器本身工作正常（控制台打印 `INJ7: armed` / `INJ7: MENU pushed`），且预加载**没有报任何符号/加载错误**。黑屏与"有没有注入"无关，**只与预加载有关**。

### 我们的推测

该固件 UI 可能依赖固定的虚拟地址布局（大量固定物理/虚拟映射、固定地址的堆或共享内存），预加载一个额外共享库改变了 `mmap`/`brk` 的分配位置，破坏其假设。

### 具体问题

1. a6600 / CXD90045 的 AppFramework 是否存在**固定虚拟地址映射**（例如固定 `mmap` 到某个 VA、或依赖 `brk` 起点）？预加载一个 `.so` 是否会破坏它？
2. 如果是，除了 `ld.so.preload`，有没有**不改变加载布局**的用户态注入手段被验证可行？
   - 例如 `ptrace` 附加后用远程调用执行 `InputService::createEvent` / `pushFilterEvent`；
   - 或者在固件镜像里 patch 一个周期性调用的函数，插入跳转到自建代码段。
3. 有没有已知的 a5000/a6400 项目做过"运行期往 UI 注入按键"，用的是什么方式？

## 问题 2：驱动读到了 ADC 值，但不产生按键事件

### 已确认的键表（`/proc/udm/input` 的 `table` 模式实读）

```
*** ADC KeyConfig ***
ID: 0-1  port: f-0    0/ 5b 10[ms] 1[jif] H2 key: 1ac-1   ← MENU
ID: 0-1  port: c-0    0/ 5b 10[ms] 1[jif] H2 key: 1f8-1   ← PLAY
ID: 0-1  port: d-0    ...                 H2 key: 70e7-1 / 66-1
ID: 0-1  port:10-0 / 11-0 ...             H4 key:7025-x   ← 多向选择器
*** FRONT(CA) KeyConfig ***  key: 2 / 1f7 / 1ab / 70d5 / 7094
```

**MENU = `0x1AC`，ADC 全局端口 `0x0F`，有效电平 `0x00–0x5B`。**

### 已做的注入

在 QEMU 里直接给第二个 ADC 单元（`cxd90014-adc` 实例 1）的通道 3 写入电平 `0x20` 并保持（全局端口 `0x0F` = 单元 1 × 12 + 通道 3）。

### 观测结果

- 在 ADC 模型里加日志，确认驱动确实读取了该值：`[ADCRD] ch=3 val=0x0020`（多次）；
- `/proc/udm/input` 的 `adc` 模式也显示 `Ch1:Port 3 0020`；
- 但 `echo get > /proc/udm/input; cat /proc/udm/input` **始终**是：
  ```
  *** Getkey 0x0 ***
  keycode:0x0
  subocde:0x1
  value:0x7ffffffe
  ext:0x0
  ```
- 逐通道扫描 ADC ch0–ch7（每通道 5 秒）后轮询 `get`，全部 `0x0`；
- 在 `InputService::createEvent`（`libObj+0x3CFAEA`，运行时基址 `0x057E3000` 已从 `/proc/144/maps` 确证 = `0x05BD2AEA`）下断点，**零命中**；
- 按键扫描线程 `kbd_timer_hndlr`（`input.ko` 内偏移 `0x21e4`，模块基址 `0x5f07c000`）断点**持续命中**，说明扫描在跑。

### 具体问题

1. `input.ko` 的按键扫描是否**必须由副控制器的 UIPC 帧驱动**才会采样？（驱动打印的是 `*** ADC UIPC data ***`，我们怀疑 ADC 快照来自 UIPC 而不是本地 ADC 寄存器。）
2. 键表里的 `H2` / `H4` / `L1` / `L2` / `L4` 是什么含义？是否要求特定的**边沿/去抖/连续命中次数**（表里的 `10[ms]` 和 `1[jif]` 是去抖与计数吗）？
3. `get` 模式显示的到底是"当前按键"还是"最近一次上报的事件"？如果是后者，有没有别的办法确认扫描器看到了 `0x20`？
4. 全局端口 `0x0F` 映射到"第二 ADC 单元 local ch3"这个换算是否正确？`/proc/udm/input` 的 `adc` 模式只打印每单元 12 个端口（0–11），而键表里出现 `0x10`/`0x11`，说明端口号可能另有编码。

## 四、附：我们已排除的路径（不必再建议）

| 假设 | 结论 |
|---|---|
| 按键走 `/dev/input/event*` | ❌ UI 从不打开（libc `open`/`openat` 钩子零命中） |
